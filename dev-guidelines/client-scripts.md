# Client-side scripts

`js/` has 18 files, plus per-series hero bundles under `series/<slug>/`. 15 are plain classic scripts (`<script>` tags, no bundler needed to ship them). The other three are ES modules: `js/three-viewer.js`, which needs to `import` the `three` npm package (only a module script can); `js/viewer-entry.js`, the tiny module the pages actually load (`<script type="module">` in `<head>`) that fetches the first one lazily — see below; and `js/hdr-worker.js`, a module **worker** (`new Worker(new URL("./hdr-worker.js", import.meta.url), { type: "module" })` in `three-viewer.js`) that decodes the HDRI off the main thread — see `loadEnvironment` below. Despite the different script *kind*, they are fully part of the live site, not dev-only files — see `tooling.md` for why an ES module is safe to mix into an otherwise-classic-script codebase, and `pages.md` for the exact load-order mechanics.

## Load order (see `pages.md` for the full page × script matrix and the `defer`/blocking explanation)

`js/scroll-memory.js` is blocking in `<head>` on `index.html` only, and is the **first** script on that page — ahead of `series.js` — because its height reservation has to be in place before `<body>` is parsed. `js/loader.js` is blocking in `<head>` on every page, right after it (and before `series.js`), because the arrival cover has to be up before `<body>` is parsed and every page's scripts use `window.EmjiveLoader`. `js/series.js` is blocking in `<head>` on every page, so `window.EmjiveSeries` and `window.EmjiveHero` exist before anything else runs. **Everything else is `defer`red**: each page's body scripts download in parallel with the parser and run in document order once it is done, behind `viewer-entry.js` (a module, in `<head>`, so first on the deferred queue) — which is why `window.EmjiveLoadViewer` exists before any of them runs. They used to be plain parser-blocking scripts, and the parser waited on each file in turn: a staggered chain of round trips that held `product.js`, the 3D module and the arrival loader back by about a second on a slow link. **That document order is the contract**: `selection.js` before anything that touches `window.EmjiveSelection`; `order-rows.js` before `selection-bar.js` (which builds its drawer rows with it at load); `focus-trap.js` and `carousel.js` before `product.js`. On `index.html` and `product.html` the order is `focus-trap`, `selection`, `carousel`, `order-rows`, `metal-picker`, `modify-modal`, `selection-bar`, then `main.js`, then `product.js` — `main.js` last, as it was when it was the only deferred one. On the other pages `main.js` comes first in the body (`series.html` slots `series-page.js` in straight after it), then the same helpers, `selection-bar.js` last (`launch-order.html` has `selection-page.js` instead of it). `viewer-entry.js` does **not** guarantee `window.EmjiveModelViewer` exists: the viewer module is a lazy chunk, so every consumer goes through `EmjiveLoadViewer()` (or checks `typeof window.EmjiveModelViewer === "function"` and degrades to the icon). `modify-modal.js` asks for it only once a row has been tapped.

A series' `hero.js` loads later still — injected at runtime by `series.js` — which is why it's written to be inert until called.

## `js/viewer-entry.js` — the lazy loader for the viewer

The only 3D thing the pages load up front (~2KB). `three-viewer.js` plus three.js is ~645KB minified (~168KB gzipped), so it is pulled in with a dynamic `import("./three-viewer.js")` instead of a `<script>` tag: pages that never draw a model (`terms`, `archives`, …) never download it unless a Modify sheet is opened, and the ones that do fetch it after their first paint rather than ahead of it. It is a module because only a Vite-processed module can have that import resolved to the hashed chunk (the classic scripts are copied verbatim).

`window.EmjiveLoadViewer()` → promise of the viewer factory (the same function `three-viewer.js` also still assigns to `window.EmjiveModelViewer`); the result is cached **including a failure**, so a visitor whose connection dropped keeps the icon fallbacks rather than retrying on every scroll. When to start fetching is `<html data-viewer="…">`: `idle` (`index.html`) — not at the first idle moment, as it used to be (on a slow link that was while the hero picture was still downloading), but once the page has revealed (`js/loader.js`'s `pageReady()` dispatches `emjive:pageready` on `window`, and `EmjiveLoader.isPageReady()` covers a script that starts after it) **and** the browser is idle, or at once on the first scroll/wheel/touch/pointer/key, with a 10s backstop for a page that never reveals; `eager` (start now) is still supported but **no page uses it** — `product.html` did, waiting up to 8s for the chunk before building anything, but its first paint doesn't need it and the download competed with the images that do; absent (everything else) — only when something asks: `product.js` asks once its first paint is in (see its section), `modify-modal.js` when a sheet opens. Consumers: `main.js`'s `startViewerLoad` (not loaded yet → ask, then `scheduleReconcile()`), `product.js`'s `mountViewer`/`attachViewer` (guards + try/catch → icon slide), `modify-modal.js`'s `scheduleViewer` (asks while the sheet slides in). `scene-tool.html`, `loader-test.html` and `auto-render.js` still load `three-viewer.js` directly as a module.

**`?mem=1`** — adding it to any address puts a small fixed read-out in the corner of the page (built at the bottom of `viewer-entry.js`; nothing runs without the parameter). It exists because iOS Safari ends a tab that uses too much memory and reloads it, and from a Windows machine there is no inspector to attach to a phone. It shows `window.EmjiveMem`'s numbers: live 3D viewers (the gallery allows 3, a product page 1), decoded model geometry still held as JavaScript arrays (should fall to ~0 once every live model has drawn), the GPU objects the live renderers hold, Draco workers alive (0 a few seconds after the last load), whether the window counts as a **phone** for the image variants (a "NO" on a phone means the big desktop pictures are loading) with the window size, aspect ratio and pixel ratio it was judged on, and the JS heap where the browser reports one (not iOS Safari).

## `js/three-viewer.js` (~2660 lines) — the 3D viewer, and the largest file here

The single shared construction path for every 3D product view on the site (homepage grid cards, the product-detail carousel, the Modify sheet's small carousel) and for `scripts/auto-render.js`'s render pipeline — see `tooling.md`. A raw three.js scene per instance, driven by the `TrackballControls` addon (free, pole-crossing rotation — unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have), with a substantial amount of hand-tuned polish layered on top. Exports (all module-internal except the one exposed global):

- **One** module-scope `DRACOLoader` and **one** module-scope `GLTFLoader`, built once at module scope with the decoder attached once — not a fresh `GLTFLoader` per load. Unlike `loadEnvironment()`'s PMREM texture, neither holds per-context state, so one of each safely serves every viewer on the page. This is not a tidiness preference: a `DRACOLoader` per load is the single most-reported cause of Draco failing specifically on **iOS Safari** (three.js#22445, discourse#68835), because each instance spawns its own worker pool and its own WASM heap. Three further settings, all aimed at the same device:
  - `setDecoderPath(new URL("assets/draco/", document.baseURI).href)` — resolved **once, absolutely**, rather than left as the bare relative string `"assets/draco/"`. `DRACOLoader` resolves its paths against the *document*, which is fine while every page sits at the repo root and breaks silently — and only for Draco models — the moment one doesn't.
  - `setWorkerLimit(...)` — lowered from the default 4 to at most 2 (`hardwareConcurrency - 1`, capped). Every viewer here decodes exactly one model and the grid keeps only a handful alive, so extra workers can never be usefully busy; each one is just another structured-clone copy of the decoder config, `wasmBinary` included.
  - `preloadDracoDecoder()` — calls `dracoLoader.preload()` the first time any model load starts, so the decoder's ~336KB downloads *in parallel with* the `.glb` rather than serially after it. Guarded so pages that never show a model never pay for it.
  - **Idle workers are ended** (`releaseDracoWorkers()`): a Draco worker is a WASM heap that only grows, and decoding a big model leaves the worker that did it holding a heap of that order for the page's life. `DRACO_IDLE_RELEASE_MS` (4s) after the last model load settles — immediately on `pagehide` and `visibilitychange → hidden` — the pool is terminated and emptied; `DRACOLoader` starts a new worker on the next decode. It deliberately does **not** call `DRACOLoader.dispose()`, which also revokes the worker's source URL while the loader keeps its already-resolved decoder promise, so the next decode would start a worker from a dead URL. Model loads go through `loadModelFile()` (a counted `gltfLoader.load`) so the release knows whether a decode is still running. `workerPool` is the loader's own field and the code guards on it being an array: if a later three.js renames it this degrades to the old behaviour (workers stay), not to a crash.

  Three's own decoder files are self-hosted under `assets/draco/` rather than pulled from the Google CDN three.js's examples default to, so the site stays fully offline/no-external-requests — see `assets.md`. **Every** product `.glb` now ships `KHR_draco_mesh_compression`. Without a `DRACOLoader` attached, `GLTFLoader` doesn't degrade gracefully for a Draco model — it throws synchronously (`"THREE.GLTFLoader: No DRACOLoader instance provided."`), the load promise rejects, and the viewer's own fallback behavior makes that read as an inert, undraggable model with no visible error — exactly what happened the one time rib-cage/rib-cage-extended shipped ahead of this being wired up.
- `METAL_PRESETS` — PBR values (`baseColorFactor`/`metallicFactor`/`roughnessFactor`) per metal name, the single source of truth repo-wide (also reused by `scripts/auto-render.js`'s harness, since it loads this exact module). Must stay in sync with `data/series.json`'s top-level `metals` list — see `procedures.md`'s "adding a metal" checklist. `metalToStandardMaterialParams()` converts a preset to `THREE.MeshStandardMaterial` params. Also exposed live as `window.EmjiveModelViewer.METAL_PRESETS` (tool-only — `main.js`/`product.js` never read it) — `applyMetal()` and every viewer build already re-read `METAL_PRESETS[metalKey]` fresh on every call, so `scene-tool.html`'s shader-tuning sliders just mutate this object in place and re-invoke `applyMetal()`/rebuild to preview a change instantly, with no separate override-parameter path needed.
- `parseOrbitConfig()` / `parseTargetString()` — parse `product["3d-viewer-camera-default"]`'s `{ rotation, tilt, zoom, roll }` object (descriptive names for what used to be a single `"<theta>deg <phi>deg <radius%>"` string, the convention a `<model-viewer camera-orbit>` attribute would have used; `roll` — spin around the camera's own view axis — has no equivalent there, it's new) / `cameraTarget`'s `"Xm Ym Zm"` string format into the radians/percent the camera-framing math needs. `roll` defaults to 0 (level) when omitted, true of every product predating the field. Two more optional fields exist for the swatch alone (see `options.swatch` below) and are `null`/absent for every product: `target: [x, y, z]` orbits that point instead of the model's own centre, and `envRotation` (degrees) turns the HDRI about Y by setting `scene.environmentRotation`.
- `loadEnvironment(renderer, hdriSrc, isStale, blurPx)` — loads + PMREM-converts an HDRI into an environment map. `hdriSrc` is the caller-resolved path (`data/series.json`'s top-level `hdris` map, looked up via a series' own `hdri` key by `js/series.js`'s `hdriPath()`, or `scripts/auto-render.js`'s own equivalent resolution — see `data.md`); an omitted/unresolved value falls back to the module's own `DEFAULT_HDRI_SRC` (`studio_kontrast_04_1k.hdr`) — this module is deliberately series-unaware, and `auto-render.js`'s headless harness never loads `js/series.js` at all, so it can't resolve a key here either way. Rebuilt fresh for every `buildThreeViewer()` call, never cached/shared across instances despite two viewers often resolving to the same file (any two showing series that picked the same `hdris` key): a PMREM texture is a GPU resource tied to the specific `WebGLRenderer`/context that built it, and each instance has its own renderer. An earlier version cached this at module scope, meant to be reused across the homepage grid's several simultaneous viewers — that handed later instances a texture handle from a different (invalid) context, which silently rendered them solid black, since this scene has zero `THREE.Light` objects and depends entirely on `scene.environment` for lighting. The PMREM step and the GPU upload therefore stay per-instance — but the *decode* no longer is: `loadHdrSource(src)` memoizes the loaded `DataTexture` per URL (sharing one in-flight promise, so N viewers appearing during one scroll trigger exactly one decode between them), and each call then wraps that one shared pixel buffer in a throwaway `DataTexture` purely so PMREM can upload it into *this* renderer's context, disposing the wrapper immediately after. Disposing a `DataTexture` frees the GPU copy and never the JS typed array behind it, so the cached source survives untouched. That removes N-1 fetches and, more importantly, N-1 RGBE→half-float decodes — tens of ms of main-thread work each, previously repeated once per grid card. (The cached value is now a plain object — `{ image: { data, width, height }, format, type, colorSpace, filters, … }`, made by `hdrSource()` — not a `DataTexture`; `loadEnvironment` only ever reads those fields.) A failed load evicts its own cache entry so a later viewer can retry rather than inherit a permanently-rejected promise. **That cache is dropped wholesale on `pagehide` and on `visibilitychange → hidden`** (`releaseHdrSources()`, skipped while a decode is in flight — clearing mid-load wouldn't cancel it, it would just guarantee the next caller starts a second one). What it costs is invisible in a heap profile, because a `DataTexture`'s pixels live in an external `ArrayBuffer` rather than the JS heap: Bones' `studio_kontrast_04_1k.hdr` is 1.4MB on the wire and decodes to 1024 × 512 half-float RGBA — ~4.2MB — held at module scope for the life of the document. (Both figures were 4× larger before `npm run optimize-hdri` halved the source; the cache mattered proportionally more then, and still earns its keep.) Worth every byte while viewers are being built and rebuilt during a scroll, and worth nothing once the page is frozen or backgrounded, which on iOS is exactly when the memory is wanted elsewhere; the price is one re-decode on the next viewer built after the visitor returns. `loadEnvironment` returns the whole **`WebGLRenderTarget`**, not just its `.texture` — `PMREMGenerator` hands target ownership to the caller (`pmremGenerator.dispose()` frees only the generator's own scratch resources), so disposing the texture alone would strand the target's framebuffer. The download has a real error callback (logs + rejects) — without one, a failed HDRI request used to leave the returned promise neither resolved nor rejected, silently hanging `Promise.all([modelPromise, environmentPromise])` below forever with zero console output. `isStale()` (the viewer's `isDisposed`) is checked once the pixels arrive: a card scrolled past mid-load has had its renderer released and its context force-lost, so the PMREM build is skipped (the promise resolves `null`) rather than run against a dead context. `blurPx` (optional; the swatch's `"swatch-blur"`, passed as `options.environmentBlur` — products never pass one) is a **gaussian blur of the HDRI itself**, its sigma in pixels of the HDRI image: `PMREMGenerator.fromEquirectangular()` has no blur, so with one the HDRI becomes the `background` of a throwaway scene (`EquirectangularReflectionMapping`) and goes through `fromScene(scene, sigma)` — sigma `blurPx · 2π / image.width` radians, cube faces a quarter of the image's width, as `fromEquirectangular()` makes them; without one, the original path.
- **HDR decode worker** (`decodeHdr()`, `js/hdr-worker.js`) — `loadHdrSource()` downloads the `.hdr` itself with a `THREE.FileLoader` (arraybuffer) on the main thread — that has to be the page's own request, so the `<link rel="preload" as="fetch" crossorigin>` `product.js` adds for it is matched rather than downloading the file twice — and hands the bytes (copied, not transferred) to a module worker, which runs `HDRLoader.parse()` and transfers the half-float pixels back. PMREM and the GPU upload stay on the main thread (WebGL is). It is used only where Vite bundled the module: `typeof import.meta.env === "undefined"` on a page that loads `three-viewer.js` unbundled through an import map (`scene-tool.html`, the `auto-render` harness), where a module worker could not resolve `three` anyway. Any failure — no module workers, the worker script missing, a decode error (`worker.onerror` retires the worker and re-runs the pending jobs) — falls back to `new HDRLoader().parse(buffer)` on the main thread, the same function, so the result is identical either way. The worker is created on first use and lives for the page.
- `buildThreeViewer(product, metalKey, options)` — builds one viewer instance: `WebGLRenderer` + `Scene` + `PerspectiveCamera` + `TrackballControls`, a `ResizeObserver`-driven canvas that always exactly fills its container, a poster `<img>` (sourced from `product.assets["fallback-img"][metalKey]` — see `data.md`) shown until the model's first frame renders, and — layered on top of the base rotation — release inertia (frame-rate-independent, re-derived from a continuous decay rate rather than assumed-60fps, with an added progressive-braking boost at low speed so a coast stops crisply instead of trailing off), a continuous two-attractor up-vector leveling drift (pulls toward the product's resting roll — see the roll paragraph under `options.freeOrbit` below — fades to zero at the poles, flips sign continuously through the equator rather than snapping), a bezier/slerp-based "ease back to the default pose" idle reset, and a 3-phase idle "nudge" hint (a small camera wiggle synchronized with a floating hand-shaped overlay — a plain `<div>`, not an `<img>`, whose visible pixels come entirely from a `backdrop-filter: invert(1)` clipped to `assets/hand-pointer-thumb-opened.svg`'s silhouette used as a CSS mask, so it reads as a color-inverted cutout of whatever's underneath rather than a fixed-color icon; see `styling.md`) — suppressed session-wide via `sessionStorage["emjive_model_interacted"]` once any instance has actually been dragged (a real drag, not just a tap — same 6px-distance-threshold pattern `main.js`'s click-navigation uses). Returns `{ el, whenSettled, applyMetal(newKey), setCameraOrbit(orbitConfig), target, dispose() }` — `whenSettled` is a promise that resolves when the model's download-and-decode and the environment have both finished one way or the other, **whether or not the viewer was disposed first** (a dispose cannot cancel a decode already running — three's loaders take no abort signal — so a caller that rations concurrent loads, `main.js`'s grid, waits on this instead of assuming that discarding the viewer ended the work); — `setCameraOrbit` is an instant (non-animated) reposition, used by the render harness (see `tooling.md`) and by `scene-tool.html`'s rotation/tilt/roll/zoom fields; `target` (tool-only) is the live `controls.target` `Vector3` reference, needed to read a camera pose back as numbers (`scene-tool.html`'s whole reason for existing — nothing else in the codebase computes this inverse, roll included — see `options.freeOrbit` below); `dispose()` tears down the animate loop/`ResizeObserver`/`TrackballControls`' own `window`-level key listeners, disposes the loaded model's own geometry/materials and the HDRI environment's PMREM texture (real GPU memory, tied to this renderer's context — not freed by `renderer.dispose()` alone), then calls `renderer.dispose()` followed by `renderer.forceContextLoss()` — the latter is what actually returns the WebGL context to the browser's finite per-page budget, since `renderer.dispose()` alone only frees the renderer's own bookkeeping (shader program cache, render lists), not the context itself. It then shrinks the canvas to 1×1, which neither call does: WebKit keeps a canvas's backing store (its multisample buffer included) until the element itself is collected. Originally `scene-tool.html`-only (builds-and-replaces a viewer every time its HDRI/model selection changes, and without a real teardown each switch leaked all three) — `main.js`'s grid now calls it too, repeatedly, as cards scroll in and out of `disposeObserver`'s range (see its own section below), which is exactly why the geometry/environment/context-loss teardown was added: the original renderer/controls-only version would have leaked exactly the GPU memory that lazy build/dispose scheme exists to cap. Returns `null` instead, without throwing, if the browser can't grant a WebGL context (a finite per-page budget — several simultaneous viewers, bfcache-retained contexts from earlier navigations, a weak/mobile GPU) — `main.js` and `product.js` fall back to the plain `assets.icons[metalKey]` image in that case, same as a product with no `assets.model` field at all, and `modify-modal.js` keeps showing the `assets["fallback-img"]` image it opened on. Calls `controls.handleResize()` on every real resize (not just once at construction) — `TrackballControls` caches the element's screen rect itself rather than measuring fresh per pointer event, and at construction time the wrapper is still a detached `<div>` (the caller hasn't appended it to the page yet), so skipping this left `screen.width` permanently stuck at 0 and every drag silently a no-op (NaN rotation deltas, falsy, quietly skipped).
- `options.swatch` (tool/harness-only; truthy) — swaps the loaded GLTF for the **metal swatch scene**: `buildSwatchStack()` makes **one** sphere (radius 1) at the origin, and `applyMaterial()`'s mesh traversal gives it the current metal like any model — so `applyMetal()` re-tints it, which is how every swatch render changes the shader and how `scene-tool.html`'s live shader edits reach it. It is **lit by an HDRI** (`options.hdri`, as any product is) and nothing else — no light of its own — optionally blurred (`options.environmentBlur`, see `loadEnvironment` above). Everything downstream (`frameCamera()`'s bounding-sphere measurement, controls, the animate loop, `freeOrbit`, `dispose()`) is already agnostic to how `modelRoot` was built, so this is the only branch needed; `product` can be a minimal stub (`product["3d-viewer-camera-default"]`/`name` only, `product.assets` is never touched). The camera is **solved from three angles**: `window.EmjiveModelViewer.swatchOrbit({ rotation, tilt, roll })` (`data/series.json`'s `"swatch-camera"`; a missing one is 0, 90, 0) returns the whole orbit — the camera standing round the sphere at those angles (the product cameras' three: rotation round the vertical axis, tilt 90 = eye level, roll the picture's turn; `target` at its centre) at `SWATCH_DISTANCE` = 12 radii, with a **`fov`** (an orbit field of its own, read by `parseOrbitConfig()` and applied by `frameCamera()`; only the swatch passes it) that makes the frame **the biggest square inside the disc the sphere shows** — the same from every angle, a sphere being round: seen from `d` the silhouette is a circle of angular radius `asin(r / d)`, the inscribed square's half-side is `tan(that) / √2`, so `fov = 2 · atan(tan(asin(r / d)) / √2)` (≈ 6.77°), and `zoom = 100 · d · sin(fov / 2) / groupRadius` (the sphere's bounding box's half-diagonal, √3 radii: `frameCamera()` measures zoom against it). Used by `scene-tool.html`'s swatch mode and `scripts/auto-render.js`'s swatch renderer (see `tooling.md`) — this **replaced** a scene of three spheres under one point light and a uniform white environment (`swatch-light`), before that the tube-and-HDRI scene (a long tube per metal, turned by `swatch-rotation`, in a 1600×48 strip), the earlier single-`options.primitive` swatch (cylinder/box/sphere/torus, camera authored by hand as `swatch-camera`), and before that a separate `buildMaterialSwatch()`.
- `options.static` — harness-only (never set by the interactive site): skips the idle-nudge hint and the continuous per-frame animation loop entirely (only explicit `render()` calls, so nothing can shift the framing between the harness's `onReady` firing and its screenshot being taken a few ms later). One of those explicit calls is in `applySize()`: a resize wipes the canvas, and with no animate loop to consume `needsRender`, a static viewer repaints right there instead. That matters because the wrapper is still detached when the ready path's own render runs, so the `ResizeObserver` delivering the real size can land *after* it. Product renders never hit this (their model download always outlasts it), but a swatch, whose HDRI decode is already cached by the products rendered before it, does. Without the repaint, every metal swatch from the HDRI cache's arrival (`9b2ec03`) until this fix was a fully transparent WebP. The repaint is skipped for a viewer that's disposed or whose wrapper has left the page, since `auto-render.js` clears the body between renders without disconnecting old observers. `options.transparentBackground` — also harness-only, controls `preserveDrawingBuffer` (needed for an external screenshot readback of the canvas; the interactive site never reads its own canvas back). The renderer's alpha itself is unconditional now (both the interactive site and the harness render on a genuinely transparent canvas) — an earlier version kept the interactive site's canvas opaque on purpose to dodge a subtler ACES-tone-mapping edge-blending artifact, which traded it for a much more visible bug (a solid near-black square behind every model wherever the canvas wasn't covered by geometry).
- `options.blueprint` — **`product.js` only**: `{ fill, lineColor }` (`fill` the page's `--bg`, `lineColor` `--category-col`) turns on the specs stage's drawing, all of it driven by `handle.setBlueprint(sweep, fit)` (0, 0 draws exactly what a viewer without it does). Each mesh's material gets a shader patch (`blueprintMaterial()`): below a cut that travels up the model with `sweep` it is the flat `fill`, with no reflection, above it metal. The real mesh's edges (`meshEdges()`, each once; one `LineSegments` per mesh sharing its position buffer) are drawn in faint black below the same cut, through a clipping plane. The model, those lines and the brackets sit in one group (`fitGroup`) scaled about the orbit target by `fit` to `fitScale × sizeFactor`. **Brackets** come from `product.geometry["min-box"]` (`data.md`): three consecutive edges of the box's outline as seen, the box scaled up a little (`BRACKET_GAP`), drawn as thin solid lines (`LineSegments2`/`LineMaterial` from three's addons, `BRACKET_LINE_DEVICE_PX` = half a device pixel wide, so thinner than a plain GL line can be; the three segments live in the geometry's own buffer, rewritten in place each frame, and `instanceCount` says how many are drawn) with HTML labels (`.emjive-3d-viewer__dim`, in cm, two places) beside them; the run is chosen lowest and rightmost and kept until another is clearly better. The box itself is drawn as a faint tinted volume (`boxMesh`, `BOX_OPACITY`, faded in with the brackets, written to no depth buffer). Handle: `setBlueprint(sweep, fit)`, `setSize(factor)` (the ring size over its base, 62: scales the model and its labels), `scanSpan()` (where the cut is on screen, for the page's inversion band), `setPaused(bool)`, `hasBrackets()`.
- `options.environment: false` / `options.nudge: false` — no environment map is loaded (a viewer that only ever draws the flat blueprint needs none; nothing uses it now) / no idle "drag me" hint.
- `options.loader` / `options.loaderBleed` — the loader (see `js/loader.js`). **The viewer no longer waits for it.** Unless `static` or `loader: false`, a loader is mounted in the viewer's own wrapper (or, if `options.loader` is a hold the caller already mounted — `js/main.js`'s cards, `js/product.js`'s carousel — that one is used), over the poster. The moment the model and environment are in, the ready block runs — `frameCamera`, first `renderer.render`, the poster hidden (instantly: its 0.3s fade becomes `transition: none` whenever a loader is involved), `onReady` — and `hold.done()` is called **without being awaited**: releasing only tells the loader nothing is loading any more, and it then finishes the crossing it is in (accelerated) inside its own safe window and goes, playing out over the live model. It is click-through and above the canvas, so a drag started under it works. (It used to hold the whole reveal back until the loader had finished its cycle and left — up to most of a 4s cycle after the model was ready.) `reportError()` and `dispose()` release it too, so a failed, disposed or evicted viewer never strands a loader. `loaderBleed: true` (`js/modify-modal.js`) lets the viewer's own loader run past its box to the carousel's edges; `js/product.js` no longer uses it (see its shared loader). The render harness (`static`) and `scene-tool.html` never load `loader.js` and are untouched.
- `options.hitCircle` — **`product.js` only**: a number, the share of the viewer's width left as a margin around the part of it that answers to a drag (`0.25`: a circle whose radius is three quarters of the viewer's own). Adds a transparent `.emjive-3d-viewer__hit` overlay clipped to that circle with CSS `clip-path` (which clips hit-testing too), puts `has-hit-circle` on the wrapper, and builds `TrackballControls` on the overlay instead of the canvas, so a press inside the circle rotates the model and one outside falls through to the carousel (`js/carousel.js` leaves only presses inside `.emjive-3d-viewer__hit` to the model). Without it the whole canvas is the model's, as everywhere else (grid cards, the Modify sheet).
- `options.freeOrbit` — `scene-tool.html`-only, wants the opposite trade-off from `static`: full interactive dragging (`static` never starts the animate loop at all, so a drag would be visually dead), but with release inertia and the idle-reset/leveling-drift/nudge behaviors above all switched off, so a dragged pose simply *stays* exactly where it's released — position **and** orientation, roll included — rather than coasting, easing back, or leveling out from under you. That's the whole point of a tool meant to let someone read a pose back as numbers: what you see is what gets saved, nothing about it drifts on its own while you're composing a shot. Three small, additive effects: sets `controls.staticMoving = true` (`TrackballControls`' own built-in "no momentum" flag, simpler than fighting the decay math that drives normal release inertia); skips arming the idle nudge (`scheduleIdleNudge()`'s guard); skips arming the "ease back to default" reset tween and the continuous up-vector leveling-drift correction (both gated individually inside the animate loop's normal-frame branch). `camera.lookAt(controls.target)` and the pole-crossing rotation itself (simply the *absence* of a polar clamp, not a separate mechanism — see below) are unaffected either way.

  Roll — the camera's orientation around its own view axis, 0 = level — is a real, savable part of `3d-viewer-camera-default` (`parseOrbitConfig()`'s `roll` field, defaulting to 0), not just an interactive-only side effect. `rotation`/`tilt`/`zoom` alone only ever encode the camera's *position* on the orbit sphere; `frameCamera()` derives `camera.up` via `restUpRaw(out, eyeDir, rollRad)` — the "level" reference (`WORLD_UP` projected perpendicular to the eye direction) rotated by `roll` around that same eye direction — so the *value* left in `camera.up`, not just the final `lookAt()`-derived orientation, genuinely encodes any authored roll. Exactly at a pole (tilt 0/180) that projection vanishes, and `frameCamera()` falls back to its limit along the orbit's own meridian, `(-cos(tilt)·sin(rotation), 0, -cos(tilt)·cos(rotation))`: at rotation 0 that's what `lookAt()`'s own parallel-up nudge used to produce, which matters because auto-render's top shots sit exactly on the pole (tilt 0) and the hero-hand overlays' rotations are tuned against that orientation — an arbitrary fallback axis was tried and turned every top shot 180°.

  The live site keeps the resting pose — roll included — as an exact fixed point of everything that moves the camera on its own. The "ease back to default" reset tween slerps `camera.up` toward `defaultCameraUp` (captured right after `frameCamera()`). The leveling drift and the idle nudge both rebuild their reference per frame from `restUpRaw()` with the product's `defaultRollRad`, for whatever eye direction they're at. For the drift, that reference is the attractor, left unnormalized (length = sin of the angle from the pole): at rest the tangent is exactly zero, so an authored roll holds instead of decaying toward level, and a roll-0 model doesn't churn `camera.up` along the view axis (invisible, but it defeated render-on-demand); away from rest, the roll-0 in-plane pull is identical to the old `WORLD_UP`-based one, sin² pole fade included. For the nudge, rebuilding up from the yawed eye is what keeps roll steady — a fixed up vector only stays roll-free under a yaw when it's literally `WORLD_UP`, and holding `defaultCameraUp` fixed wobbled roll by ~13° at a 28° tilt. Verified headlessly: at rest, eye and up hold within 1e-4 rad with zero redraws; through the full nudge, roll stays at its authored value; an injected off-rest roll drifts monotonically back to the authored value, not to 0. `TrackballControls`' own rotate step spins `.up` right along with the eye during a free-drag — exactly how `freeOrbit` composing a rolled shot by hand works — and `scene-tool.html`'s `readCurrentOrbit()` reads that roll back out via the same "level reference" projection in reverse (the signed angle, around the eye direction, from level to the camera's actual `.up`), the exact inverse of `frameCamera()`'s forward transform. For `roll: 0` (or omitted, the case for every product predating this field), the projected-vs-raw `WORLD_UP` distinction changes nothing about the final rendered orientation — `lookAt()` only ever uses the up hint's component perpendicular to the view direction, and the two differ by exactly a parallel component, whose cross product with the view direction is zero — so this is additive, not a behavior change for any existing render.

- `options.poster: false` / `options.maxPixelRatio` / `options.onReady` / `options.onError` — all four exist for `main.js`'s grid, where several viewers are alive at once. `poster: false` skips the built-in pre-load `<img>` entirely because the card already has its own image underneath doing that job; `maxPixelRatio` (1.5 on the grid, default 2 elsewhere) caps the canvas backing store, since **iOS Safari enforces a page-wide total canvas budget**, not a per-canvas one, and kills the tab once every canvas summed crosses it. `onReady`/`onError` fire once the model has loaded and painted, or once it definitively hasn't — the grid times its crossfade off the former and restores its static image on the latter. `onReady` predates both, added for `auto-render.js`'s screenshot timing.
- **The idle nudge is capped on touch devices.** It replays every `IDLE_NUDGE_DELAY` (3s) until the visitor drags, and takes ~3.6s to play, so an untouched live viewer used to redraw its whole model for more than half of its life — on the gallery, every live card at once. With `(pointer: coarse)` it now plays `NUDGE_MAX_PLAYS_TOUCH` (2) times per viewer and then rests; a mouse keeps the endless version.

### Teardown, and why it is load-bearing

`dispose()` is called constantly now — `main.js`'s grid disposes a card's viewer the moment it scrolls clear — so "was I torn down before this arrived?" is the normal case during a fast scroll, not an edge case. Four things this file gets right that are easy to regress:

1. **Both async load callbacks check `isDisposed` before touching anything**, and free what they were handed if it's set. A `.glb` arriving after teardown has its geometry disposed on the spot; a PMREM target likewise. Without that, a fast scroll leaked the full decoded geometry of everything it started but didn't finish, and — worse — the `Promise.all` ready path ran `renderer.render()` against a context `forceContextLoss()` had already killed, which is what filled the console with repeating `THREE.WebGLRenderer: Context Lost`.
2. **`dispose()` unregisters the viewer's `cancelNudge` from the module-level `allCancelNudgeFns` array, and removes its own `wrapper` pointer listeners.** Both are closures over the entire `buildThreeViewer()` invocation — renderer, scene, controls, decoded model — so either one left behind pins the whole viewer in memory no matter how diligently its GPU resources were freed. Measured on the Bones grid before this: **26 live `WebGLRenderer`s (and `Scene`s, and `TrackballControls`) retained after two scroll passes with zero viewers on screen**, growing linearly with every further pass. After: flat at whatever is actually visible. This is the kind of leak that reads as "iOS Safari reloads the page after a while" rather than as anything obviously wrong.
3. **`dispose()` is idempotent** — an early `if (isDisposed) return` — so a double dispose can't fire a second `forceContextLoss()` at a dead context.
4. **The JavaScript copy of the geometry is freed after the first frame** (`releaseGeometryArrays()`). A glTF loaded through Draco arrives as Float32 positions and normals plus 32-bit indices however small the file was on the wire — a 4MB ring decoded to ~120MB when the catalog was dense — and three.js keeps those typed arrays for the life of the geometry even though the GPU holds its own copy after the first draw. Right after the ready block's `renderer.render()` every mesh buffer's `array` is set to `null`, after the bounding box and sphere are computed (three computes them lazily from positions it would no longer have). Nothing reads them again: a metal switch only swaps materials, the camera is framed from the box, and a lost context is reported as a failure and the viewer rebuilt from the file rather than re-uploaded. **Skipped for `static` and `freeOrbit`** (the render harness and `scene-tool.html` call `frameCamera()` again for every pose). The bytes still held are tracked in `window.EmjiveMem.cpuGeometryBytes` and handed back in `dispose()`. Also on this list: **`dispose()` shrinks the canvas to 1×1**, and **`loadEnvironment` skips the PMREM build for a viewer already disposed** (`isStale`).
5. **The counters are plain numbers on `window.EmjiveMem`** (`cpuGeometryBytes`, `liveRenderers()`, `gpuObjects()`, `dracoWorkers()`) kept current whether or not anything reads them — the `?mem=1` read-out (`viewer-entry.js`) is the only reader. `liveRenderers` is pushed on construction and spliced in `dispose()`.

### Render-on-demand

**Read the repaint triggers below before touching any of this.** The animate loop ends in `drawIfChanged()`, not an unconditional `renderer.render()`. It compares the camera's current eye direction and up vector against the pose the canvas currently *shows*, and skips the draw when both are within `STILL_ANGLE_EPSILON` (1e-4 rad, ~0.006° — far below one pixel at any canvas size here). A `needsRender` flag covers the changes that aren't camera motion: a resize, and `applyMetal()`. The `rAF` loop itself keeps running (it's nearly free, and it's what notices a drag starting); only the WebGL draw is skipped. Before this, a viewer that had finished loading and was sitting perfectly still still issued a full draw 60+ times a second forever — on the homepage, for every live card at once, producing pixels identical to the ones already on screen. The epsilon is deliberately *smaller* than `SETTLE_ANGULAR_VELOCITY * dt`, so a release always registers as settled (arming the ease-back-to-default) **before** drawing stops; the other order would strand the camera wherever inertia happened to fade out.

**The catch, and the reason `requestRepaint()` exists.** Skipping redundant draws is only safe while the canvas keeps what was last drawn into it. Every viewer is created with `preserveDrawingBuffer: false` (the default; only `auto-render.js`'s harness sets it true), which explicitly licenses the browser to throw the drawing buffer away after compositing — and iOS Safari does, under memory pressure, on tab/app backgrounding, and on a bfcache restore. **No `webglcontextlost` fires for this**: the context stays alive, only the pixels are gone, so `handleContextLost`'s icon fallback never triggers either. The old unconditional per-frame render hid it completely by repainting within ~16ms; with render-on-demand, an idle viewer that has settled never draws again and the blank canvas is permanent until reload. The easiest way to hit it is the most ordinary navigation there is: tap a product, press Back, and every model on the restored homepage is gone. So `requestRepaint()` (just `needsRender = true` — not a direct draw, because `rAF` is paused when these fire) is registered via `addGlobalListener` on `document`'s `visibilitychange`, `window`'s `pageshow`, and the canvas's own `webglcontextrestored`, and torn down with the rest in `dispose()`. Verified headlessly on a settled viewer: 0 draws while idle, then exactly 1 per trigger, and 0 after `dispose()` — that last number is what proves the listeners really came off shared targets.

Separately, `handleContextLost` treats a genuine `webglcontextlost` as a viewer failure and routes it through the same idempotent `reportError()` path an initial load failure uses, so `options.onError` fires for a model that *had* already loaded and was on screen — not just for one that never made it.

Free, pole-crossing rotation (unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have) isn't a dedicated function either — it's the *absence* of any clamp on `TrackballControls`' own rotation. The extra code on top handles the *consequences* of that freedom: the up-vector leveling drift (so "up" doesn't visibly flip the instant a spin crosses a pole) and the slerp-based (not lerp+normalize) reset/nudge tweens (a naive lerp cuts a visually-wrong-speed chord for a large-angle/near-antipodal sweep, which a pole-crossing spin can easily leave the camera at).

**Exposes**: `window.EmjiveModelViewer = buildThreeViewer` — consumed by `main.js`'s grid, `product.js`'s carousel, `modify-modal.js`'s small carousel, and (with `options.freeOrbit`/`options.swatch`) `scene-tool.html`, a standalone dev tool outside the built site entirely (see `tooling.md`). Also `window.EmjiveModelViewer.METAL_PRESETS` and `window.EmjiveModelViewer.swatchOrbit` (both tool/render-only), see above.

## `js/series.js` (~520 lines) — series resolution

**`window.EmjiveMessage.show(container, text, button, role)`** (also in this file — the one script every page loads first) is how every "didn't load" / "doesn't exist" state is worded and laid out: it fills `container` with a `.page-message` (text, then an optional centred button; `button` is `{label, href}` for a link or `{label, onClick}`, defaulting to a page reload). Used by `main.js` (grid / hero slot), `product.js` and `series-page.js`. Wording: missing product → "Item not found" + "Back to gallery"; unknown series → "The requested series doesn't exist" + "Back to gallery"; any failed load → the explanation + "Reload". On the homepage a failed `series.json` puts the message in the empty hero slot (the first screen), not the grid below it.

Loaded blocking in `<head>` on every page (see above). Fetches `data/series.json` once and exposes `window.EmjiveSeries`:

- `ready` — a promise resolving to `{ index, slug, series }`. **Everything else on the site hangs off this**; `main.js`, `product.js` and `series-page.js` all start from it rather than fetching any JSON path themselves.
- `slug`/`series` — the ACTIVE series: `?series=` if it names a real one, else `index.featured`.
- `metals` — the global metal list. `categories()` — the active series' own category subset. `categoryInfo(id)` — that category's `{ sizes, unit }` from the global vocabulary (only `unit` is read now — see `data.md`).
- `loadProducts(slug)` / `loadManifest(slug)` — **memoized per slug**, so the grid and the hero handoff share one request. With `<html data-products="eager">` (`index.html`, `product.html`) `loadProducts(activeSlug)` is called the moment the index resolves, instead of when the page's own deferred script gets round to asking — the same request, a whole script-download chain earlier (the build adds a matching `<link rel="preload">`, see `tooling.md`).
- `mainHref` / `manifestHref` / `productHref` / `productSlug` — URL builders, all **root-absolute** (`/gallery`, `/series?series=<slug>`, `/<slug>`; see `pages.md`'s "Addresses"). `mainHref` and `manifestHref` deliberately **omit `?series=` for the featured series** (`mainHref` appends it for any other), so everyday URLs stay clean. `productHref(product)` is just `"/" + productSlug(product)` — no series, no id: an item's slug (its name, URL-safe) is unique across all series, so the address alone finds it. `productSlug()` is the browser copy of `slugify()` in `scripts/slugs.js`; `validate-data.js` reads its source out of this file and fails if the two disagree on any product name, so it has to stay a single self-contained function declaration.
- `requestedSlug()` — the raw `?series=` with no fallback applied. Only `series.html` uses it, so it can show a not-found state instead of silently rendering the featured series' manifest.

It also owns **hero bundle loading** on `index.html` (guarded on `#seriesHero` existing): inject the preload hints (the first `hero.preload` entry — the picture the first paint is made of — at `fetchpriority="high"` and as its low-res version for this viewport; the rest, layers that start clipped away, at `low` and as the right high-res version), inject the hero stylesheet, fetch the fragment and inject the hero script — all in flight at once — then clone each `<template data-series-slot>`, **choose the version of each `<img data-full>` for the viewport while the clone is still inert** (`chooseHeroImages()`: the fragment's pictures carry no `src`, only `data-full` — the original, the desktop high-res file — and `data-lo` when they have the low-res pair; `EmjiveLoader.versions()` picks, and an `<img>` in a template's content doesn't load until it is attached), attach it into its slot, call `EmjiveSeriesHero.init()`, and hand the series' products to `onProducts()`. Once the hero's first image is decoded the page's loader is released and `upgradeHeroImages()` swaps each `[data-full][data-lo]` picture for its high-res version when the browser is idle; `watchHeroForPhoneChange()` re-points every hero picture at the other set if the viewport crosses the phone line (the hero's layout changes shape with it, see `styling.md`). On failure it strips `body.has-series-hero` so the selection bar isn't stranded off-screen. See `pages.md` for the full contract and the anti-flash reasoning.

`window.EmjiveHero` lives here too — a plain function registry (`onScroll`/`publishScroll`), not a `CustomEvent`, because it fires once per animation frame during scroll and a registry costs no allocation per publish.

`window.EmjiveMenus` also lives here — click-away coordination for the header menu (`main.js`) and the selection-bar drawer (`selection-bar.js`), two panels that don't know about each other and can be open at once. Each registers `{ root, close() }` via `opened(panel)`/`closed(panel)` when its own open state changes; `root` spans both the panel's trigger and its content, so clicking the trigger itself is never mistaken for "away". `root` only needs a `contains(node)` method — the drawer passes an object whose `contains` also accepts anything inside `#modifyModal`, so a tap on the Modify sheet's backdrop closes the sheet but not the drawer it was opened from. A single `document` click listener here closes only the most-recently-opened panel when a click lands outside every currently-open one's `root` — a second outside click is needed to close the other if both happened to be open together.

## `series/<slug>/hero.js` — one per series

The hero's behavior, loaded at runtime. Assigns `window.EmjiveSeriesHero = { init(root, ctx), onProducts(products) }` and does nothing else at execution time. For Bones that means the frontier-band lift, the scroll-driven x-ray wipe, and `updateHeroRings()` — one `.reveal__ring` `<img>` per product with `hero-hand-visibility.visible: true` (see `data.md`), each positioned/sized/rotated via inline custom properties set from that product's own `hero-hand-visibility` object, so multiple rings on screen don't fight over one shared set. It gets the **full, unfiltered** product list: the rings are hero art, not a listing.

Two rules any hero bundle has to keep: no side effects at execution time (the loader parallelizes on that assumption), and no bare specifiers (Vite never sees this file, so `import "three"` would ship unresolved — call `window.EmjiveModelViewer` instead).

## `js/main.js` (~910 lines)

Loads on **every** page. Owns:

- The header hamburger menu toggle. A delegated click handler on `.site-header__row` also toggles it from anywhere in the row's empty space — same as the `+`/`-` icon — while ignoring clicks on the brand logo (which navigates home instead) or on `.menu-toggle` itself (which already has its own listener, and would double-toggle otherwise). Registers a panel with `window.EmjiveMenus` (`js/series.js`) so a click away from the whole header closes it too — see that file's doc above.
- The **category filter row** (`renderHeaderFilter()`), rendered from `EmjiveSeries.categories()` — the active series' own subset — so it renders identically on pages that load no product data at all. Dual-purpose, branching on `filtersAreInPlace` (`!!document.getElementById("productGrid")`, true only on `index.html`): on the grid page it's the real filter (label + one `.is-cat` tag per category when there's more than one, a single inert `.is-active` tag with no `href` when there's exactly one, hidden outright at zero); everywhere else it's unconditionally a plain `.is-info` "Gallery" link back to `index.html#products` via `EmjiveSeries.mainHref()`. `syncFilterButtons()` toggles `.is-active`/`aria-current` on whichever tags are in `activeCats` — `css/style.css` turns that into a dot, not a color change, the same recipe size/metal selection uses elsewhere. The menu-close handler is **delegated** to the menu container, because those buttons are created after the script runs; a per-link listener would never reach them.
- **Filtering** (`applyFilter`/`toggleCategory`/`setCategories`), on the grid page only. Multi-select toggles that hide already-built cards, sync `?cat=` via `history.replaceState`, and leave the menu open so successive toggles are usable. Elsewhere the same buttons are ordinary links that navigate to the grid with one category applied. Unknown `?cat=` values are dropped against the active series' categories, so a typo shows everything rather than nothing.
- `wireModelClickNavigation(el, href)` — the 6px drag-distance-threshold click-vs-drag disambiguation, attached to a viewer's wrapper so rotating a model doesn't accidentally navigate. Wired inside `startViewerLoad` now (see below), at the point a card's viewer actually gets built, rather than unconditionally in `buildCard`. Tracks `activePointerId` so a `pointerup` that never had a matching `pointerdown` on this element — a drag begun on the page background and released over a card, or a second finger lifting during a two-finger scroll — is ignored rather than measured against stale (initially `0,0`) coordinates, which read as a zero-distance "click" and navigated to a product nobody tapped.
- The grid rendering (`buildCard`/`renderProducts`) — one card per product from `EmjiveSeries.loadProducts()`. Cards are built **once** and kept in a module-scope array; see the WebGL note in `pages.md` for why filtering must never rebuild them.
- **Lazy viewer build/dispose** (two `IntersectionObserver`s feeding one `reconcileViewers()`) — `buildCard` no longer calls `window.EmjiveModelViewer` itself; it always builds the card's placeholder `<img>` first and returns `{ el, figure, iconEl, href }`, which `renderProducts` wraps into a `{ product, el, figure, iconEl, href, modelHandle, wantsViewer, queued, loadHold, releaseSlot }` entry and hands to both observers (`figure.cardEntry = entry` is how each observer's callback finds its way back to that state). `buildObserver` (`rootMargin: "150px 0px 150px 0px"`) marks a card `wantsViewer` once its figure nears the viewport; `disposeObserver` (`"300px 0px 300px 0px"` — deliberately larger, for hysteresis, so a card doesn't thrash build/dispose right at one boundary) calls `disposeViewerFor` once it's scrolled well clear. Falls back to eagerly building every viewer up front (the old behavior) if `IntersectionObserver` doesn't exist at all.
  **The observers only decide which cards are in *range*; `reconcileViewers()` decides which of those are worth the memory.** It sorts every `wantsViewer` card by distance from the viewport centre, builds the nearest `MAX_LIVE_VIEWERS` (**3**) and evicts the rest. `evictViewer` drops the viewer and its queue place but leaves `wantsViewer` set, so a card demoted by the ceiling comes straight back when a slot frees — that's the whole difference from `disposeViewerFor`, which means "out of range entirely". A ceiling is needed *on top of* the margins because the margins bound a **distance**, not a count: how many cards fall inside one is a function of viewport height and card pitch, and on a phone (measured back when the figure had a 210px floor: + the 8rem mobile row gap = a 338px pitch, inside an 860px viewport plus 300px of dispose margin each side) that came to **five at once** — the phone figure has since shrunk to exactly half the row (`calc(50vw - var(--edge-px))`, ~177px on a 393px-wide phone, see `styling.md`), which only packs more cards into the same range, each with its own WebGL context, decoded model and — the expensive part — its own PMREM environment target, which cannot be shared across renderers (see `loadEnvironment` above). Three covers everything genuinely on screen at any realistic viewport plus one for the direction of travel; the trade is a very tall narrow window, where a fourth on-screen card sits on its icon.
  **Scheduling** (`scheduleReconcile`, `RECONCILE_INTERVAL_MS = 250`) — both observers, the `scroll`/`resize` listeners, `applyFilter` and `pumpLoadQueue` all funnel through it. The scroll listener is not optional: neither observer fires while a card merely moves *within* its margins, so without it a card held back by the ceiling on the way in would stay on its icon all the way past the middle of the screen. It's a **timer, deliberately not `requestAnimationFrame`**, with the pending timer's own handle as the "already scheduled" flag (cleared as the callback's first statement, so no separate boolean can be stranded by a reconcile that threw). rAF looks like the obvious fit for something driven by scrolling and is the wrong choice: it only fires while the page is producing frames, so a reconcile armed just as the compositor goes idle sits unfired and every later scroll returns early against it — measured at **0–3 rAF callbacks across a six-second idle window where `setTimeout` ticked ~350 times**, with the visible symptom being cards stopping mid-screen on their icons, wanting a viewer, nothing in flight and nothing queued.
  **Freezing** (`releaseAllViewers` on `pagehide`, `rebuildViewersInRange` on `pageshow` with `event.persisted`) — navigating to a product doesn't end this page; both browsers this site cares about put it in the back/forward cache, and a bfcached document is a **live** document, holding every renderer, model and PMREM target while `product.html` builds its own on top. Even under the ceiling that's four at once across the two pages, against an iOS Safari budget that is a page-wide total. The rebuild **re-observes** every figure rather than calling `buildViewerFor` directly: both observers only fire on a threshold crossing and no crossing happens while the page is frozen, so without it every card would sit on its icon until the visitor scrolled far enough to cross a margin. `product.js` does the same from the other end of that navigation — see its section below.
  **Which placeholder image, and why it isn't the icon.** The card shows `assets["fallback-img"][defaultMetal]` when the product has a model, falling back to `assets.icons[...]` only when it doesn't. These are **not** interchangeable: `auto-render.js` trims `icons` to their own alpha bounding box and rescales that to a fixed 80% of the frame (`ICON_CONTENT_FRACTION`) so thumbnails read consistently next to each other — deliberate, and exactly wrong here, because a thin ring's silhouette is far smaller than the bounding *sphere* `frameCamera()` fits to the viewport. Measured on Furcula: the icon drew the ring **1.232× larger** than the live model in both axes and re-centred it ~6% horizontally, so the handover read as the model snapping smaller and sideways the instant it appeared. `fallback-img` is the same capture saved *without* that treatment and matches the live canvas to **0.999× wide / 0.997× tall, centre within 0.1%** — i.e. invisibly. This is the whole reason `fallback-img` exists as a separate asset (see `assets.md`).
  **Load concurrency** (`MAX_CONCURRENT_MODEL_LOADS = 2`, `loadQueue`, `pumpLoadQueue`) — lazy building bounds how many viewers *exist*, not how many start loading at once, and a brisk scroll crosses every card's build margin within a second or two. Capping it means cards resolve one after another in the order they were scrolled past, rather than every model finishing late together with bandwidth split N ways. `entry.wantsViewer` (set by `buildObserver`, cleared by `disposeObserver`) lets `pumpLoadQueue` **drop** queued cards that scrolled back out before their turn came, instead of fetching a model nobody is looking at any more; it also schedules a reconcile afterwards, since the queue is FIFO and knows nothing about where the viewport is now — an entry queued three screens ago can otherwise reach the front long after a nearer card started wanting one.
  **`entry.releaseSlot`, and the bug it closes.** A slot is claimed in `startViewerLoad` and returned by `releaseSlot`, which only ever ran from `onReady`, `onError`, or a refused WebGL context. A dispose landing **mid-load** is the one way a viewer settles without either callback firing — `three-viewer.js` guards its whole ready path on `isDisposed`, and `reportError()` on `isDisposed` too — so a card scrolled past while its model was still downloading silently kept the slot it had taken. Two of those (it's a two-slot pipeline) and the grid **stopped loading models for the rest of the page's life**: every later card queued behind a counter that could never come back down, showing its icon forever with nothing in the console to say why. `startViewerLoad` now hands its `releaseSlot` to the entry and `teardownViewer` calls it — last, since `pumpLoadQueue` inside it can start the next viewer synchronously, and a no-op on the `onError` path where it already ran. **One refinement for a viewer evicted mid-load:** the slot is not handed back at once. Disposing frees the viewer, but the model's download and decode cannot be cancelled and are still running — the very thing the two-slot limit exists to ration — so `teardownViewer` holds the slot until the handle's `whenSettled` resolves (6s cap, `SLOT_HOLD_AFTER_EVICT_MS`). Without that, a fast scroll started a new load for every card it passed beside the decodes the evicted ones were still finishing: tens of megabytes of geometry in flight at once on a phone. `releaseSlot` only clears `entry.releaseSlot` if it is still its own hook, since the card may already have started a newer load.
  **The handover is instant, not a crossfade** — the viewer is mounted at `opacity: 0` over the placeholder, which stays visible for the whole load with the logo loader (`entry.loadHold`, `js/loader.js`) over both — the viewer reveals the moment its model is ready rather than waiting for the loader, which is released then and plays out its crossing over the live model (click-through, `z-index: 2` above the viewer's `z-index: 1`); from `onReady`, `revealViewer()` swaps them in the **same frame** (viewer `opacity: 1`, icon `hidden`). A fade window was tried and removed: drags during the load are buffered on purpose (the transparent canvas sits above the icon and takes them), and a fade would show that already-applied rotation, plus any release inertia still decaying, visibly mid-motion under the fading icon — it read as the model twitching rather than appearing. `teardownViewer` (used by `disposeViewerFor`/`evictViewer`) releases an unfinished `loadHold` and puts the icon back, so a card disposed mid-load recovers correctly. Combined with `poster: false`, the card never shows the model's own poster.
  Exists because building every product's viewer — a `WebGLRenderer`, a full glTF fetch/decode, a from-scratch HDRI PMREM build, each — unconditionally and instantly the moment the grid rendered stopped being safe once the catalog grew past a handful of products: eight bones products at up to several tens of MB each meant eight simultaneous WebGL contexts, eight HDRI builds, and over 100MB of glTF data all at once on page load, reported as the page reloading erratically on scroll and crashing outright (Chrome's repeated-crash page) on real devices. Verified headlessly (a scripted scroll through the real page, not visual inspection): peak simultaneous viewers capped around 5 of 8 (was: all 8 instantly), zero models fetched before scrolling anywhere near the grid (was: ~100MB at page load), and a disposed card's viewer correctly rebuilds if scrolled back to.
  **`css/style.css`'s `.product-card__figure > img[hidden]` rule is load-bearing for this** — see `styling.md`. Toggling `.hidden` on the icon is a new use of that attribute here; without the matching CSS override, the base `img { display: block; }` rule (author-origin, beats the UA `[hidden]` regardless of specificity) left the "hidden" icon still laid out and pointer-interactive on top of the canvas, silently swallowing every drag meant for the model — confirmed via `elementsFromPoint` and `TrackballControls`' `_pointers` count staying 0 after a simulated `pointerdown`.
- **Lending a WebGL slot to the Modify sheet** — the sheet (`modify-modal.js`) can open over the homepage grid from the floating bar's drawer and builds a viewer of its own. On `emjive:modify-open` the grid's ceiling (`liveViewerCeiling`, normally `MAX_LIVE_VIEWERS`) drops by one and `reconcileViewers()` runs **immediately**, not scheduled, so a grid viewer is gone before the sheet's arrives and the page never holds four contexts at once (the iOS budget is page-wide). `emjive:modify-close` — dispatched only once the sheet's viewer has actually been disposed, after its slide-out — restores the ceiling and schedules a reconcile. Both listeners only exist on the grid page, and only when lazy viewers are supported.
- A guarded contact-form stub (`getElementById("contactForm")`) — a no-op, since no page has that element. Kept for whenever a contact form gets built (see `procedures.md`).

Owns **no hero logic at all** any more, and no `METAL_PRESETS` or viewer-construction logic — those live in the active series' hero bundle and `js/three-viewer.js` respectively. `main.js` is purely a consumer of both.

## `js/scroll-memory.js` (~375 lines) — back-navigation scroll memory

`index.html` **only**, blocking in `<head>`, first script on the page. Makes Back return to the gallery exactly where the visitor left it: right offset on the first painted frame, no jump, no smooth-scroll travel, no blank hold.

**Why the browser can't do this itself.** At first paint `index.html` is almost empty — `#seriesHero` is an empty div held at `min-height: 100svh` and `#productGrid` is empty (the arrival loader covers the wait, see `js/loader.js`). The real height only arrives after three async hops: `data/series.json`, the hero bundle (whose `hero.css` sets `.reveal { height: 200vh }`), then that series' `products.json` rendered by `main.js`. Native scroll restoration runs long before any of that, against a document a fraction of its final height, so the offset clamps to near zero and the visitor lands at the top. Every other page builds its height synchronously from markup, which is why this is scoped to one page — elsewhere it would be a second opinion fighting a working one.

- **Per-history-entry key.** A token minted into `history.state` as `emjiveScrollKey`; the position itself lives in `sessionStorage` under `"emjive:scroll:" + key` as `{ y, h }`. Keyed off the *entry*, not the URL, because one session can hold two `index.html` entries at different offsets and a URL key would let the second overwrite the first. The value is in `sessionStorage` rather than `history.state` because saving means writing on every scroll and Safari rate-limits `replaceState` hard enough to throw. **`main.js`'s `syncFilterUrl()` must keep passing `history.state` back through its `replaceState`** — it used to pass `null`, which discarded the token on every category toggle.
- **Saving** — `window.scrollY` plus `documentElement.scrollHeight` on `pagehide`, on `visibilitychange → hidden`, and on a ~300ms-throttled `scroll` listener as the crash/OOM net. Suppressed while a restore is in flight, so a mid-restore `scrollY` of 0 can't overwrite a good value.
- **Restoring (fresh load)** — `history.scrollRestoration = "manual"` (per-entry, so it doesn't leak to other pages), then the saved height is set as `--emjive-restore-height` inline on `<html>` and `emjive-restoring-scroll` added, all from the head script *before `<body>` is parsed*. `css/style.css` turns that into a `min-height` on `body`, so the offset is reachable immediately; `applyScroll()` then runs in the first `requestAnimationFrame` that has a `document.body`, and rAF callbacks run **before** the frame they belong to is painted, so no wrong-offset frame is ever presented. The loop keeps re-asserting while the hero and grid land.
- **Restoring (bfcache)** — `pageshow` with `event.persisted`: the DOM and height come back intact, so it just calls `applyScroll()` synchronously. Needed because `"manual"` opts out of the UA's traversal restore too.
- **`contentReady()`** — called by `main.js` once the grid is rendered *and* filtered (the last thing that changes this page's height), and also from its `.catch`, so a failed products fetch releases the restore immediately instead of waiting out the deadline. It waits for `scrollHeight` to reach the reservation, then races the on-screen cards' placeholder decodes plus `document.fonts.ready` against a ~250ms grace, then reveals. Two frames, not one, before revealing — the first lets the hero's own scroll handler and `selection-bar.js` react to the restored offset, so the x-ray wipe and the floating bar are already in step on the frame the grid appears.

**Three things that had to be defused, all of which will re-break this if changed:**

1. `html { scroll-behavior: smooth }` (`css/style.css`) would make `scrollTo` **animate** — i.e. exactly the visible "scrolling back to where you were" this file exists to avoid. `applyScroll()` overrides it inline around the call; `behavior: "instant"` is belt-and-braces, wrapped because a browser predating that enum value throws on it.
2. **Scroll anchoring** would shift the offset as the hero grows `100svh → 200vh` *above* the restored position — correct in general, wrong here, where an absolute offset is the thing being preserved. Hence `overflow-anchor: none` in the restore CSS.
3. The first `wheel`/`touchstart`/`pointerdown`/`keydown` (capture phase, so a canvas handler that stops propagation can't hide it) sets `userTookOver`, which stops the re-assert loop but deliberately **does not** end the restore window — dropping the height reservation early would collapse the document under the visitor and yank the scroll, the same jerk this prevents, just triggered by their own input.

**Failsafes**, none of which may ever leave the page stuck: a `setTimeout(endRestore, ~1200)` armed at script execution, so a JS error anywhere else still releases the reservation; an idempotent `endRestore()`; and guards on `"scrollRestoration" in history`, on `replaceState`, and on `sessionStorage` access (which throws outright in Safari private mode) — any failure degrades to the browser's own behaviour.

**Exposes**: `window.EmjiveScrollMemory = { isRestoring(), contentReady() }`, consumed only by `main.js`.

## `js/selection.js` (~360 lines)

The cart/selection data layer — a thin `localStorage` wrapper. `STORAGE_KEY = "emjive_selection"`. Storage is `{ v: 1, items: [...] }` (a bare array — every earlier release's format — is still read and rewritten in the new shape on the next write). `readAll()` falls back to `[]` on any read error (e.g. corrupted JSON) and **sanitises what it finds**: entries that aren't objects or have no `productId` are dropped, and `productId`/`name`/`category`/`metal`/`size` are coerced to strings, `price` to a non-negative number (else 0), `image` to `""` unless it is a same-origin relative path (no scheme, not `//host`) — since it ends up in an `<img src>`. One bad entry used to throw inside `itemKey()` and take the bar and the order page down. A `storage` listener re-announces (`action: "sync"`) when another tab changes the cart. `writeAll()` never throws: if `setItem` fails (storage blocked outright, as Safari does with all site data blocked, or over quota), the list moves into an in-memory copy (`memoryItems`) that `readAll()` serves instead, so the bar and order page still show the change and the index-based mutators below keep acting on the list that's on screen. The next successful write clears it and hands the selection back to `localStorage`. That copy lasts only as long as the page does — it can't follow the visitor to the next one. Every mutating call dispatches `new CustomEvent("emjive:selection-changed", { detail: { action, index } })` on `window`, **synchronously**, from inside the call — the sole mechanism other scripts use to react live to a change without a page reload. `action` is `"add"`/`"remove"`/`"insert"`/`"update"`/`"clear"`; it's how `selection-bar.js` tells an Undo's insert (its icon plays the collapse in reverse) from an Add's (its icon slides in from the edge), and how `selection-page.js` knows a Save happened.

Four mutators, all index-based (an item's position in the stored array, not an id): `addItem(item)` (pushes to the end — `product.js`'s Add), `removeItem(index)` (splices it out — the Modify sheet's Unselect), `insertItem(index, item)` (splices it back in at a specific position — the Modify sheet's Undo, so a restored item lands back where it was rather than at the end the way `addItem` would), and `updateItem(index, patch)` (`Object.assign`s `patch` onto the existing item in place — the Modify sheet's Save, changing metal/size and the price and icon that come with them without moving the item).

**Sizes** — the rules both size fields (`product.js`'s sheet and the Modify sheet) share, so the two can't drift apart: `sanitizeSizeInput(raw)` is the keystroke filter (comma → dot for comma-decimal keypads, digits and one dot, at most two decimals); `normalizeSize(raw)` is the one form a size is stored in (`"62."` → `"62"`, `"62.5"` → `"62.50"`, `".5"` → `"0.50"`, leading zeros dropped, `""` for no digits); `isValidSize(raw)` — non-empty and above zero — is what gates Add and Save. `appendSize(parent, size)` appends a size value to `parent` as plain text, except a decimal size's fractional part — that renders in a `.size-fraction` span (`css/style.css`, `font-size: 0.75em`), always two digits (padded for carts saved before `normalizeSize` existed), instead of as a literal `.`, since every row that shows a size joins `.category.metal.size` with literal dots, and a decimal point in the size itself would read as a fourth trait segment.

**Size guide** — `fillSizeGuide(container, guide)` builds a category's `size-guide` (`data.md`) into `container` and returns whether there was one: the "how to measure" sentence, then a table *turned* from the data — a row per fact (`Size`, `Diameter (mm)`, `US`; its label a `th scope="row"`), a column per size — inside `.size-guide__scroll` (`overflow-x: auto`, a focusable region: on a phone the table runs out to the right and scrolls there). `wireSizeGuide({ toggle, panel, onToggle })` wires its button: it toggles `.is-open` on the panel and `aria-expanded` on the button, a click anywhere else closes it, `onToggle(open)` lets the caller do its own part; returns `{ close(), isOpen() }`. Used by the specs stage, `#sizeModal` and the Modify sheet.

**Diffing** — `itemKey(item)` (`series|productId|metal|size`, tolerating a missing `series`) and `singleChange(oldKeys, keys)`, which says whether a change from one list of keys to the next was a single insert, remove or in-place update (and at which index), or `null` for anything else. Shared by `selection-bar.js`'s icon strip and `order-rows.js`, so both animate exactly the one thing that changed.

**Exposes**: `window.EmjiveSelection = { getSelection, addItem, removeItem, insertItem, updateItem, clear, formatPrice, sanitizeSizeInput, normalizeSize, isValidSize, appendSize, fillSizeGuide, wireSizeGuide, itemKey, singleChange }`.

**Item shape** (enforced by `sanitizeItem()` on every read): `{ series, productId, name, category, metal, size, price, image }` — a deliberately self-contained snapshot, so `launch-order.html` never has to re-fetch or join against any products file to render itself. `series` is what makes `productId` meaningful, since ids are only unique within one series. Selections saved before that field existed simply lack it; `itemKey()` tolerates it being absent so an existing cart doesn't read as all-new.

## `js/focus-trap.js` (~290 lines) — the two sheets' keyboard containment, and the page lock

Loaded on **all seven pages**, since every page can open the Modify sheet. Not folded into `js/series.js` despite that file already hosting two non-series globals: `series.js` is blocking in `<head>`, and nothing here needs to be.

**Exposes**: `window.EmjiveFocusTrap = { activate(root, options), release(focusTarget), focus(target) }`. `options` is `{ include, returnFocus, fallbackFocus, initialFocus, onEscape }`, all optional. `release(focusTarget)` sends focus somewhere other than `returnFocus` (the Modify sheet sends it to the Undo on the unselected row's line after an Unselect); `focus(target)` moves focus the same way `release()` hands it back, for moves that aren't a release (an Undo resolving).

Load-bearing rather than incidental:

- **The trap root is `.size-modal`, never `.size-modal__panel`.** On `#modifyModal` the small carousel is a *sibling* of the panel, not a child — a panel-scoped trap would leave part of the dialog outside itself. Both sheets carry `role="dialog"`/`aria-modal`/`aria-label`/`tabindex="-1"` on `.size-modal`: a screen reader honouring `aria-modal` hides everything outside the declared dialog.
- **`include`** — elements outside the root whose controls count as inside the trap: the Modify sheet's buttons live in the page's bar (its strip), so the sheet passes that. Every Tab is moved by hand, wrapping at both ends, across root then include, since the browser's own Tab order would never step between two separate parts of the document. Focus landing on an included element isn't pulled back. `focusable()` skips anything inside `[inert]`.
- **`returnFocus` may be a function**, resolved at `release()` time rather than at `activate()` — the thing that opened a sheet can be gone by the time it closes (a row whose item was just unselected, a list that emptied). Both list pages pass a lookup by index plus a `fallbackFocus`.
- **Candidates are re-queried on every Tab**, never cached: the Modify sheet rebuilds its metal buttons and carousel slides per open, and Save toggles `disabled` live.
- **Escape lives here**, registered on `activate` and removed on `release`. One listener means Tab and Escape can't disagree about whether a sheet is open.
- **Focus handed back after a tap draws no ring.** Programmatic focus inherits `:focus-visible` from the element focus came from, and the size field (a text input) always matches it — so a row refocused after typing in the field and tapping Save would get a ring around it. A capture-phase `pointerdown`/`keydown` tracker records the last input; focus handed back right after a pointer input gets `.is-focus-quiet` (`css/style.css` drops the ring for it) until that element blurs or a key is pressed.
- **The root it focuses on open must never be given a position by a focus style.** It's focused so the dialog's label is announced, and iOS Safari counts the first scripted focus after a page load as `:focus-visible`; the site-wide ring rule used to set `position: relative` on anything with a `tabindex`, which turned the fixed sheet relative and dropped it to the end of the page, out of sight and untouchable. See `styling.md`'s focus section.

**The page lock** is here too: `activate()` locks and `release()` unlocks, since every modal on the site freezes the page behind it. `html.is-modal-open` (`css/style.css`) sets `overflow: hidden` on `<html>`, not `<body>` — `html` carries `overflow-x: hidden`, and once `html`'s overflow isn't `visible`, `body`'s own overflow no longer reaches the viewport (the `body`-level lock this replaced never worked). The scroll position doesn't move, so nothing driven by it (the homepage bar's scroll-linked reveal) does either. Where scrollbars take up room (Windows), hiding the page's would widen everything behind the backdrop by its width, so its width is published as `--page-scrollbar` and given back as padding on `<html>` and on the fixed bars and header. (`scrollbar-gutter: stable` would be tidier, but Chrome doesn't keep the root's gutter once its overflow is hidden.)

A closed modal needs no handling: `.size-modal` is `visibility: hidden`, `visibility` inherits, nothing inside redeclares it, and an element whose computed `visibility` isn't `visible` is excluded from sequential focus navigation.

## `js/product.js` (~1520 lines)

Owns `product.html` (and every item's built copy of it, `dist/<slug>.html`) end to end. `getRequest()` reads the item from `location.pathname` — the last segment, lower-cased; `product.html`/`product` mean "none" — falling back to the old `?id=` (+ `?series=`, which `series.js` already uses to pick the active series). `findProduct(slug, request)` matches by slug (or by id for the old form) in the active series first, then scans the remaining series in index order (each memoized) — the scan is what keeps bare `?id=` bookmarks working now that ids are only unique per series, and what lets an item of a non-featured series live at a plain `/<slug>`. `canonicalizeUrl()` then rewrites the shared template's `/product.html?id=…` address to `/<slug>` with `history.replaceState` (hash kept); a path the server really has is left as typed. Then renders (by the file's own numbered section comments):

1. **Label** — name, `.category.metal` (like the rows' label in the selection lists, rebuilt by `labelTypeText()` on every pick), per-metal thumbnail, price. The *other* metals' icons are `EmjiveOrderRows.preload()`ed once the first paint is in (the selected one's is the thumbnail itself) so a pick swaps the thumbnail at once, and the picture and text under the label bar's invert band call `EmjiveOrderRows.resampleBand()` so Safari's backdrop-filter re-samples immediately (see `order-rows.js` below).
2. **Carousel** — builds the slides into `#productCarousel` (if `product.assets.model` is set, the model's **poster** — `showPoster()`, a `.size-modal__model-poster` box sized exactly like the viewer that replaces it, holding the viewer's own `fallback-img` poster image (the metal's icon if there isn't one) — which `attachViewer()` later swaps for the real viewer; else a fallback icon image; then any `product.assets.photos`, built with `imageSlide(..., { deferred: true, loaderHost })` so they don't start downloading with the first paint) and calls `carousel.sync(true)` right after `#productDetailContent` is unhidden, since `[hidden]` elements measure zero. The dragging, paging and tap-to-center behaviour is `js/carousel.js`'s (see below) — the Modify sheet's small carousel runs the same code. Each photo slide (`buildPhotoSlide()`, built on `EmjiveCarousel.imageSlide()`) also renders a `.product-carousel__caption` naming which finish/context that shot depicts — `"On display: " + (photo.description || "—")`. The caption is a real sibling of the `<img>`, not an overlay on top of it: it's absolutely positioned to the slide's own bottom-right corner, in extra height `css/style.css`'s `.product-carousel--has-photos` reserves below `--tile` on the viewport (toggled by `renderCarousel()` whenever `product.assets.photos` is non-empty) — done this way, rather than shrinking the photo's own box to fit a caption inside it, so every photo still fills `--tile` edge-to-edge and stays flush against its neighbors in the filmstrip.
   **The page renders without waiting for the 3D chunk, and what it waits for instead is ordered by what the first paint is made of.** `init()` calls `render()` as soon as the product data is in. `render()` starts the x-ray backdrop first (`startXray()`: the low-res version for this viewport, `fetchpriority="high"` in the markup — see "Responsive images" under `loader.js`), then builds everything else. `firstPaintReady` is the x-ray plus the poster (6s cap) and does two things: lifts the arrival loader (`pageReady()` — it used to lift on a blank page that filled in underneath), and — once `afterFirstPaint()` says the carousel's first picture has actually been *painted* (a `largest-contentful-paint` observer on `#productCarouselFrame`, 2s cap, two animation frames where the API is missing) — runs `loadRemainingAssets()`: the other metals' icons, the photo slides (`slide.loadImage()`), and `mountViewer()`, which adds `<link rel="preload" as="fetch" crossorigin>` for the HDRI and the `.glb` (the viewer asks for them only after the chunk has arrived and run; this puts all three downloads in flight at once, and the viewer's own requests reuse them), asks `EmjiveLoadViewer()` for the chunk, and `attachViewer()`s when the browser is idle (creating a WebGL context and compiling shaders is a long task). The sharp x-ray replaces the low-res one only after `viewerSettled` (the model drawn, or never coming — `onReady` / `replaceModelSlideWithIcon` / no model; 20s cap), so its 320KB doesn't share the link with the viewer. Why this order: everything started before the first paint — the chunk, the 0.9MB HDRI, the model, three icons, two photos — shared a throttled link with the x-ray, which is the LCP element; and a hint for any of them in the `<head>` measurably pushed the LCP image later, which is why the build adds none for them (`tooling.md`).
3. **Metal picker** — mounts `js/metal-picker.js` into `#productMetals` (see its section below; the squares, the dot and the name are all there) and reacts to a pick: re-tints the live 3D model in place via `state.modelHandle.applyMetal(metal)` (no reload, no camera reset), and separately updates the label thumbnail/fallback icon/specs/price, since only the 3D model re-tints itself automatically. The re-tint runs through `tintAfterPaint()` (a rAF plus a 0ms timeout), *after* the label text has painted — re-tinting is a fresh material per mesh and a re-render, heavy enough on an iPhone to hold the next frame and the label with it; picks made meanwhile retint to whichever metal is current.
4. **The two stages** (`js/product-stages.js` publishes the scroll; `wireStages()` mounts it and `onStageChange()` reacts) — `refreshStage()` works the rest out from `state.toSpecs` and where the model is on screen, on every change and resize: the phases' timing (`--t0`, `--t1`: the first fade ends as the inversion band reaches the model's foot, the second begins as it leaves its head — so they hold on any screen), the band's place, the sweep (`state.sweep`) and fit (`state.fit`), the model's lift (`--lift`, below), and the toggle of `.is-specs-layout` on the stage in the middle of the blank (the picker lies down, and its label comes). The fades' timing (`--t0`, `--t1`) is worked out from where the model stands **as the transition starts** — the first stage's browsing has taken the show up by `--room-0` (`barsPx()` reads it off a probe), so the model's rest place (`modelSpan()` plus the lift and `browsePx()`, the show's transform) less that: it doesn't move while the show does. **The model's path** (`modelRise()`) is one curve from the first pixel of scrolling, in `state.along`: it goes up with the show while the first stretch browses (`--room-0` by its end), carries on up at the same speed and slows to a stop `SPECS_GAP_REM` (8rem) above its place in specs, then comes down into it, eased at both ends (`LAND_AT`) — so it lands from above, and the show coming back down as specs arrives never takes it along. Its place is its middle on a quarter of the screen's height, or under the title bar if it is tall, **plus that 8rem gap** before it. `--lift` is that path less what the show does by itself (the first stretch's browsing, less the part given back as `--s-in` rises), so the carousel, the picker, the edge bands and the column under the model follow the model, not the show. The band is a monotone curve (`bandAt()`) through four places — under the screen, the model's foot at `--t0`, its head at `--t1` (where they stand by then, the model having risen), over the screen — and the sweep is its passage across the model as it stands now. `applyStageToViewer()` hands `setBlueprint(sweep, fit)` and `setSize(factor)` to the viewer. A viewer built later (first mount, after the Modify sheet, after Back) starts where the page is. The carousel's strip is taken home (`carousel.goHome()`) and locked (`setLocked`) once presentation's things are well on their way out (`--leave` of `HOLD_AT`); before that it can still be paged, and the first scrolling sends it home by itself (see `product-stages.js`). **Browsing**: each stage's stretch of scrolling takes the show up (`--browse-px`, `css/style.css`): by `--room-0` (the two bottom bars and 4rem) in presentation, and in specs by `--browse-room` — `fitBrowse()` measures where the column's last block would end unshifted and takes it up until it clears the Select bar by `BROWSE_CLEAR_REM` (16rem), never less than `--room-0`.
   - **Size** — `#productSize` (slider `#productSizeRange` 40–70 step 0.1, then the field `#productSizeInput` with the size guide's "?" button at its top right corner; the slider shrinks as the row narrows and goes below 320px) is pre-filled with 62 when specs first arrives (`seedSize()`), then follows what is typed or dragged: `setModelSize()` sets `state.sizeFactor` (size / 62), which scales the model and its labels, and rewrites the label bar's size (whole millimetres, the decimals small, like the order rows), the dimensions and the costs. The Select sheet opens pre-filled with it. The guide (`#productSizeGuide`) opens and closes with a 0.2s height glide (`tweenHeight(node, from, to, after)`: pins the old height, sets the new one next frame, and `.is-resizing` — `overflow: hidden` plus the transition — carries it; closing keeps the guide displayed with `.is-closing` until it is gone, and the column keeps `.is-extended` — its own scroll, `--below-max`, ending above the Select bar's fade — until then; a reversal starts from the height it had got to). The column does **not** scroll when the guide opens (an earlier `scrollTo` to the size row's offset only nudged it a few pixels: the row is the column's first, so the guide is in view); it closes on its button, a click elsewhere, or going back to presentation.
   - **`renderPrinting()`** — the chosen metal's printing technology (name and text); when the text changes with the metal, so does the row's height, and everything under it moves, so it glides there too (`tweenHeight()` from the old height, 0.2s, `.product-printing.is-resizing`).
   - **`renderSpecs()`** — the dimensions (cm, two places, ×`sizeFactor`; text for screen readers while the brackets are drawn, `.has-brackets`) and the cost chart. The pure `computeCosts(volume, costs)` derives weight = volume × density, raw materials = weight × (1 + loss margin) × price per gram, production = volume × production cost per cm³ and manufacturing = production − raw, from `product.geometry` × `sizeFactor`³ and `state.metalCosts` (`data.md`'s `metal-costs`); the weight is not shown. The chart's bars are **shares of the production cost** (raw from 0 to its share, manufacturing from there to the whole — `--from`/`--to` on each row), so together they fill their column at every size and metal. They **build** (`.is-built` on `#productCosts`, once specs is fully in) one after the other, and once that has played out (`.is-settled`, 1.8s later) a new metal moves them together on one transition. Figures it can't work out read "TBD" (the dimensions' row, which is for screen readers, "n/a"). `renderPrinting()` fills the printing technology from `metal-technology` and `printing-technologies` (`data.md`) for the chosen metal.
5. **Select bar + size sheet** — `#productSelectBar` is the page's blurred strip floating on the selection bar (static markup, `hidden` until `wireSelectButton()` shows it); its one button, `#selectButton`, says "Select" and opens the sheet, then "Add" while the sheet is up. The unit is looked up by *category* (not per-product) via `EmjiveSeries.categoryInfo()`; a category without one leaves the bar disabled with "No sizes available". Because that vocabulary is global rather than per-series, a cross-series hit needs no re-hydration. `#sizeModal` is a `size-modal--drawer size-modal--select-bar` bottom sheet resting right above the blurred bar — see `styling.md`. Its one control is the typed size field ("Size"), filtered on every keystroke by `EmjiveSelection.sanitizeSizeInput()` (two decimals at most; a comma-decimal keypad's `,` becomes `.`), with the size guide's "?" button at its top right corner, the guide as the sheet's last row and the material picker as its first row (a second `EmjiveMetalPicker`, `row: true`, kept in step with the page's own by `renderMetalOptions()`).

   There's no confirm button inside the sheet. `syncBar()` sets the label by the sheet's state, toggles `.is-add` on the bar (a `--bg` ground that fades in with the label, so the sheet resting above the bar doesn't show through its blurs) and dims "Add" until the field holds an orderable size (`EmjiveSelection.isValidSize()`) — through `aria-disabled`, not `disabled`, so the button keeps focus across the Select → Add swap; `setBarLabel()` fades the label out, swaps it and fades it back in (80ms) rather than changing it in plain sight. A click opens the sheet, or — sheet up and the size valid — calls `confirmAdd()`. **Enter** in the field adds too, since the bar sits outside the focus trap. `confirmAdd()` calls `EmjiveSelection.addItem({...})` with the self-contained snapshot (the resolved series included, the size through `normalizeSize()`) and then `closeModal()`, which calls `syncBar()` *before* `EmjiveFocusTrap.release()` so focus lands back on a live "Select" — covering both a successful add and an abandoned one (backdrop click/Escape). On `emjive:modify-open` the sheet closes itself (the drawer can still be opened over it, and a drawer row's Modify must not stack a second sheet on top) and the bar steps aside (`.is-away` + `inert`, back on `emjive:modify-close`) — the Modify sheet rests on the drawer's one remaining row, right where the bar rides. The bar also hides while an Add's peek is up, with no help from this file — pure CSS off `selection-bar.js`'s `.is-peek-up`.

All page state lives in one `state` object (product, metals, selected metal, the live model handle, the model poster's `<img>` while the viewer isn't in yet, the x-ray's original path, the icon-fallback image). A metal pick before the viewer arrives re-points the poster (`posterSrcFor()`), and the viewer is built for whichever metal is selected when it does.

**The carousel viewer's failure and freeze paths** (both inside `renderCarousel`, and easy to confuse):

- `onError → replaceModelSlideWithIcon()` is the **permanent** fallback, for an initial load/HDRI failure or a later WebGL context loss (see `three-viewer.js`'s `handleContextLost`). It also settles `viewerSettled`, and swaps the failed slide's contents for the same icon a model-less product gets, **in place** — the slide keeps its place in the track (`slideSources`), which is what the carousel's geometry is built on, so a failure arriving long after the carousel was measured and scrolled can't desync it. It reuses `state.iconFallbackImg`, so `onMetalSelect`'s existing swap branch handles a later metal switch with no extra wiring. Before this existed, either failure left a permanently blank 3D slide with nothing telling the visitor anything was wrong.
- `releaseModelViewer()` on `pagehide` / `restoreModelViewer()` on `pageshow` with `event.persisted` is the **reversible** one, and the mirror of `main.js`'s `releaseAllViewers` from the other end of the same navigation: pressing Back doesn't end this page, it goes into the back/forward cache still holding its WebGL context, decoded model and PMREM target while the grid rebuilds several of its own. `restoreModelViewer` is `attachViewer()` — the same function the first mount uses — which builds via `buildModelViewer()` (it reads `state.selectedMetal` at call time, so it picks up whatever metal is selected *now*) and **bails if the slide has lost `.product-carousel__slide--model`** — that class disappearing is exactly the `replaceModelSlideWithIcon` case, where a rebuilt viewer would be an invisible second context underneath the icon the visitor is looking at.
- **The Modify sheet takes the carousel viewer's place.** On `emjive:modify-open` the page's own viewer is released (`releaseModelViewer()`) and its slide goes back to the poster (`showPoster()`); on `emjive:modify-close` — dispatched after the sheet's viewer has been disposed — `attachViewer()` rebuilds it. The sheet builds a viewer of its own (a second WebGL context, a second PMREM environment, a second decode of a model that was once over a hundred MB) while the page's sat behind the backdrop drawing nothing anyone could see; now there is one at a time.
- **One loader for the whole carousel** (`carouselLoadHold(slide)`). The model, each photo and the model-less icon fallback all go through a single loader mounted on the carousel's **frame**, `#productCarouselFrame` (`EmjiveLoader.mount(carouselFrameEl, { target: slide })`, and `imageSlide`'s `loaderHost` option for the image slides), crossing the carousel's full width, instead of one per slide. It is on the frame rather than `#productCarousel` because the carousel is a stacking context of its own (its `transform`), inside which the loader passed under the metal picker and the edge bands; on the frame (`.product-carousel-frame > .loader`, `z-index: 5`, one `--tile` tall, lifted with the carousel) it is above everything laid in the frame. A wait only counts while its slide is on screen, so nothing fires for a photo that is scrolled out of view; the full rules are `js/loader.js`'s "a loader shared by several assets". The model's hold is taken in `buildModelViewer()`, handed to the viewer as `options.loader` and released by it (or here, if no viewer comes back). The photos fade in as soon as they have loaded, not when the loader leaves. The x-ray backdrop and the model's poster have no loader of their own — the page's arrival loader covers them.

## `js/product-stages.js` (~240 lines) — the product page's scroll show

A classic script, loaded on `product.html` only, ahead of `product.js`. **Exposes** `window.EmjiveProductStages.mount(stageEl, { onChange })` → `{ scrollToStage(index) }`. It reads the track's position on every scroll frame (rAF-throttled — the technique `series/bones/hero.js` uses for the homepage wipe) and publishes, as custom properties on `.product-stage`, one number 0 to 1 — `--to-specs`, eased (smootherstep) over the transition —, `--leave` (how far presentation's things have gone: linear in the scroll, **from its very first pixel** — not once the first stretch is over — to where `--to-specs` reaches `--t0`, which `product.js` sets; `--p-out` is `1 − --leave`; `invEase()` finds that point), `--browse-0` and `--browse-1` (how far through each stage's stretch of scrolling the page is, which the CSS turns into the show browsing up, see `product.js`; the second stage's is eased in — `entry()`, a quadratic over the first third of the screen's height of scrolling — `ENTRY_SCREENS`, the screen being the small viewport (a `100svh` probe, `screenPx()`: `innerHeight` changes as iOS Safari's toolbar collapses mid-scroll, which stretched the ramp while it ran) — then at `BROWSE_PACE` — 15px of show per 24px of scroll — which the ramp reaches without a step in the speed — so the column doesn't start browsing at full pace the moment the transition comes to rest). **That pace is fixed, so the end stretch's length isn't:** `syncEndHold()` sizes it — the room to cover (`max(--room-0, --browse-room)`, the latter fitted by `product.js`) over the pace, plus half the ramp — and sets it as `--end-hold` on the track (px; `css/style.css`'s height uses it, falling back to as long as the first stretch), and `measure()` splits the rest between the first stretch and the transition in their ratio. A taller column therefore means a longer page, and the page's length follows `--browse-room` as that settles and `data-stage` (the nearest stage), and calls `onChange({ toSpecs, leave, along, stage })` when they change (`along`: 0 to 1, how far the page is through the first stretch and the transition, linear in the scroll from its first pixel — what the model's path runs on; `product.js` takes the carousel's strip home and locks it once `--leave` passes `HOLD_AT` (0.25), since the photos are then on their way out to the model's right — until then the strip stays wherever the visitor paged it, whatever the page does). (`LEAD_RAMPS`, 0 now, would start the second stretch that many ramps before the transition ends.) (An earlier version took the strip home at the first pixel of scrolling and buffered the show's response behind it — `homeFraction`/`onHome`, `HOME_MS`/`CATCH_MS`; gone: the strip now goes home at `HOLD_AT`, in `product.js`.) The track is hold, transition, hold (`--hold-ratio`, `--stage-step`, in `css/style.css`), measured fresh each frame, so it holds at any size.

- **Focus** — `focusin` on an element inside `[data-stage-owner]` (one stage, or several space apart: the size row is `"specs"`) scrolls to the first of its stages when the show is in none of them — but only for `:focus-visible` (a keyboard), since a click on the model focuses the carousel's viewport, a tab stop, without any such intent.
- **The loop** — a fresh wheel gesture, swipe or key at the very end of specs (after `LOOP_QUIET_MS` of stillness, so a trackpad's momentum doesn't carry on into it) adds `.is-veiled` (the pin fades to the page background, 0.55s), jumps to the top while nothing shows, and lifts the veil. Instant under reduced motion.
- **Flow** — under `(max-height: 560px)` it stands down: `data-stage="flow"`, nothing published, the page a plain column (`css/style.css`'s flow block).

## `js/carousel.js` (~595 lines) — the carousels' dragging and paging

**Keyboard**: the viewport is `tabindex="0"`, `role="group"`, `aria-roledescription="carousel"`, `aria-label="Product images"`; ←/→ page one slide, Home/End jump, all through `centerOnSlide()` (the same centring a tap does). Dragging and tapping were the only ways to reach slide 2 before.

Moved out of `product.js` when the Modify sheet grew a small carousel of its own, so both run the same code. **Exposes** `window.EmjiveCarousel(carouselEl, { dragScroll })` → `{ sync(reset), center(index), goHome(), awayFromHome(), setLocked(locked) }` (`goHome()` centres the first slide, over `HOME_TRANSITION` (0.5s, gentler than a tap's 0.25s: it runs while the page scrolls, and Safari — the model's canvas and the edge bands' backdrop filters around the strip — drops frames of a short glide, which reads as a snap); `awayFromHome()` is how far the strip is from it, 0 to 1 in slides; `setLocked(true)` holds it and ignores drags, taps and keys). **With `dragScroll`** (the product page's) it also publishes, on the frame, `--paged-px` (how far the strip is paged on from the first slide, px, never negative) and `--paged` (0 to 1: `PAGED_SPAN`, 0.3 of a tile, and it is 1) and the class `.is-paged` (past 0.5), tweened with the strip itself through an inline `transition` on the frame over the same timing (both are registered `@property`s in `css/style.css`) — the metal picker follows them (`styling.md`). While locked nothing is published, so a strip taken home by the page leaves the picker where paging put it; `setLocked(false)` republishes, plus `EmjiveCarousel.imageSlide(src, alt, opts)` — a plain full-bleed `<img>` slide, `draggable = false`. `opts.deferred: true` builds the slide without starting the download; `slide.loadImage()` starts it (the loader over the slide waits for that too, so it still covers the box until the photo is in). `opts.loaderHost` (the product page passes `#productCarouselFrame`) sends the slide's wait through that element's **shared** loader — `EmjiveLoader.coverWithin(host, slide, ready)` — instead of a per-slide `cover()`; the Modify sheet's small carousel passes nothing and keeps one loader per slide. The product page defers its photos until after its first paint. The caller builds slides into `.product-carousel__track` and calls `sync(true)` once they're in and visible — it re-counts the slides from the track and centers the first; a resize re-clamps on its own.

No rim/arrow click zones: navigation is either a free horizontal drag (rubber-band overshoot past either end; release lands exactly where the drag left it, clamped back into bounds — no momentum coast) or a tap directly on a slide, which centers it (`centerOnSlide()`) however far from center it started. On a narrow/phone-width viewport (`isMobileCarousel()` — the one existing `max-width: 640px` breakpoint) a real drag instead always pages exactly one slide forward/backward and centers it, committing only past a real drag distance (15% of a tile) or a fast-enough short flick (gated by a minimum distance too, so touch-event jitter on a barely-moved drag can't read as a flick) — short/slow drags spring back to the slide they started on. **Where drags are read:** on the carousel's frame (`.product-carousel-frame`, falling back to the viewport where there is none, as in the Modify sheet), so nothing stacked over the strip — the edge bands — can hide one; a press counts only inside the strip's own band, not on a control (`INTERACTIVE`), and not on the model's circle (`.emjive-3d-viewer__hit`; for a viewer without a circle, any press inside `.emjive-3d-viewer`). The slide under it is found by `elementsFromPoint`. **The axis rule:** a pointer's horizontal-vs-vertical intent is axis-locked in `onPointerMove` (the first movement past a small slop decides it, once): within 45° of horizontal (`|dx| > |dy|`) it pages the strip, anything else is vertical. A vertical gesture is left to the browser's own `touch-action: pan-y` for touch (a scripted touch scroll fought the compositor's sticky stage on iOS Safari), and with `dragScroll` (the product page) scripted for a mouse or pen, which have no native drag scroll: `window.scrollBy({ behavior: "instant" })` per move, grab-style, with an exponential glide (`GLIDE_TAU`) after a flick, stopped by a wheel or a new press. A touch drag moves the strip `TOUCH_GAIN` (0.7) px per px; a mouse or pen is 1:1; the phone's paging goes by the finger's own distance; `pointercancel` (the browser interrupting a pointer itself — that same scroll handoff is the common case) is handled separately from a clean `pointerup` so an interrupted gesture is never misread as a tap. Every way a slide gets centered shares one symmetric ease-in-out transition (`CENTER_TRANSITION`; `CANCEL_TRANSITION` is the same curve, shorter, used only when a mobile drag springs back). Bounds stay "first/last tile centered" (not edge-flush).

The drag's pointer is captured on the **track**, not the viewport: in the Modify sheet only the track takes pointer events (the empty band beside the slides lets a tap through to the sheet's backdrop), so a capture on the viewport would lose the drag.

**Notable gotchas** (from the file's own comments): `img.draggable = false` + `dragstart` prevention stops the browser's native image-drag gesture from fighting the custom pointer-drag scroll; a `pointercancel` doesn't reliably carry the pointer's final coordinates, so settling a drag interrupted mid-gesture falls back to the strip's own live position instead of the event's `clientX`; a press inside the model's circle (`.emjive-3d-viewer__hit`) is left alone entirely (no `pointerdown` tracking at all) so it rotates the model via `TrackballControls` instead of paging the carousel; a locked strip (`setLocked`) still scrolls the page by a vertical drag but ignores sideways ones and taps.

## `js/order-rows.js` (~690 lines) — the item rows, in every list

**`EmjiveOrderRows.notice(message)`** is the site's replacement for `alert()`: one `role="status"` element (`.emjive-notice`, created on first use), a full-width bar that slides up from the bottom of the screen and rests on whatever stands there (`stackHeight()` measures the selection bar and its drawer, the Select/checkout bars, the checkout drawer and the Modify sheet each time it is shown), then slides away after 6s. Used by the Modify sheet's "couldn't be found" cases and the checkout stub.

The rows `launch-order.html`'s order list and the floating bar's drawer share (`selection-page.js`, `selection-bar.js`) — and the copy in the order page's drawer over its checkout bar — so they can't drift apart. **Exposes** `window.EmjiveOrderRows.create({ listEl, rowClass, showPrice, onModify, onResize, dropAtOnce })` → `{ render(items, { animate }), preview(index, values), settledHeight(), buttonAt(index), offerUndo(index, handlers), isHolding() }`, plus the two module-level helpers `EmjiveOrderRows.preload(srcs)` and `.resampleBand(el)` that `product.js` and `modify-modal.js` reuse.

- **A row is one `<button>`** (`li.order-item > .order-item__inner > button.order-item__content`: thumb, name + `.category.metal.size` via `appendSize()`, the price when `showPrice`) with a spoken `aria-label` ("Modify Furcula, steel, size 62.50"). A tap anywhere on the `<li>`, padding included, calls `onModify(binding)` — no hover state, no in-row overlay; the Modify sheet does the rest. A row mid-collapse ignores taps.
- **Rows follow the selection one change at a time** instead of being rebuilt. With `animate` on, `render()` runs `EmjiveSelection.singleChange()` over the old and new keys: an **update** (a Save) crossfades just the parts of that row that changed — icon, label, price (`fadeSwap()`: `.is-swapping` fades a part out in 0.12s, the new value goes in, a new icon only once decoded so there's never a blank frame, and it fades back in over 0.18s; a per-element token makes the latest swap win); a **remove** (an Unselect) collapses the row (`.is-removing`, taken out once *both* the inner's `max-height` transition *and* its invert band's own opacity transition have ended, or a 400ms fallback — the band now fades out on a longer, delayed schedule than the row's own collapse, per `styling.md`'s "bar first-in/last-out" rule, so `collapse()` races both via `Promise.all` rather than just the one that used to finish last); an **insert** plays that collapse in reverse — the row goes in at full size so `onResize()` can measure where the list is heading, snaps shut under `.is-instant` with no frame painted in between, and opens from there on the next frame, `.is-expanding` clipping it meanwhile (an Undo normally doesn't get here: it finds its held row — next bullet). Anything it can't explain as one change, or `animate` off, rebuilds.
- **`preview(index, values)`** — the Modify sheet's live draft: the row's changed parts (any of `metal`, `size`, `price`, `image`) switch to `values` **at once, no fade** (`crossfadeRow(binding, item, true)`, using `setNow()`, which also cancels a `fadeSwap` still under way so it can't land over the draft); `null` puts the stored item back. Storage is untouched, and a row that has left the list is ignored. Each binding tracks `shown` — what the row currently displays — separately from `item`, and `crossfadeRow` compares against `shown`, so a Save after a preview finds nothing left to swap.
- **`preload(srcs)`** fetches and decodes images ahead of a no-fade swap (kept in a map so they stay in memory), so a pick that changes an icon shows the new one at once instead of the old one lingering. **`resampleBand(el)`** nudges the invert band's own filter (`.is-resampling`, an imperceptible `invert(0.99)` for two frames — see `styling.md`) so Safari's backdrop-filter re-samples at once; used wherever a value under a band changes with no fade to cover it (a preview, a thumbnail `load`, `product.js`'s label bar).
- **Thumbnails are the icon's 128px version** (`thumbSrc()` → `EmjiveLoader.variant(src, "128")`, set through `EmjiveLoader.setSrc()` so a missing file falls back to the 512px icon): a row's thumb is 48px, the bar's icons 36px, and the 512px icons are 25–40KB each against ~3KB — on every page that has a selection. `selection-bar.js` does the same for its icon strip. `scripts/make-image-variants.js` writes them (and `auto-render` rewrites them after a render); `validate-data.js` fails the build if one is missing.
- **`offerUndo(index, handlers)` holds an Unselect's row open as its Undo line.** The Modify sheet calls it just *before* `removeItem()` (`pendingHold`); `render()` then answers the single **remove** at that index by keeping the row (`hold()`): it comes out of `bindings` but stays in the DOM at full height, its content `inert`, an `.order-item__undo` (an `Undo` button + `.order-item__undo-band`) appended and laid out before `.is-undo` lands, so there is a state to transition from. `handlers` is `{ onUndo, onGone }`; the returned handle is `{ held(), button(), leave(done), drop() }` (`held()` is false when the list wasn't animating — then the removal is plain and there is no offer). **`leave(done)`** is the offer running out: `.is-undo-leaving`, and once the band's `width` transition ends the row closes like any removed row (`collapse(binding, done)`). **`drop()`** closes it at once (another Modify opened) — with `dropAtOnce` (the bar's drawer sets it) the row is removed without collapsing, since that drawer is about to measure the tapped row's place and mustn't have the row above it still shrinking. An **Undo** is a later **insert** whose key matches the held row: `revive()` puts *the same row* back in `bindings` (`.is-undo` → `.is-undo-revived`, a pure CSS sequence — the band sweeps the whole row, the row's own band and content return after it — then the undo line is taken down). The row is only moved in the DOM if something came between: re-inserting an element drops the state its transitions start from, and the whole sequence snapped. A `rebuild()` sweeps a held line away (`onGone`, deferred a tick since the page it tells may be the one rendering). `isHolding()` is what a page checks before treating its list as empty.
- **The list emptying out is left to the page** (the drawer closes, the order list crossfades to its empty state), which simply stops calling `render()` — so the last row leaves along with its list rather than collapsing on its own first. Except while a line is held (`isHolding()`): the last item's Undo line keeps the list up, doesn't collapse when its offer runs out (`finishHold()` with no other rows left just reports `onGone`) and the page lets go of the list then.
- **`settledHeight()`** — the list's height once every row now collapsing or expanding has finished. What the bar's drawer sizes itself to, so it heads straight for its final height rather than overshooting and correcting afterwards.
- **`buttonAt(index)`** — the row button now at that index. The Modify sheet's `returnFocus` looks it up late, since rows come and go.

## `js/modify-modal.js` (~845 lines) — the Modify sheet

The one "Modify" popup on the site, opened by tapping a row in either list — so it lives on all seven pages and builds its own DOM at load (`#modifyModal`, a `.size-modal--drawer.size-modal--modify` bottom sheet; no page has markup for it). **Exposes** `window.EmjiveModifyModal = { open(item, index, options), isOpen(), attach(bar) }`.

An `openToken` makes the latest tap win over a slower earlier fetch; a product that's gone, or a failed fetch, shows a pop-up notice (`EmjiveOrderRows.notice`: "This item listing couldn't be found, please reload.") rather than leaving a row that silently does nothing. - **`options`** — `bar`: the page's bar, as `{ el, show(strip), hide(strip) }` — the strip lives in `el`, and `show`/`hide` let that bar hand its own content over its own way (`selection-bar.js`'s summary slot, `selection-page.js`'s checkout bar); `offerUndo(index, handlers)` — the page's list holding the unselected row open as its Undo (its `rows.offerUndo`, wrapped so the page can settle its drawer/list when the line is gone; no `offerUndo`, no Undo); `onOpen()`/`onClose()` (the floating bar's drawer shrinks to the row and grows back; the order page's drawer opens and closes); `returnFocus`/`fallbackFocus` (an element or a function returning one); `onPreview(index, values)` — the sheet's draft changed (a metal pick, a size typed): the page passes it on to its list(s) via `EmjiveOrderRows`'s `preview()` so the row under the sheet follows the draft live; `values` is `null` when the sheet is dismissed unsaved. `selection-page.js` previews both copies of the row (the list's and the drawer's).
- **Its buttons live in the page's bar** — the strip (`.modify-strip`), mounted into the bar as soon as the bar exists, via `attach(bar)` (called by `selection-bar.js` and `selection-page.js`), rather than in the middle of the first open. Unselect (the left quarter of the page's content span, plain `--white` label) and Save (the right three quarters of it, label centered on the whole bar; `disabled` while the field holds nothing orderable — `isValidSize`) share one invert band (`.modify-strip__band`) sized to Save's own button at rest, so only Save's label reads dark on a light band — Unselect is never under it (an earlier version gave each of Unselect/Save its own band, measured by this file into `--unselect-band`/`--save-band` on every open and resize; both the second band and the measuring are gone now). The strip's own outer show/hide (`bar.show`/`hide`) splits its dark surface (`css/style.css`'s `.modify-strip::before`, grouped with the band) from its buttons' opacity — surface leads in/trails out, buttons the reverse, `css/style.css`'s `--fade-fast` each — since a pseudo-element's opacity is capped by its host's, so the old single-opacity container couldn't time the two independently. The focus trap `include`s the strip, so Tab reaches Unselect and Save; Enter in the size field saves.
- **The draft** — `draftValues()` is the item as the sheet would save it right now: the picked metal, that metal's price and icon, and the field's size *when it's orderable*, else the item's own (a half-typed field mustn't blank the row's label). `previewDraft()` sends it to `onPreview` on every metal pick and size input, and once on open; `close()` sends `null` unless told `keepPreview` (a Save, whose row already shows what was stored, or an Unselect, whose row is leaving). A pick's model re-tint is `tintAfterPaint()` — after the row's new label has painted, same reasoning as `product.js`. On open every metal's icon and poster is `EmjiveOrderRows.preload()`ed. The size field's label reads "Size".
- **Save** → `updateItem(draftValues())` (metal, `normalizeSize()`d size, that metal's price and icon), the sheet closes, and the band — grown to cover the whole strip, then faded out (`css/style.css`'s `.is-saved` rule, ~0.5s total: the width grow doubles as the fade's own delay) — finishes before `bar.hide()` hands the bar back (`leaveAfterSave`, waiting on the band's own `opacity` `transitionend`, with `SAVE_LEAVE_MS` — 600ms, sized for this longer real transition — as its fallback). **Unselect** → asks the list for an Undo line (`options.offerUndo`), then `removeItem()` with the item kept aside; the strip hides like any dismissal (the bar gets its content back in the usual sequence), the sheet closes, and focus goes to the Undo button on the item's own line — the row is held open, not collapsed (see `order-rows.js`). **Undo** (offered for `UNDO_MS`, a plain 4s timer — hover and focus don't extend it) → `insertItem()` back at its index; the list finds its held row and revives it (the band sweeps the whole row, then the content fades back in), and focus goes to the restored row. An unused offer runs out (`handle.leave()`: the band regresses to the left edge, the row closes), the removal standing; another Modify opening meanwhile closes it at once (`dropUndo`); if the list lets go of the held line by itself (a rebuild), `onGone` ends the offer (`forgetUndo`). Nothing here re-renders anything — the lists follow `emjive:selection-changed`.
- **Events** — dispatches `emjive:modify-open` before building anything (`product.js` closes its size sheet; `main.js` frees a WebGL slot) and `emjive:modify-close` once its viewer is actually disposed, after the slide-out.
- **Laid out like the specs stage** — each control row is a label, a gap and the control (`--label-col`, `--label-gap`): *Material* (the picker with `row: true`) and *Size* (the plain field with the "Size guide" button inline to its right — no slider here). The guide (`EmjiveSelection.fillSizeGuide` / `wireSizeGuide`, filled from the item's category on every `open()`) is the sheet's last row: it opens at the bottom, the sheet growing upward; the button, or a click elsewhere in the sheet, closes it.
- **`pagehide`** — closes the sheet, disposes the viewer at once rather than after the slide-out (a bfcached page is still live, context and all), and ends any Undo offer (`expireUndo(true)` drops the held line at once), so a restored page doesn't come back offering one.

## `js/selection-bar.js` (~750 lines)

The floating bar, on every page except `launch-order.html` (that page isn't in its script list at all, plus it self-guards with `if (!window.EmjiveSelection) return;`). Builds its whole DOM programmatically and appends to `<body>`.

**The summary row's one slot** shows exactly one thing at a time, in this order of precedence: `strip` (the Modify sheet's strip, while the sheet is up), `order` (the thumbnail strip + "Order ›") and `empty` ("No selected item"). `computeSummaryMode()`/`summaryElFor()` pick one; `updateSummaryState()` swaps. The swap is **sequenced, not simultaneous**: the incoming label only starts fading in once the outgoing one has fully faded out (`revealCurrentSummaryMode()`, chained off the outgoing element's own `transitionend` — filtered on `e.target`, not just `propertyName`, now that the strip's own opacity is two separately-timed layers rather than one, so a button's faster leg bubbling up can't fire this early — with a 350ms fallback for a backgrounded tab) — a simultaneous crossfade left two semi-transparent labels stacked mid-transition. A swap asked for while another is still mid-fade **retargets** it rather than starting a second one on top (saving and at once tapping another row). Hidden labels are `inert`, and so is the whole summary row while the strip covers it. All share one `--fade-fast` opacity duration — see `styling.md`. **The icon strip joins this same reveal now, rather than fading in on its own the instant `is-strip-active` clears**: `updateSummaryState()` still hides it at that same instant (its own `.is-hidden` class), but `revealCurrentSummaryMode()` is what un-hides it, alongside Order/the empty label — so icons and whichever label is coming back fade in together instead of icons arriving a beat early, the bug this fixed.

**The bar has no "add" mode any more** — `product.html`'s Add button is the blurred Select bar (see `product.js`), so this bar stays a plain summary and its drawer stays openable the whole time the size sheet is up (it used to be forced shut once a size was typed, and `window.EmjiveSelectionBar` existed to drive that; both are gone).

**The add peek.** On a `selection-changed` with `detail.action === "add"`, `peekNewest()` raises the closed drawer just far enough to show the newest row (the whole list, padding included, when it's the only one), holds `PEEK_HOLD_MS` (1s), and lowers it — skipped if the drawer is open or reduced for a Modify, and cancelled by anything that opens, empties or restarts the drawer (`cancelPeek()`). The inner box jumps straight to the peek height under `transition: none` so the row's scroll can be set at once; the drawer's own height is what animates. `.is-peeking` is the whole peek; `.is-peek-up` is the narrower window in which the row is actually up, and is what hides the product page's blurred Select bar (`styling.md`) — gone as the row draws up, back as it draws down.

**The drawer** lists the items as `js/order-rows.js` rows (`.order-item--drawer`, created with `dropAtOnce`); tapping one calls `openModify()`, which opens the Modify sheet with this bar as its `bar` (`stripHost`, `attach`ed at load) and an `offerUndo` that wraps `rows.offerUndo`: while the unselected row's Undo line is held the drawer stays open even for the last item (`render()` keeps feeding `rows` while `rows.isHolding()`, and `setDrawerOpen(true)` skips its rebuild then, which would sweep the line away), and once the line is gone a drawer with nothing left closes (`setDrawerOpen(false)`) and re-measures. The drawer's height is a real measured px value, set on the drawer and on its inner scroll box alike by `syncDrawerHeight()` — it reads `rows.settledHeight()`, caps the list at two thirds of the screen (`LIST_CAP`), and publishes two variables on `<html>`: `--selection-bar-live-height` (summary + the height the drawer is heading to, a peek excluded — what either sheet rests on) and `--selection-bar-stack-height` (the same with a peek included — what the product page's blurred Select bar rides on, so it rises and falls with the drawer in step with its own 0.3s ease). While the Modify sheet is up the drawer is **reduced to the tapped row** (`setDrawerReduced()`): its height becomes that row's, `.is-drawer-reduced` stops scrolling by hand (a space-taking scrollbar's width goes back as padding, so the rows keep their width), and `animateDrawerScroll()` moves the list's scroll in step with the height transition — each frame, the same share of its distance as the drawer has covered of its own — so the row glides into place right above the bar. When the sheet goes, height and scroll go back. `setDrawerOpen()` registers the drawer with `window.EmjiveMenus`, whose `root` also counts `#modifyModal` as inside — the sheet's backdrop closes the sheet, not the drawer.

**The icon strip** (newest first in DOM, so the oldest pick stays anchored next to Order) animates only the one icon a change touched (`EmjiveSelection.singleChange()`): an Add slides its icon in from the screen's left edge (`playEnterAnimation`), an Unselect collapses it (`playExitAnimation`), an **Undo plays that collapse in reverse** (`playRestoreAnimation` — told apart from an Add by the change event's `detail.action`), a Modify swaps its `src`. Anything else rebuilds. The strip doesn't shrink to fit once wide: `.selection-bar__icon` is `flex-shrink: 0` and the strip `justify-content: flex-end`, so the excess overflows past its *left* edge, where `.selection-bar__toggle` clips and fades it — see `styling.md`.

This file has no notion of **which page it's on**, which was always the point. It subscribes to `window.EmjiveHero.onScroll` for the homepage's scroll-driven entrance — unconditionally: the active series' hero owns all the geometry and publishes how far past its trigger the page has scrolled, and this file measures its own `.selection-bar__summary` height to turn that into a transform. On a page with no hero nothing ever publishes, so the bar just stays visible. The starting-hidden state is `css/style.css`'s `body.has-series-hero` scoping (see `pages.md` for why that stopped being `:has()`).

Listens for `emjive:selection-changed` (`render(e)`) — this is how it stays in sync with adds from `product.js` and every change the Modify sheet makes.

## `js/selection-page.js` (~400 lines) — `launch-order.html`'s checkout review

The order page's logic — see `pages.md`'s `launch-order.html` section for what it all looks like.

- **Rows** — `js/order-rows.js` rows with prices; tapping one opens the Modify sheet with the checkout bar as its `bar`, and its `onPreview` forwards the sheet's live draft to both the list's rows and the drawer copy's. `render()` runs on load and on every `emjive:selection-changed`, and the rows animate just the one change. `listState` tracks whether the list or the empty state is showing: the last item leaving crossfades the list into the empty state, and an Undo crossfades it back — except that an Unselect's row is held as its Undo line (`rows.offerUndo`, via `openModify`'s `offerUndo`), and a held line counts as the list still being there (`rows.isHolding()`): the list stays up through the 4s offer, and `onGone` re-runs `render()` so the empty state takes over only once it's over (`crossfade(fromEl, toEl)` — a sequential opacity swap, hand-orchestrated because `[hidden]` is `display: none`, which can't transition; a newer one supersedes one still under way).
- **The checkout bar as the strip's host** (`stripHost`, `attach`ed at load): showing the strip sets `.is-strip-active` (a pure-CSS, `transition-delay`-sequenced swap — now a three-beat cascade, row-out then the strip's own surface-in then its content-in, since the strip's reveal itself split into two beats — see `styling.md`), makes the bar's own row `inert`, and — through `stripShown`, then `stripFading` for the strip's own fade-out (`STRIP_FADE_MS`) — keeps the bar up after the last item's Unselect until the strip has gone, with `.is-empty` keeping its row out meanwhile (nothing left to total). The Undo is not in the bar: it's on the unselected row's own line in the list. The checkout button ignores clicks meanwhile.
- **The drawer over the checkout bar** — this page's version of the floating bar's drawer shrinking to the tapped row: `.order-checkout-drawer`, a fixed element built here holding a copy of the tapped row (its own `EmjiveOrderRows`, `inert` and `aria-hidden` — assistive tech already has the real row in the list). Opened on the sheet's `onOpen` (max-height to the row's measured height, publishing `--selection-bar-live-height` so the sheet rests on it), closed on `onClose`. A Save crossfades the copy along with the real row (`detail.action === "update"`); an Unselect leaves it to close with the sheet.
- **Shipping/terms/checkout** — `SHIPPING_OPTIONS`, a small in-file placeholder array (easy to extend later, not a restructure), rendered as a single-select dot-indicator list. Shipping is part of the checkout bar's total. The terms row's click is delegated across the whole element (the dedicated tick-box or the surrounding sentence both toggle; a click on the actual `<a>` to `terms.html` navigates instead). `updateCheckoutGate()` disables `#orderCheckoutButton` until both a shipping option is selected and terms are ticked. The button itself is a stub — no Stripe session exists yet, so a click (once enabled) just shows a pop-up notice (`EmjiveOrderRows.notice`) that it isn't connected.

## `js/loader.js` (~855 lines) — the logo loader

A classic script, blocking in `<head>` on **all seven pages** (after the stylesheet, after `scroll-memory.js` on `index.html`, before `series.js`), exposing `window.EmjiveLoader`. One loader per host (a `WeakMap`), and **holds**: `mount(host, opts)` returns a hold, and the loader goes when the last hold on that host is released.

- **API** — `mount(host, { page, bleed, watchdog, target })` → `hold` (`hold.done()` releases it, idempotent); `cover(host, ready)` → Promise (hide the host's `<img>` children behind a loader, reveal them with a quick fade once `ready` settles *and* the loader has left); `coverWithin(host, target, ready)` → Promise (`cover`'s counterpart for a shared loader, below); `imageReady(img)` → Promise (loaded or failed, then `decode()`d, raced against 1s); `pageReady()` (the arrival loader may go; also dispatches `emjive:pageready` on `window`, once, on every page whether or not it has an arrival loader); `isPageReady()`; and the responsive-image helpers below (`isPhone`, `onPhoneChange`, `versions`, `variant`, `setSrc`, `upgradeImage`).
- **The guardrails** — every path goes through them. (1) **Never removed while a part is visible:** `hold.done()` resolves only inside the cycle's *safe window* — after the last (staggered) part has fully left, before the first re-enters — polled off the first part's `currentTime` (no delay, so it is the cycle's clock). Mid-crossing it waits — **but accelerated**: a hold released with none left outstanding ramps the animations' `playbackRate` from 1 to `FINISH_RATE` (2.5×) over `FINISH_RAMP_MS` (700ms) on a smoothstep curve (`finishCrossing()`; the rate is eased, not switched, because a step is a visible jolt, and the `playbackRate` setter keeps `currentTime` so the parts carry on from where they are), so content that was ready doesn't sit behind the cover for most of a cycle. The rate survives a `ResizeObserver` rebuild (`s.rate`) and a destroy cancels the ramp. In the blank gap it is immediate. (2) **Show-delay:** the loader is created hidden and only shown `--loader-delay` after its host first intersects the viewport (an `IntersectionObserver`, which respects overflow clipping — a lazy image far down the page, or a slide not scrolled to, costs nothing); released before that, it never shows. (3) **Watchdog:** each hold auto-releases after 15s (`watchdog: false` is for `loader-test.html`'s endless loops). (4) **Reduced motion:** `mount` returns an already-released no-op, `cover` hides nothing.
- **When a hold is released with others still outstanding** the released hold's promise still waits for a safe window (so its asset is revealed at one), but the loader keeps looping — which is how a card's fallback image shows under a loader still waiting for the 3D model.
- **A loader shared by several assets** (`mount(host, { target })`, `coverWithin`) — the product page's carousel holds a 3D model and some photos that load independently, which used to have a loader each. Now they share one, mounted on the carousel, and each asset takes a hold naming the element it appears in (`target`). A hold only counts while its target is on screen — an `IntersectionObserver` per hold, which respects the carousel's own clipping, with `VISIBLE_RATIO` (0.2: a sliver of a neighbouring slide doesn't count; on a phone the slide beside the model peeks about 10%). The loader is **active** while some unreleased hold is visible (`isActive`), and `reevaluate()` runs whenever that changes: the show-delay (`--loader-delay`) is counted from the moment it becomes active and abandoned if it stops being so first, so a wait nobody can see never shows anything; once shown, the loader carries on while active, and when the last visible wait ends — released, or scrolled out of view — `park()` finishes the crossing in progress (the same acceleration and safe window as a release) and `hide()` puts it away (animations cancelled, `.is-waiting` back) **without destroying it**, since holds remain; a pending asset scrolling into view starts it again, after the delay, as a new cycle (and a loader being finished off when something visible starts waiting again drops back to the loading pace); the last release destroys it as before. `s.targeted` marks such a state — decided by the first mount on the host, which has no host-level on-screen test of its own. `coverWithin` is `cover` for it, with one difference: the target fades in **as soon as its asset has loaded**, because the loader isn't its own and goes when nothing visible is still loading.
- **Timing** — tokens on `.loader` (see `styling.md`): `--loader-cycle` in seconds, every phase as a percentage of it, the gap held exactly and in/slow/out scaled to fit. **One keyframe set drives transform *and* opacity**, so move and fade share every offset and curve and cannot drift out of sync. The two eased legs are **quadratic curves** (constant deceleration into the slow stretch, constant acceleration out of it) written as the equivalent cubic `cubic-bezier(...)` (CSS has no quadratic easing); each leg's end next to the slow stretch is solved to the drift's own speed, so there is no jolt. The drift's speed is `--loader-slow-speed` × the crossing's average, and its length follows (speed × `--loader-slow`), capped at 90% of the travel.
- **Geometry** — travel = half the loader's box + half the mark, so parts start fully outside the container's right border and end fully outside its left. Measured from the loader (not the window), and rebuilt by a `ResizeObserver` keeping each animation's `currentTime` — hosts can be 0×0 at mount (the product page builds while its content is `[hidden]`). **`bleed: true`** is for a host whose own edges are invisible — a 3D viewer's box in a carousel slide, deliberately smaller than its slide: the loader isn't clipped at that box, and travel is measured to the nearest clipping ancestor (`findClipAncestor`, the carousel's viewport), widest side wins. The ancestor is observed too.
- **The page's arrival loader** — a page opts in with `data-page-loader` on `<html>` (`index`, `product`, `series`). The script, running before `<body>` exists, adds `html.emjive-page-loading` (an opaque pseudo-element cover, so half-built content never flashes) and mounts the loader on `<body>` at DOMContentLoaded; the page calls `EmjiveLoader.pageReady()` when it has something to show — `js/series.js` for the homepage (the hero's first `<img>` decoded; **not** the products below, which only feed the hero rings; also on no-hero / hero failure), `js/product.js` (once the x-ray backdrop and the model's poster are in — capped at 6s — and after `showNotFound()`), `js/series-page.js` (manifest in, or not-found). Released through the safe window, then `emjive-page-revealing` fades the cover. **Skipped** under reduced motion, when the homepage is restoring a back-navigation scroll (`js/scroll-memory.js` owns that and runs first), and on a bfcache restore (`pageshow` persisted clears it); a 15s watchdog clears it if a page script never calls `pageReady()`.
- **Where it mounts** — homepage card icon (`cover` on the figure, `js/main.js`) and, sharing that loader, the card's 3D viewer (`mount` on the figure, passed to the viewer as `options.loader`); every `imageSlide()` photo (`cover` per slide in the Modify sheet; on the product page `coverWithin` the one shared carousel loader, which also carries the model's wait — see above); the viewer itself (below). Deliberately **not** mounted on tiny slots (order-row thumbs, the label thumb, bar icons, metal swatches), the hero's rings/x-ray, or the four pages that never wait.
- **Responsive images** — the big pictures ship in **four versions**, written by `scripts/make-image-variants.js` (`tooling.md`, `assets.md`): desktop low `<name>_lo.webp`, desktop high `<name>.webp` (the original), smartphone low `<name>_m_lo.webp`, smartphone high `<name>_m.webp`. The smartphone ones are **cropped** to the middle of the picture (all a phone shows), so they are smaller as well as lower-res; a picture that is hidden or far down the page has no low version. **A phone** is `PHONE_QUERY`, `(max-width: 640px) and (max-aspect-ratio: 3/5)` — the aspect clause is what the hero's crop is sized for, so a square 640px window gets the desktop files; the same string is in `css/style.css`, `series/<slug>/hero.css` and `vite.config.js`, and `validate-data.js` fails the build if any copy differs. `isPhone()` / `onPhoneChange(fn)` read and watch it; `versions(src, hasLow)` → `{ first, hi }` (what to show first and what to swap in, for the viewport right now); `variant(src, suffix)` builds a sibling name; `setSrc(img, first, src)` points an image at `first` and falls back to `src` on an error; `upgradeImage(img, hiSrc)` → Promise, which swaps `hiSrc` in once the image has loaded and the browser is idle, by decoding it off-screen first (one frame, no flicker, same box) — and **doesn't** on `saveData` or a 2g/3g connection, or when the file in use already covers the rendered size × DPR. Users: `product.js` (x-ray), `series.js` (hero). The swap does not register as a new Largest Contentful Paint (tested: Chrome keeps the first candidate).

## Cross-cutting contracts (the highest-value section if you're changing behavior that spans files)

- **`window.EmjiveSeries`** — set by `js/series.js` (blocking, in `<head>`), consumed by `main.js`, `product.js`, `modify-modal.js` and `series-page.js`. The one place "which series is this, and where's its data" lives.

- **`window.EmjiveSeriesHero`** — set by a series' `hero.js`, called by `js/series.js`. `{ init(root, ctx), onProducts(products) }`.
- **`window.EmjiveModelViewer`** — set by `three-viewer.js`, consumed by `main.js` (grid), `product.js` (carousel), `modify-modal.js` (the sheet's small carousel), and `scene-tool.html` (a standalone dev tool, `options.freeOrbit`/`options.swatch`). The one place 3D viewer construction/materials/camera behavior lives.

Other browsers get the blur alone.

Every `100vw` breakout is that much too wide and sticks out half of it past each edge of the page; `.product-edge-veil` offsets itself by it so its edge masking lines up with the edge actually seen. - **`window.EmjiveProductStages`** — set by `product-stages.js` (`product.html` only), consumed by `product.js`. `mount(stageEl, { onChange })` → `{ scrollToStage(index) }`; publishes `--to-specs`, `--leave`, `--browse-0`, `--browse-1`, `data-stage` on the stage.
- **`window.EmjiveMetalPicker`** — set by `metal-picker.js` (all seven pages), consumed by `product.js` and `modify-modal.js`. `mount(container, { metals, selected, onSelect, row })` → `{ select(metal) }`.
- **`window.EmjiveLoader`** — set by `loader.js` (every page; blocking in `<head>`), consumed by nearly everything: `mount`/`cover`/`coverWithin`/`imageReady`/`pageReady`/`isPageReady`, and the responsive-image helpers (`isPhone`, `onPhoneChange`, `versions`, `variant`, `setSrc`, `upgradeImage`) used by `product.js`, `series.js`, `order-rows.js` and `selection-bar.js`. Also the **`emjive:pageready`** window event it dispatches once (`viewer-entry.js` waits for it on the homepage).
- **`window.EmjiveModifyModal`** — set by `modify-modal.js`, consumed by `selection-bar.js` and `selection-page.js`. `{ open(item, index, options), isOpen(), attach(bar) }`; `options.bar` (`{ el, show(strip), hide(strip) }`) is the contract between the sheet and whichever bar hosts its strip.
- **`"emjive:modify-open"` / `"emjive:modify-close"`** — `CustomEvent`s on `window`, dispatched by `modify-modal.js` before it builds anything and once its viewer is disposed. `product.js` closes its size sheet on the first, hides its Select bar until the second and gives its carousel viewer back to the poster between the two; `main.js`'s grid gives up one WebGL slot between the two.
- **`prefers-reduced-motion`** — honoured in three places that don't know about each other (`js/loader.js` is the third: it checks the query itself and skips its animation). `css/style.css`'s trailing `@media` block collapses every CSS transition site-wide (at `0.01ms`, **not** `0s` — see that block's own comment; several `transitionend` listeners drive real logic and a `0s` transition never fires one). `js/three-viewer.js` reads the query directly via `matchMedia` for the four things CSS can't reach: release inertia, the ease-back-to-default pose reset, the up-vector leveling drift and the idle nudge. It reuses `freeOrbit`'s existing plumbing via a shared `noAutoMotion()` predicate, so the two switches can't drift apart. Deliberately **not** a shared `window.Emjive*` global: `three-viewer.js` is the only JS consumer, and it's also loaded by `scene-tool.html`, which loads no `series.js` at all. The homepage hero's x-ray wipe is deliberately **not** gated — it's scroll-linked and entirely visitor-driven, nothing plays on its own, and short-circuiting it would strand the floating selection bar off-screen (see `window.EmjiveHero` above).
- **`window.EmjiveScrollMemory`** — set by `scroll-memory.js` (`index.html` only), consumed only by `main.js`, which calls `contentReady()` once the grid is rendered and filtered. Guard every call on the object existing; it is absent on every other page.
- **`"emjive:selection-changed"`** — `CustomEvent` on `window`, dispatched synchronously by every `selection.js` mutation, with `detail: { action, index }`. `selection-bar.js` and `selection-page.js` listen for it.
- **`pagehide` / `pageshow`** — five separate files listen, for three different reasons, and it's worth knowing which is which before adding another. `main.js` (grid) and `product.js` (carousel) release their viewers on `pagehide` and rebuild on `pageshow` with `event.persisted`, so a bfcached page holds no GPU memory; `modify-modal.js` closes its sheet and disposes its viewer on `pagehide`, and ends any Undo offer, without rebuilding anything; `three-viewer.js` drops its decoded-HDRI cache and ends its idle Draco workers on `pagehide`; `three-viewer.js` also registers `requestRepaint` on every `pageshow`, for the discarded-drawing-buffer case; `scroll-memory.js` saves the offset on `pagehide` and restores it on a persisted `pageshow`. Nothing uses `unload` anywhere — an `unload` listener would disqualify the page from the back/forward cache entirely, which is the thing all of the above are written around.
- **`localStorage["emjive_selection"]`** — the persisted selection array (via `selection.js`).
- **`sessionStorage["emjive_model_interacted"]`** — unrelated to selection; remembers within a browsing session whether the visitor has already discovered models are draggable, to stop nudging them with the wiggle hint (set/read in `three-viewer.js`).
- **`sessionStorage["emjive:scroll:<key>"]` + `history.state.emjiveScrollKey`** — the saved `{ y, h }` for one history entry and the token that names it (`scroll-memory.js`). Anything calling `history.replaceState` on `index.html` must pass `history.state` back through rather than `null`, or the token is lost.
- **Item shape**: `{ series, productId, name, category, metal, size, price, image }` (see `selection.js` above).

## `js/series-page.js` (~65 lines)

`series.html` only. Resolves the slug via `EmjiveSeries.requestedSlug()` — deliberately **not** the fallback-applying `.slug` — loads that series' manifest, fills in the title/year/subtitle, and otherwise shows a not-found state. Rendering `manifest.json`'s `sections[]` belongs here later; the page is an empty shell by design.
