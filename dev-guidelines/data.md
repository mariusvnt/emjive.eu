# Data

Three kinds of file, all fetched client-side (no backend, no server-side templating), all hand-formatted with aligned columns — see the "how it's written" note at the end before running any formatter over them.

- **`data/series.json`** — the index. Brand-wide settings plus one entry per series.
- **`data/series/<slug>/products.json`** — that series' catalog.
- **`data/series/<slug>/manifest.json`** — that series' design manifest.

There is no global `data/products.json` any more; it split into the three above.

**Every path inside these files is repo-root-relative with no leading slash** (`assets/series/bones/...`, `series/bones/hero.css`). That resolves correctly *only* because every HTML page sits at the repo root — the fetches are relative to the page, and `vite.config.js` sets `base: "/"`. A page in a subdirectory would silently break all of them.

**`npm run validate-data` (`scripts/validate-data.js`) checks all of this** — field types, the cross-references below (featured slug, hdri/category/metal keys, ids unique within a series, a product's `designs` — below), and that every path exists with its exact on-disk case. It runs in CI before every deploy; run it after hand-editing or after `json-tool`.

## `data/series.json` — top-level schema

| Field | Type | Purpose |
|---|---|---|
| `featured` | `string` | Which series' slug the homepage shows. **This one field is how you switch the featured series**; nothing else needs touching. |
| `metals` | `string[]` | Source of truth for valid metal keys, used throughout `assets.icons`, `assets.fallback-img`, `per-metal-specs`, `assets.top-shot`, and `default-metal`. Global rather than per-series because it must stay in sync with `METAL_PRESETS` in `js/three-viewer.js` (see `client-scripts.md`), which is module-scope and series-unaware. |
| `metal-costs` | `{ [metal]: { "density-g-cm3": number, "price-per-g": number, "production-per-cm3": number } }` | The constants behind the product page's weight and cost rows, one entry per `metals` key (`validate-data` enforces both directions). With V = the product's `geometry["volume-cm3"]`: weight = V × density, raw materials = weight × price per gram, production cost = V × `production-per-cm3`, manufacturing = production − raw materials. `validate-data` also rejects an entry whose `production-per-cm3` is below its own raw-material cost per cm³ (manufacturing would go negative). Currency is €, like every price on the site. |
| `metal-technology` | `{ [metal]: string }` | Which printing technology (a key of `printing-technologies`) makes each metal — steel `binder-jetting`, silver and bronze `lost-wax`. `validate-data` checks every metal has one and every one resolves. |
| `printing-technologies` | `{ [key]: { name: string, description: string } }` | The product page's "Printing technology" row: the chosen metal's technology name and a sentence on what it is. |
| `categories` | `{ [id]: { sizes: string[], unit: string } }` | The brand's full category vocabulary, and the one place sizing is declared. `unit` labels the one size field both size sheets have — "Custom size" on `product.html`'s Select sheet and in the Modify sheet (e.g. `"mm"` for ring) — and an empty `unit` ⇒ the product page's "Select" button disables itself ("No sizes available"). `sizes` is **no longer read by the UI**: the standard-size list it used to fill was removed, and the typed field is now the only way to give a size. It stays in the schema (and in `json-tool`'s Global tab) rather than being deleted in the same change. Replaces the old parallel `sizesByCategory` + `sizeUnits` maps, which had to be kept in sync with each other by hand. The optional `size-guide` (`{ how: string[], head: string[], rows: string[][] }` — `how` the paragraphs on measuring, at least one, `head` the names of the columns, `rows` one row per size as wide as `head`, checked by `validate-data`) is what the size finder's "No" / "Use a different method" screen shows (`js/size-finder.js`, through `EmjiveSelection.fillSizeGuide`; the finder is opened by the "Find my size" buttons on the product page's specs stage and in both size sheets): the paragraphs, then the table turned so each of `head` is a row and each size a column. The ring's table is `EU size` and `US size` only — it used to have a diameter row, but measuring on screen is now the finder's other path. |
| `hdris` | `{ [key]: string }` | Name → HDRI path map, the vocabulary each series' own `hdri` field (below) picks from. `js/three-viewer.js` never reads this directly — a caller (`js/series.js`'s `hdriPath()`, or `scripts/auto-render.js`'s own resolution) looks up the key and passes the resolved path as `options.hdri`; an omitted/unresolved key falls back to `three-viewer.js`'s own `DEFAULT_HDRI_SRC`. |
| `swatch-hdri` | `string` | Which `hdris` key the metal swatches are lit with — their own choice, separate from any series' `hdri`; `scripts/validate-data.js` checks it is a key. Tuned via `scene-tool.html`'s swatch mode (the HDRI dropdown; "HDRI" tick + Save). |
| `swatch-blur` | `number` | A gaussian blur of that HDRI for the swatches, its sigma in **pixels of the HDRI image** (so a 2k HDRI is blurred half as far, in angle, as a 1k one): 0 or more, `3` today; products' HDRIs are never blurred (`loadEnvironment`'s `blurPx`, `client-scripts.md`). Tool: the Blur slider and field (changing it rebuilds the viewer), saved with the HDRI tick. |
| `swatch-camera` | `{ rotation: number, tilt: number, roll: number }` | Where the swatch camera stands round the sphere, in degrees — the product cameras' three (`rotation`, `tilt` with 90 = eye level, `roll`); `{ 0, 90, 0 }` is straight in front. The distance and fov are solved (the frame is the biggest square inside the sphere's disc: `swatchOrbit` in `js/three-viewer.js`, see the `options.swatch` entry in `client-scripts.md`). Tool: a slider and a field each; "Camera" tick + Save. A missing or malformed block renders with the default (`scripts/auto-render.js` warns); `validate-data.js` checks its shape. Replaced `swatch-light` (a point light's position, strength and falloff and a uniform environment's strength — the three-sphere design), before that `swatch-hdri`/`swatch-rotation` (the tube design) |
| `series` | `Series[]` | Every series across the brand's lifetime. Drives the archives page. |

### Series entry schema

| Field | Type | Purpose |
|---|---|---|
| `slug` | `string` | URL identity — `/gallery?series=<slug>`, `/series?series=<slug>` (items don't carry it: `/<item-slug>` is unique across series, see below). |
| `name`, `year` | `string` | Display name and vintage. |
| `categories` | `string[]` | **A subset of the top-level `categories` keys**, in the order the header's filter row should show them. Each series declares its own, because the available categories genuinely differ between collections. Nothing enforces the subset relationship at runtime, but `scripts/auto-render.js` warns about violations (see `tooling.md`). |
| `products` | `string` | Path to this series' `products.json`. |
| `hdri` | `string` | Which top-level `hdris` key this series renders under — resolved to a path via `js/series.js`'s `hdriPath()` and passed as `options.hdri` to every `window.EmjiveModelViewer(...)` call `js/gallery-stack.js`/`js/product.js`/`js/modify-modal.js` make for this series' products (and to the stack's shared scene, `js/stack-scene.js`, for all of them). `scripts/auto-render.js` mirrors the same resolution for its icon/fallback-img/top-shot renders. `scripts/auto-render.js`'s `warnHdriDrift()` warns if a series declares a key the top-level `hdris` map doesn't have. |
| `manifest` | `string` | Path to this series' `manifest.json`, rendered by `series.html`. |
| `hero` | `{ fragment, css, js, preload[] }` | This series' hero bundle — see `pages.md`. `preload` lists image **originals** (repo-root-relative) to preload: the first is the hero picture the first paint is made of (preloaded as its low-res version for the viewport, high priority — it needs the full four-version set), the rest are layers that start hidden (preloaded low priority, smartphone/desktop high-res version only). The build also emits the first entry's preload, and the fragment/CSS/JS/`products.json` ones, into `index.html`'s `<head>` for the featured series. `validate-data.js` checks the versions exist. |

## `data/series/<slug>/products.json`

`{ "series": "<slug>", "products": Product[] }` — the `series` field is self-identifying, a cheap cross-check if a file ever gets copied to a new folder and half-edited.

Currently one series: **Bones** (`data/series/bones/products.json`), 9 entries with ids `01`–`09` in catalog order (furcula, foramen, Disc, Marrow, suture, cartilage, rib-cage, joint, omoplates), all category `"ring"`. Three of them carry several **designs** (foramen, rib-cage, omoplates — see `designs` below); the ids were renumbered when the former `omoplates-unified`/`omoplates-dual` and `rib-cage`/`rib-cage-extended` pairs were merged into one product each, which is why `js/selection.js`'s stored carts are version 2 (an older cart's ids would point at other items).

## `data/series/<slug>/manifest.json`

`{ series, title, subtitle, year, intro, sections[], credits[] }`. Rendered by `series.html` via `js/series-page.js` — but **only `title`/`year`/`subtitle` are read today**; the page is otherwise an empty shell awaiting its design. The intended `sections[]` entry shape is `{ id, heading, body: string[], media: [{ type, src, alt, caption }] }`, documented here ahead of anything rendering it.

## Product object schema

Top-level field order: `id, name, category, description, default-metal, per-metal-specs, geometry, hero-hand-visibility, 3d-viewer-camera-default, assets, designs`. `assets` itself is ordered `model, wireframe, icons, fallback-img, xray, top-shot, photos` (`wireframe` optional); `designs` is optional and follows `assets`.

- **`id`** (`string`) — e.g. `"01"`. **Unique within one series' file, not globally** — every series starts over at `"01"`. No longer part of the product's URL (that is `/<slug>`, below); kept as the anchor `scripts/auto-render.js` scopes its text-patching to (see `tooling.md`) and for the old `product.html?id=...` links, which resolve against the active series first, then scan the others — see `client-scripts.md`.
- **`name`'s address** — the product's page is `https://emjive.eu/<slug>`, where the slug is `name` lower-cased with every run of other characters turned into `-` (`Furcula` → `furcula`; `scripts/slugs.js`). So **a name is also an address**: it must be unique across **all** series (not just its own) and must not equal a page or a top-level file/folder (`gallery`, `archives`, `terms`, `series`, `launch-order`, `creation-process`, `product`, `index`, `404`, `assets`, `js`, `css`, `data`…); `npm run validate-data` fails otherwise. Renaming a product changes its address (the old one 404s).
- **`name`** (`string`) — display name; also the basis for auto-render's generated filenames (lowercased, spaces→hyphens).
- **`category`** (`string`) — should be one of the categories its own series declares, which in turn must be a key of the global `categories` vocabulary. Looks up that category's `unit` for the size field. A product in a category its series doesn't declare still renders in the unfiltered grid, but no filter button can reach it — `auto-render.js` warns about this.
- **`description`** (`string`) — shown on the product detail page only. Empty string falls back to "No description yet." in `js/product.js`.
- **`default-metal`** (`string`) — singular. Picks which of `assets.icons`/`per-metal-specs` the *homepage* gallery defaults to (no picker there; the grid's Select sheet opens on it), and which metal's `assets.top-shot`/`assets.xray` gets used wherever a single, unpicked variant is needed (the hero ring overlay, the product carousel backdrop). The product page separately defaults its own picker to this value but lets the visitor change it.
- **`per-metal-specs`** (`{ [metal]: { price: number } }`) — the per-metal selling price, shown in the product page's label bar and carried into the selection/order. `price: 0` renders as "TBD". The Characteristics section no longer reads it: it shows weight, size and a production-cost breakdown instead (see `geometry` and the top-level `metal-costs`), and the old hand-typed `weight`/`composition` strings are gone.
- **`geometry`** (`{ "volume-cm3": number, "dimensions-mm": [number, number, number], "min-box": { "center": [x, y, z], "axes": [[x, y, z] × 3] }, "model-sha1": string }`) — **generated, never hand-edited**: `npm run measure-models` (`scripts/measure-models.js`) measures `assets.model` and writes this one line into the product's block. `volume-cm3` is the enclosed mesh volume (the models are authored in millimetres, 1 unit = 1 mm, so cm³ = mm³ / 1000); `dimensions-mm` is the extents of the **minimum-volume bounding box**, longest first (pose-independent, so a model's baked-in rotation doesn't change it, and the axes aren't tied to the viewer's x/y/z); `min-box` is that box's pose — its centre (mm) and three unit axes, in the model's scene frame, in the same order as `dimensions-mm` — which the specs stage's box (and its dimension labels) is drawn on (`validate-data` checks the axes are unit length and orthogonal); `model-sha1` is the hash of the `.glb`'s bytes. Required on every product, and `validate-data` fails when the hash no longer matches the file (a replaced or re-optimized model), pointing back at `measure-models`. Metal-independent on purpose: the per-metal weight and costs are derived on the page from this plus `metal-costs`, so nothing per-metal is stored that could go stale. A mesh that isn't watertight still gets a volume, but an approximate one (the script flags it; today six of rib-cage's ten designs: 1L2L3, 123, 23, 2L3, 13, 3 — their volumes and so their costs are approximate). A product with `designs` has this on each non-default design too (inside the design's own entry, below); the product-level `geometry` is the default design's.
- **`hero-hand-visibility`** (`{ visible: boolean, x: number, y: number, scale: number, rotation: number }`) — controls whether and how this product's `assets.top-shot[metal]` image is overlaid on the homepage hero's x-ray hand. `visible` gates whether the hero bundle's `updateHeroRings()` creates a `.reveal__ring` `<img>` for this product at all — any number of products can have this `true` at once, each getting its own independently-positioned image. `x`/`y` are that image's center as a % of the hand image's own width/height (not the viewport); `scale` is its width as a % of the hand image's width; `rotation` is in degrees. All four are set inline per-image from this data (the `--ring-x`/`--ring-y`/`--ring-size`/`--ring-rotation` values in `series/<slug>/hero.css` are only the pre-JS fallbacks). This is hero art, so it deliberately ignores the header's category filter. See `pages.md`/`styling.md` for the reveal/positioning mechanics these feed into. The same rings are what the gallery's stack takes off the hand: `hero.js` tags each ring `data-product-id`/`data-rotation`, and `js/gallery-stack.js` flies the product from exactly that spot, size and rotation (its top shot crossing into the model) to its place in the stack. Products with `visible: false` rise with the wave instead.
- **`3d-viewer-camera-default`** (`{ rotation: number, tilt: number, zoom: number, roll?: number }`) — default/reset camera framing, parsed by `js/three-viewer.js`'s `parseOrbitConfig()` (see `client-scripts.md`). `rotation` spins left/right, `tilt` is up/down (90 = eye-level), `zoom` is radius as a % of the distance that exactly frames the model's bounding sphere, `roll` spins the camera around its own view axis (0/omitted = level — the overwhelmingly common case, and what every product predating this field implicitly has). Also inherited (`zoom` only — `rotation` and `roll` both forced to 0) by auto-render's top-shot renderer, which wants a canonical top-down framing regardless of a product's own default rotation, and for the same reason doesn't inherit roll either. Set by hand, or via `scene-tool.html` (`npm run scene-tool`) — drag the model (or type exact rotation/tilt/zoom/roll values), tick "Camera," and save writes straight into this field. Same tool also handles the swatch renderer's one setting, `swatch-light` (a top-level field, above — swatches aren't tied to a product).
- **`assets.model`** (`string`) — `.glb`/`.gltf` path. Empty string → falls back to `assets.icons[metal]` instead of a 3D viewer. For a product with `designs` this is the **default design's** model.
- **`assets.wireframe`** (`string`, optional) — `.glb` path of the model's wireframe, drawn over it in the product page's specs stage (`client-scripts.md`'s `options.blueprint`). Missing or empty → the specs stage shows just the grey model and its box. Written by `npm run split-models` from the wireframes export (`tooling.md`); no `json-tool` upload slot, the tool carries it through a rewrite and moves it with the folder; `validate-data` checks the path exists. The file lives beside the model as `<slug>_wireframe.glb` and is authored in the model's own frame (`assets.md`). Not covered by `geometry.model-sha1`: replacing it needs no `measure-models`.
- **`assets.icons`** (`{ [metal]: string }`) — one 512×512 transparent WebP path per metal, every metal (not just the default) — the metal picker swaps this live. A flat, tightly-cropped/re-centered thumbnail (see `tooling.md`'s `normalizeIconFraming`) used for the product page's label thumbnail, the cart/order-page line-item snapshot (the selection bar's icons and every order/drawer row), the homepage card's fallback when `model` is empty, and the carousel's fallback slide for a model-less product (on the product page's design stage and in the Modify sheet). **Not** used as the 3D viewer's pre-load poster any more — see `fallback-img` below. The selection bar's 36px icons and the order rows' 48px thumbnails show a generated 128px sibling instead (`<name>_icon_<metal>_128.webp`, found by name, not listed here; `npm run image-variants` / `auto-render` write it, `validate-data.js` requires it).
- **`assets.fallback-img`** (`{ [metal]: string }`) — one 512×512 transparent WebP path per metal, same shape as `icons`. This IS the 3D viewer's `.emjive-3d-viewer__poster` overlay (shown until the model's first frame renders), and — for the same pixel-for-pixel reason — what the homepage card and the Modify sheet show *before* a viewer exists at all (the sheet opens on it and builds the viewer only once it has slid in; see `client-scripts.md`), and what the sheet falls back to if no viewer can be built. Captured by `scripts/auto-render.js` from the exact same screenshot `icons` is derived from, but saved as-is (no crop/re-center/pad) — so it holds the model's real `3d-viewer-camera-default` framing pixel-for-pixel and the poster→model handoff shows no jump, unlike `icons`' tighter, re-centered crop.
- **`assets.xray`** (`string`) — single path, the design stage's backdrop image (behind the model). Empty string hides it. This is the **original** (desktop high-res); the page shows three other versions of it chosen for the viewport, found by name, not listed here: `<name>_lo.webp` (desktop low), `<name>_m.webp` (smartphone high, cropped to the middle 0.85 of the width — `PHONE_CROP.xray` in `scripts/make-image-variants.js`, `--xray-crop` in `css/style.css`) and `<name>_m_lo.webp` (smartphone low). `npm run image-variants` writes them and `validate-data.js` fails the build if one is missing — see `assets.md`.
- **`assets.top-shot`** (`{ [metal]: string }`) — one 1024×1024 WebP per metal, straight-down camera, lit with the same studio HDRI every other render uses, with an invisible "finger" occluder plane baked into the render so the ring's own hidden-from-above geometry (the far side of a gap in the shank, the inner wall of the hole) doesn't show through once composited over a hand (see `tooling.md`'s `scripts/auto-render.js` section). Generated by `scripts/auto-render.js`, populated for all 9 current products (a design has none: it is only the product's own). Read by the active series' hero bundle (`series/<slug>/hero.js`'s `updateHeroRings()`) — see `hero-hand-visibility` above.
- **`assets.photos`** (`{ src: string, description: string }[]`) — the photography shown in the product page's inspiration stage, one under the other (the carousel it used to feed is gone from the page). Empty array → that stage is the description alone. `description` is the **name of the item on the photo**, written as an item's name is everywhere (`Furcula.ring.steel.62`): the caption in the photo's bottom-right corner sets the part before the first dot in the main face and the rest (`.category.metal.size`) smaller in the mono face (`client-scripts.md`'s `captionFor()`), and no description means no caption. Editable per-photo via `npm run json-tool`, which also owns `src` (upload/replace/remove) same as before. The Modify sheet no longer shows photos: for a product that has some it offers a "See photos" button to the page.

- **`designs`** (optional; `{ default, options[], list[] }`) — a product with several designs: variants of the same item (a different shape, parts added or taken away) chosen in the product page's design stage. **The product's own fields are the default design** — `model`, `wireframe`, `icons`, `fallback-img`, `geometry`, and the `name`, camera, prices and the rest are the product's — so the homepage stack and hero, the grid, the sitemap and the item page's address need no change. `options` are what the page offers: `{ key, label, multiple?, choices[] }` (`multiple` = a set of toggles, the last one on can't be turned off; otherwise one choice of several). `list` has one entry per design: `{ key, name, picks, [geometry, model, wireframe, icons, fallback-img] }`. `picks` maps each option key to its choice (a list for a `multiple` option); **every design is a combination of picks**, unique across the list, and the page lands on the design whose picks match what the visitor has chosen — or, when a combination has no design (a link between ribs that aren't side by side), a choice of a `multiple` option goes to the design that keeps that pick and as many of the others as it can, while the choice of a plain option is disabled and does nothing. `name` is the design's name as the model file calls it (`rib-cage-1L2`); the page's label shows the product's name followed by what the design adds to it (`rib-cage` + `-1L2`), and a design's `name` doubles as how `split-models` finds its node. The **default design has only `key`, `name` and `picks`** (its assets are the product's); every other entry carries its own `model`, `icons`, `fallback-img` and `geometry` (written by `measure-models`), and `wireframe` (optional, never inherited — none means the specs stage shows the grey model without bars). No top-shot, x-ray or photos per design. File names follow `<product slug>-<design key lower-cased>_…` (`rib-cage-1l2_gltf.glb`, `rib-cage-1l2_icon_steel.webp`, `foramen-straight_wireframe.glb`), never colliding with the product's own `<slug>_…` files. Entries use `key`, never `id`, because `scripts/auto-render.js` slices product blocks on `"id":`. Today: **foramen** (`shape`: straight | twisted; default twisted), **rib-cage** (`ribs` 1/2/3, multiple, and `bound` linked | unlinked; ten designs — 1L2L3 (default), 123, 12, 1L2, 23, 2L3, 13, 1, 2, 3; a lone rib and 13 are `unlinked` only) and **omoplates** (`blades`: unified | dual; default unified). `validate-data` checks the block (schema with `additionalProperties: false`; the default exists and has no assets of its own, the others have theirs with the `_128` icon thumbnails, picks name real options and choices and are unique, keys and names are unique, paths exist with exact case, each design's `model-sha1` matches its file). `js/series.js`'s `resolveDesign(product, key)` is how the pages read one.

## How it's written

Directly in a text editor, via `npm run json-tool` (`http://localhost:5201/` — a form covering global parameters plus adding/editing/removing a series or product, see `tooling.md`), or patched by `scripts/auto-render.js` for `assets.icons`/`assets.fallback-img`/`assets.top-shot` (and a design's `icons`/`fallback-img`) specifically, and by `scripts/measure-models.js` for each product's and design's `geometry` line. All of them ultimately produce the same text-surgery shape rather than a `JSON.stringify` round-trip (see `tooling.md` for why: it preserves the hand-aligned column formatting, which a full re-serialize would flatten) — `json-tool` regenerates a whole product/series block on any edit (canonical spacing, not necessarily byte-identical to what was there), but never touches a field it wasn't given (it carries `geometry` and the whole `designs` block through unchanged — a design is hand-authored, with no editing UI), and never `assets.icons`/`assets.fallback-img`/`assets.top-shot` under any circumstance. **Don't run a formatter/prettify pass on these files** — they'll survive structurally but lose that alignment.
