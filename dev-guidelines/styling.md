## Responsive type scale (`--text-scale`, `:root` line 85 + the `min-width: 641px` override at lines 108–112)

Phones (the tuned, priority baseline) stay at `1`; past the site's one existing breakpoint, `--text-scale` becomes `1.2` and every `font-size` in the file — every one is written as `calc(<value> * var(--text-scale))`, or references `--button-font-size` which already is — grows 20%. Add any new `font-size` declaration the same way, or it'll silently stay fixed on desktop while everything around it grows.

**Deliberately not a root `font-size` bump.** `rem` is used throughout for spacing/sizing that must *not* scale with text — gaps, indicator dots, icon boxes (`--edge-px`, the various `0.25rem`/`0.3rem` selected-dot recipes, etc.). Scaling the root element's own font-size would have dragged all of that along with it. The multiplier lives in its own token instead, read only at each actual `font-size` declaration.

One coupling this created, load-bearing:

- **`--caption-h`** (`.product-carousel-frame`, line ~1765) is scaled in lockstep with `.product-carousel__caption`'s own font-size (line ~1898) — that caption box is `overflow: hidden` with `line-height: 1`, sized to exactly fit its text, so the two must grow together or the enlarged caption gets clipped.

`em`-sized text (`.product-card__label-type`, `.size-fraction`, `.product-detail__label-type`) is left as plain `em`, not double-wrapped — it already inherits the scale for free from its already-scaled ancestor; multiplying again would have made it 44% bigger instead of 20%.

## `@font-face` (lines 136–181) — Geist Mono + three DINish weights

Both typefaces are self-hosted now — neither is pulled from Google Fonts at runtime. Geist Mono (lines 136–151, SIL OFL, by Vercel) used to come in via a `<link rel="stylesheet">` to `fonts.googleapis.com`, which cost every page two extra third-party DNS+TLS handshakes plus a render-blocking stylesheet before any pixel could paint, for all of 37KB of font; it's two `@font-face` blocks (lines 136, 144), one per `latin`/`latin-ext` unicode-range subset, both resolving to the same variable-font file (weights 400–500) since only the `unicode-range` differs between them. DINish (lines 153–181) registers three weights — Regular (400, line 160), Bold (700, line 167), and Black (900, line 176, driven by `--button-font-weight` — see the design tokens table above). Bold currently has no selector actually rendering at `font-weight: 700` (it used to be justified by `.reveal__scan-hint`'s "SCROLL TO SCAN" hint, since removed — see "Entry reveal" below and `client-scripts.md`) — left registered rather than deleted, since dropping a font file is a separate call from the doc-sync pass that noticed this. Regular's `src` used to have a trailing-comma syntax error (`format("woff2"),;`) that could make browsers drop the whole declaration, silently falling back to sans-serif even with the font file present at exactly the right path — fixed; if `--font-main` text ever looks like fallback sans-serif again, that bug class is exactly where to look first (see `assets.md`/`procedures.md` for where the font files live).

## `series/bones/hero.css` (~250 lines) — the Bones hero

Not part of `css/style.css` at all: it's injected as a `<link>` at runtime by `js/series.js`, so it lands *after* the shared stylesheet and wins on ties. It carries the whole "Entry reveal" block plus the `:root` tokens only it needs: `--reveal-pin-height`, `--reveal-xray-opacity`, and the three that make the **smartphone crop** work — `--hero-aspect` (width ÷ height of every hero picture: `.reveal__img`, `.reveal__xray-group` and the `.reveal__extension` panels all size from it, so the layers stay exactly on top of one another; `calc(3840 / 2160)` on desktop, `calc(1536 / 2160)` on a phone), `--hero-crop` (the share of the full width that is left: `1`, or `0.4`) and `--hero-crop-left` (where it starts, as a % of the full width: `0%`, or `30%`). The phone values are set in one `@media (max-width: 640px) and (max-aspect-ratio: 3/5)` block, the query `js/loader.js` uses to pick the cropped files; the two numbers are `PHONE_CROP.hero` in `scripts/make-image-variants.js` and `validate-data.js` fails the build if they differ. A phone's high-res version is at most the 1536×2160 middle of the 3840×2160 art; the desktop one is the original. The DOM/CSS "SCROLL TO SCAN" hint that used to live here — `.reveal__scan-hint` — is gone; that text is baked into `hand-rings-under-flesh_3k.webp` itself now (see `assets.md`).

**Path gotcha, and it's the easy one to get wrong**: `url()` in a bundle stylesheet resolves against **the CSS file** (`../../assets/...`), while the image paths in the bundle's `hero.html` fragment (`data-full`, which `js/series.js` turns into the `<img src>`) resolve against **the page**, since the element is cloned into the live document. Two conventions, one folder. `hero.css` happens to need no `url()` at all today — every hero image is a real `<img>` — but a future series' bundle will hit this.

### `.reveal__ring` (hero.css lines 55–58 for the `--ring-*` fallbacks, 188 for the rule itself) — ring-on-hand overlay

`.reveal__ring` positions a product's top-shot image on the x-ray hand: `left`/`top` from `--ring-x`/`--ring-y` (a % of the hand image's own width/height), `width` from `--ring-size` (a % of the same) — **re-expressed against the cropped picture on a phone**: `left: calc((var(--ring-x) - var(--hero-crop-left)) / var(--hero-crop))` and `width: calc(var(--ring-size) / var(--hero-crop))` (`top` is untouched, the crop is of the width only), which leave the desktop values as they were (crop 1, left 0%), so `hero-hand-visibility` in `products.json` stays in terms of the full picture, `transform: translate(-50%,-50%) rotate(--ring-rotation)` to center on that point then spin in place. The four `--ring-*` custom properties declared on `.reveal` are fallback values only, inherited if nothing more specific overrides them — the bundle's own `updateHeroRings()` sets all four inline, per `<img class="reveal__ring">` it creates, straight from that product's `hero-hand-visibility` object (see `data.md`), so several rings on screen at once each get their own values instead of fighting over one shared set. There's no `<img>` for this in the markup at all — every one is created and inserted into `#revealXrayGroup` by that same function, one per product with `hero-hand-visibility.visible: true` (zero, one, or several).

## Shared 3D viewer (`.emjive-3d-viewer`, lines 294–356)

The wrapper `js/three-viewer.js`'s `buildThreeViewer()` returns as `el` — see `client-scripts.md`. `.emjive-3d-viewer` itself just sets `position:relative` (so the poster/nudge-hand overlays below can be absolutely positioned against it) plus `touch-action:none; cursor:grab;`. `.emjive-3d-viewer__canvas` fills it at `width/height:100%` — the module's own `ResizeObserver` keeps the renderer's pixel buffer matched to whatever size this resolves to, so there's no `object-fit`/cover-vs-contain concept needed here the way the old `<model-viewer>` tag selectors used (both real contexts, the grid card and the carousel slide, are always square anyway). `.emjive-3d-viewer__poster` (sourced from `assets.fallback-img`, not `assets.icons` — see `data.md`) and `.emjive-3d-viewer__nudge-hand` are both `position:absolute` overlays — the poster fades out via JS once the model's first frame has rendered, the nudge hand's position/opacity are driven per-frame from JS during the idle-nudge hint (only the opacity gets a CSS transition; position is hard-set every frame to stay in sync with the 3D camera nudge — see `client-scripts.md`). `.emjive-3d-viewer__nudge-hand` itself is a plain `<div>`, not an `<img>` — it paints no fill/border of its own; see technique #9 below.

Per-context sizing of the wrapper itself lives with each context instead (`.product-card__figure .emjive-3d-viewer`, `.product-carousel__slide .emjive-3d-viewer`, `.product-carousel__slide--model .emjive-3d-viewer` at `75%` of the tile, `66%` under `max-width: 640px`) — same pattern the old `model-viewer`-tag selectors used, just retargeted at this class. The model slide's viewer stays deliberately smaller than its tile at both sizes: `js/carousel.js`'s `onPointerDown` bails out of carousel paging whenever a pointerdown lands inside `.emjive-3d-viewer` (so the drag rotates the model instead), and there's no arrow/dot/keyboard nav, so the empty margin around the viewer is the only place a drag or swipe can start from to page off a model slide. At 100% there'd be none.

## `html.emjive-restoring-scroll` — the back-navigation restore window

Added to `<html>` (with `--emjive-restore-height` set inline alongside it) by `js/scroll-memory.js` from `index.html`'s `<head>`, *before `<body>` is parsed*, and removed again once the real content has grown past the reservation. Nothing here survives into the settled page. Four decisions in it that look arbitrary and aren't:

- **`min-height` goes on `body`, never on `html`.** `html` keeps its own `background: var(--bg)` painting the reserved region, so the visitor looks at the site's background at the right offset rather than a white void. Putting the reservation on `html` instead would drag `html`'s `scrollHeight` around — and that is the exact number `scroll-memory.js` measures to decide when the real content has caught up.
- **`overflow-anchor: none`**, because the hero grows `100svh → 200vh` *above* the restored position once its bundle lands. Scroll anchoring's whole job is to shift the offset to keep content visually still through that kind of insertion; correct in general, wrong here, where the saved absolute offset is the thing being preserved.
- **`visibility: hidden` on `.product-grid`, not `display: none`.** The cards stay laid out, so `IntersectionObserver` still fires and `loading="lazy"` placeholders still fetch — `js/main.js`'s lazy 3D viewers keep building underneath on schedule. They're hidden only so the grid is revealed with its on-screen cards already decoded instead of as a row of empty boxes.
- **It is not a page-wide paint hold.** The background, the reserved height and the hero all paint at the restored offset throughout; only the grid waits, and only briefly.

See `client-scripts.md` for the rest of the mechanism, including why `html { scroll-behavior: smooth }` has to be overridden inline around the programmatic scroll.

## Base-rule gotchas worth knowing before touching layout

- `html { overflow-x: hidden; }` — forbids horizontal scroll, since a horizontal scrollbar would eat into the usable viewport the fixed `.selection-bar`'s `left:0; right:0` is measured against, and the site's many `100vw` breakouts (`.product-card__bar-link`, the hero images, the carousel frame, `.product-detail__label-bar`) would toggle one on and off at the slightest sub-pixel overflow. No vertical scrollbar space is reserved: an earlier `scrollbar-gutter: stable both-edges` was removed so `50vw`-based sizes like the phone `.product-card__figure` match the real layout width on engines that reserved the gutter (Chrome for Android did, even with only an overlay scrollbar). The accepted trade-off: on desktop browsers with classic scrollbars, the selection bar can shift a few px between pages that scroll and pages that don't. If a `100vw` breakout shows a gap on one edge and a hair of scrollable overflow on the other, check `.product-card`'s own `min-width: 0` first — technique #7 below.
- `html`/`body { overscroll-behavior-x: none; }` — a separate concern from the `overflow-x: hidden` above: that stops actual horizontal scrolling, but browsers still show a rubber-band bounce for a left/right drag at the document edge regardless of whether there's anything to scroll to (narrow screens make that gesture easy to trigger by accident). Vertical overscroll bounce is deliberately left alone — scoped to `-x` only.
- `body:has(.selection-bar) { padding-bottom: var(--selection-bar-height); }` — `:has()` auto-scopes the bottom-padding reservation to only the pages that actually render the bar (not `launch-order.html`). The product page's glass Select bar adds to that (`body:has(.product-select-bar:not([hidden])) { padding-bottom: calc(var(--selection-bar-height) + var(--select-bar-height)) }`, declared after the rule above so it wins). `launch-order.html` has its own equivalent instead — `body:has(.order-checkout-bar:not([hidden]))` — for its own fixed checkout bar, same mechanism, just scoped to a `[hidden]` toggle rather than the bar's mere presence, since `launch-order.html` always renders the element but only sometimes shows it (nothing selected ⇒ nothing to check out).
- **`[hidden]` loses to any explicit `display`.** The UA stylesheet's `[hidden] { display: none }` is beaten by a rule that sets `display` itself, so hiding such an element via the `hidden` attribute silently does nothing without a matching `[hidden]` rule. Several places in this file exist purely for that: `.product-card[hidden]` (the header's category filter hides cards this way — see below), `.product-card__figure > img[hidden]` (the base `img { display: block }` rule is what beats it here — `js/main.js`'s `buildViewerFor`/`disposeViewerFor` toggle it as a grid card's 3D viewer takes over from/hands back to its icon; missing this rule was a real, shipped bug — the "hidden" icon stayed laid out and pointer-interactive on top of the canvas, silently swallowing every drag meant for the model, found via a headless drag simulation rather than by eye), `.selection-bar__icons[hidden]`, `.selection-bar__order`, `.site-header__filter[hidden]` (`js/main.js` hides the row only when the active series has zero categories — a single category renders as a lone, permanently-dotted tag instead, and every non-grid page always shows a "Gallery" link regardless of count; see the Header row in the section map above), and — since the order-page rebuild — `.selection-empty[hidden]`/`.selection-list[hidden]` (both `display: flex` now, for the centered empty state and the section-to-section `gap` rhythm respectively). If you add a `display:` to a block that JS ever hides, add its `[hidden]` companion in the same edit.
- **The category filter hides cards, it never re-renders them.** `js/main.js` builds every `.product-card` once and toggles `hidden`. Rebuilding the grid per toggle would destroy and recreate every three.js `WebGLRenderer`. Keep any future filter/sort work on the same "hide, don't rebuild" footing.
- **`.product-card__figure` is a single-cell grid, and that is load-bearing.** Every child is placed in the same cell (`grid-area: 1 / 1`) so the card's placeholder image and its live 3D viewer **overlap** instead of following each other in normal flow. It used to be a plain block, which only worked because exactly one of the two was ever in the layout at a time — `buildViewerFor` hid the icon the instant the viewer was appended. That stopped being true once the viewer was mounted over the icon for the whole load (both are present until `revealViewer()` swaps them in the same frame): as in-flow blocks each sized to the full content box, the viewer was pushed entirely *below* the placeholder, with the model clipped away by `overflow: hidden` and a band of bare canvas poking out through the figure's own bottom padding. If you add a third child here, give it the same `grid-area: 1 / 1`; paint order is DOM order, which is why the viewer (appended last) sits on top.
- **A card's own 3D viewer is now built/disposed lazily** as it scrolls in and out of range (`js/main.js`'s `buildViewerFor`/`disposeViewerFor`, `js/three-viewer.js`'s strengthened `dispose()` — see `client-scripts.md`), not once for the whole grid up front. Past the browser's per-page WebGL context budget the viewer returns `null` and that card just keeps showing its icon — retried next time it scrolls back into range, not permanent. Added after eagerly building every product's viewer at page load stopped being safe once the catalog grew past a handful of products — real devices crashed outright, not just ran slowly.

## Liquid glass (`.glass`, lines 1375–1452; `.product-select-bar`, 2088–2150)

One shared recipe for the site's glass bars — `.order-checkout-bar` (launch-order) and `.product-select-bar` (product page) — driven by `js/liquid-glass.js` (see `client-scripts.md` for the SVG-filter and clone mechanics). A new glass element is `class="glass" data-glass` plus its own layout rules; nothing else in the stylesheet needs touching.

- **Three layers of look, whatever the browser.** (1) The *bend*: the script adds `.is-glass-backdrop` (Chromium: `backdrop-filter: blur(var(--glass-frost)) var(--glass-url) saturate(var(--glass-saturate))`, the filter's URL arriving as the `--glass-url` custom property) or `.is-glass-clone` (Safari/Firefox: `backdrop-filter: none`, and a `.glass__layer` page copy carries `filter: var(--glass-url)` instead). (2) The *frost, tint and rim light*, in `.glass::before` above the bend: a directional glare, a faint white tint (`rgba(255,255,255,.16 → .05)`) and three inset box-shadows (bright 1px top edge, dim bottom, hairline all round) — an inset shadow can't live on `.glass` itself, because the clone layer at `z-index: -1` would paint over it. The outer `0 -8px 30px` drop shadow stays on the element. (3) The *fallback*: until the script has run, and for good under `prefers-reduced-transparency` or on failure, plain `blur(24px) saturate(200%)` on the element — the look the bars had before the bend existed.
- **`isolation: isolate`** makes `.glass` its own stacking context, which is what lets `.glass__layer` sit at `z-index: -1` — above the element's background, below its content. Content that has to paint above `::before` must be positioned (`.order-checkout-bar__row` is `position: relative` for exactly this; `.product-select-bar__button` already was).
- **Clone layers.** `.glass__layer` (the glass's size and shape — `inset: 0; overflow: hidden; border-radius: inherit`) carries the bend; the `.glass__pane` inside it is the same plus a bleed all round (set inline by the script, `frost × 3 + 2` px) and carries `filter: blur() saturate()`, so the blur has real pixels to sample at the rim instead of fading against transparent; `.glass__stage` is the page copy, moved with an inline `transform`. All `pointer-events: none`. The pane's background is the page's, read by the script.
- **The checkout bar's strip handoff.** The Modify strip's own invert `backdrop-filter` can't sit inside another backdrop-filter in WebKit, so `.order-checkout-bar.is-strip-active` still drops the glass's (`backdrop-filter: none`, after `calc(var(--fade-fast) * 3)`) — now also for `.is-glass-backdrop` (a higher-specificity selector, since that class sets the filter) — and, in clone mode, hides `.glass__layer` (`opacity: 0`, same delay; the layer's own `transition: opacity 0s` makes it a snap at that moment). It comes back the instant the strip starts to leave.
- **`.product-select-bar`** — fixed, full-bleed, `--select-bar-height` tall, `z-index: 90`, `bottom: var(--selection-bar-stack-height, var(--selection-bar-height))` with a `bottom 0.3s ease` transition: `js/selection-bar.js` publishes that variable (summary + wherever the drawer is heading, a peek included), so the bar rides an open drawer and an add's peek in step with the drawer's own ease. It has its own `transform: translateZ(0)` layer, and fades out (`opacity: 0; pointer-events: none`) in two situations: `.is-away` (set by `js/product.js` between `emjive:modify-open` and `-close`, the Modify sheet resting where the bar would be) and `body:has(.selection-bar.is-peek-up) .product-select-bar` (while an Add's peek has the newest row up). Its button (`.product-select-bar__button`) is text-only, `--black`, the shared button type tokens; `aria-disabled="true"` dims it to 0.35 (`aria-disabled`, not `disabled`, so it keeps focus across the Select → Add swap); `.product-select-bar__label.is-swapping` is the label's fade between "Select" and "Add". Its focus ring is the *default* one, drawn inside (`outline-offset: -2px`) — the inverted white ring would vanish on light glass. It is in `html.is-modal-open`'s scrollbar-compensation list like the other fixed bars.

## Floating selection bar (lines 2692–3021) — scroll-driven on the homepage only

`.selection-bar` itself (line 2703) is visible (`transform: translateY(0)`) by default, with no `transition` on `transform` at all — deliberately, see below. `body.has-series-hero .selection-bar` overrides that to hidden (`translateY(100%)`) purely to cover the instant between the bar being appended (`js/selection-bar.js` runs synchronously) and that page's first real scroll-computed position landing a moment later; it isn't the thing actually driving the entrance.

That selector used to be `body:has(#revealSection)`, which broke the moment the hero became a runtime-injected bundle: `:has()` is live, so at first paint there is no `#revealSection`, the bar paints visible, and it snaps away when the fragment lands — exactly the flash the rule exists to prevent. The class is static markup in `index.html` instead, and `js/series.js` strips it if the bundle fails to load, so the bar isn't stranded off-screen with nothing left to publish a scroll position.

The actual entrance is driven by the active series' hero, which publishes how far past its trigger point the page has scrolled via `window.EmjiveHero`; `js/selection-bar.js` subscribes and sets `.selection-bar`'s `transform` directly, every scroll frame, as a continuous function of that — continuing straight out of the hero's own x-ray wipe rather than switching to a separate, time-based animation once some threshold is crossed. That's exactly why there's no CSS `transition` here: one would lag behind the live scroll-computed value instead of tracking it exactly, undermining the "same physical scroll motion" effect. Pages with no hero never get `has-series-hero` and nothing ever publishes, so the bar there is just always visible — the whole mechanic never runs (see `client-scripts.md`).

**No "add" mode any more.** The bar used to turn into one big "Add" button while `product.html`'s size sheet held a pick (`.is-add-active`, `.selection-bar__add`); that button is the glass Select bar's now, and the bar stays a plain summary — its drawer openable throughout. The bar's own background stays `var(--black-bg)`.

**A real WebKit repaint bug**, not a coalescing/timing one: `.selection-bar` carries `will-change: transform` for the homepage scroll-reveal above, and on iOS Safari specifically a descendant's own `opacity` transition can fail to reliably repaint when nested inside an ancestor already promoted to a compositor layer that way. Fixed by explicitly promoting each of the summary-slot elements (`.selection-bar__icons`, `.selection-bar__empty-label`, `.selection-bar__order`) onto their own layer — `transform: translateZ(0); will-change: opacity;` — rather than leaving Safari to work that out implicitly for a plain descendant. Visually inert in Chrome (confirmed via the headless suite), and load-bearing only on the one engine it targets — don't remove it because it looks like a no-op elsewhere. A separate, harmless-either-way mitigation sits alongside it in `js/selection-bar.js`'s crossfade code: a forced `void el.offsetWidth` reflow before attaching each `transitionend` listener, guarding against Safari's known history of coalescing a transition triggered by a class change with nothing reading layout in between (same reasoning as `playEnterAnimation()`'s own reflow a bit further down that file).

**The icon strip no longer shrinks to fit.** `.selection-bar__icons` sits inside `.selection-bar__toggle` (`right: 0`, no `left` — its width is shrink-to-fit, capped at whatever's left of the toggle once `.selection-bar__order`'s own reserved flex space is subtracted). Every flex item shrinks by default under space pressure, which used to mean a big stack quietly squeezed every icon smaller and smaller instead of doing anything more deliberate. Fixed two ways together: `.selection-bar__icon` is `flex-shrink: 0` (icons stay full-size, refusing to shrink), and `.selection-bar__icons` is `justify-content: flex-end` instead of the flex default `flex-start` — packing the group flush against its own right edge (already anchored to Order via `right: 0`) so the *excess*, once the icons no longer fit, spills past the box's **left** edge instead of pushing the oldest icon out its right edge into Order (`flex-start` would have overflowed the wrong direction here). `.selection-bar__toggle` then clips that overflow (`overflow: hidden`) and fades it with a left-edge `mask-image` anchored to the toggle's own fixed-width box (not a percentage of the icon strip's own shrink-to-fit width, so it only ever visibly fades something actually being clipped — a short stack renders with no fade at all) — see technique #9 below, same recipe as `.product-card__label`'s.

**The Modify strip** (`.modify-strip`, lines 3022–3257) is what either bar turns into while the Modify sheet is open: an opaque `--black-bg` layer over the bar's bottom row, holding Unselect (left quarter, plain `--white` label), Save (the right three quarters, label centered on the whole bar via `padding-right: 25%`) and Undo (the whole strip, plain `--white` label — same treatment as Unselect's; it no longer relies on painting *above* an inverting band the way it used to, since only Save has a band under it now). One `.modify-strip__band` — an invert band (technique #1) sized to Save's own right three quarters at rest, so only Save's label reads dark on a light band; Unselect and Undo never sit under it (this replaced an earlier two-band design, one per button, whose widths `js/modify-modal.js` used to measure into `--unselect-band`/`--save-band` custom properties — both gone now). States: `.is-undo` (the band regresses to `width: 0`, "Undo" crossfading in partway through), `.is-saved` (the band grows to cover the whole strip first, then fades out), `.is-leaving` (Undo's label fades out on its own — the band's already gone), `.is-instant` (a mode change made while the strip is out of sight).

The strip's own outer show/hide (entering/leaving whichever bar's summary slot, or `.order-checkout-bar`'s strip swap) splits into two independently-timed layers rather than one shared opacity: its dark surface (`.modify-strip::before`, grouped with the band as the strip's "surface") and its three buttons. The surface leads the strip's entrance and trails its exit, the buttons the reverse — `var(--fade-fast)` each, totaling `2 × var(--fade-fast)` for the whole strip — per the sitewide rule that a bar with text on it appears first and disappears last (see "Bar-first-in/last-out" below). This split exists because a pseudo-element's opacity is capped by its host's own opacity: the old single `.modify-strip { opacity }` made independently timing the surface against its own buttons impossible, since the container hitting `opacity: 0` made everything inside invisible regardless of its own value. On `launch-order.html` the checkout bar hands over to it with `.is-strip-active` — now a three-beat `transition-delay` cascade, rather than two, to wait out both of the strip's own reveal beats: row-out, then the strip's surface-in, then its content-in, then the glass `backdrop-filter` drops (`calc(var(--fade-fast) * 3)` after the row starts fading), since WebKit is unreliable with a backdrop-filter nested inside another; the drawer that opens over that bar with a copy of the tapped row (`.order-checkout-drawer`) is its own fixed element for the same reason.

**Bar-first-in/last-out, and the shared `--fade-*` tokens (see the design tokens table above).** Two places in the file give a "bar" (a solid or inverted surface) independent timing from the text/controls it carries, so the surface leads on entrance and trails on exit: `.order-item::before`'s invert band vs. its row's own text (`.order-item__inner`, now the element that owns the row's opacity, moved off `.order-item` itself for the same "host opacity caps everything inside it" reason as the strip above) — band un-delayed in, delayed `var(--fade-fast)` out, both `var(--fade-standard)`; and the Modify strip's surface vs. its buttons, above. `js/order-rows.js`'s `collapse()` waits on both the row's `max-height` *and* the band's own (now longer, delayed) opacity transition before removing a collapsed row from the DOM, or the band's exit would be cut short. Every other fade/crossfade in the file (the floating bar's summary-slot label swaps, the checkout bar's own row/strip handoff, hover/disabled dims, sheet/poster/row fades) reads through one of `--fade-fast`/`--fade-quick`/`--fade-standard` instead of its own literal, so genuinely-similar animations land on exactly the same duration — a few pre-existing near-duplicates (0.25s → 0.3s on the size sheets and the icon-stack's opacity leg, 0.1s/0.15s → 0.075s on a couple of Modify-strip labels) were folded into their nearest tier as part of that consolidation; two literals stay deliberately un-tokenized (`.order-item::before`'s own `cubic-bezier(0.4, 0, 0.6, 1)` curve, and `.emjive-3d-viewer__nudge-hand`'s unrelated `250ms`), and the row field-value crossfade (`.order-item .is-swapping`, 0.12s/0.18s) is its own separate family, left out on purpose.

**Drawer item rows are the order page's rows.** The drawer lists `.order-item.order-item--drawer` rows (`js/order-rows.js`) — same markup, same invert band, same tap-to-Modify — sitting on the drawer's ambient `--black-bg`, which is exactly what the band is tuned against. Their name + attrs label never wraps: `.order-item__meta` is `white-space: nowrap` with a `mask-image` fade, the drawer variant keeping its fade to the last 1rem.

## Recurring non-obvious techniques

Recognizing these by pattern saves re-deriving them every time:

1. **Backdrop-filter invert band** — `position:absolute; left:50%; top/bottom:50%; width:100vw; transform:translate(-50%,-50%); backdrop-filter:invert(1);`. Used by `.reveal__frontier`, `.product-detail__label-bar::before`, `.order-item::before` (every row, in the order list, the bar's drawer and the drawer over the checkout bar) and — a variant anchored to a screen edge instead of centered — the Modify strip's one `.modify-strip__band` (sized to Save's own button; Unselect and Undo carry no band of their own — plain `--white` labels instead, see "The Modify strip" above). Text/backgrounds it crosses use the three `--*-inverted` design tokens (see the table above) rather than hand-picked hex, so each reads as the *plain* token once the band inverts it: `.product-detail__label-bar::after`'s backfill sibling uses `var(--black-bg-inverted)`; `.order-item__attrs` uses `var(--category-col-inverted)`. The label bar needs that `::after` backfill because it sits on the plain page background, so `::before` would otherwise invert whatever's actually behind it at each point; `.order-item::before` needs no such sibling, since rows already sit directly on solid `--black-bg`. **Don't rely on a band to invert a label that animates its own opacity**: WebKit gives such an element its own compositing layer, which `backdrop-filter` doesn't reliably see — that's why Unselect and Undo are plain `--white`-on-`--black-bg` labels rather than sitting under a band of their own.
2. **Full-bleed breakout of a centered column** — two variants: `left:calc(50% - 50vw); width:100vw` for absolutely-positioned overlays needing only one axis this way (`.product-card__bar-link` — vertical centering there still uses `top:50%; transform:translateY(-50%)`, a separate axis with no equivalent single-step expression), vs. `width:100vw; margin-left/right: calc(50% - 50vw)` for normal-flow blocks (`.product-detail__label-bar`, `.order-items`). `.product-card__bar-link` used to pair `left:50%` with `transform:translateX(-50%)` instead of the `calc()` form — changed because that pairing mixes two independently-rounded values (a % of the card's own width, then a transform based on the bar's own `100vw` width), which on some device pixel ratios showed up as a hairline gap at one screen edge.
3. **`grid-template-rows: 0fr → 1fr` open/close reveal** — animates a height from/to auto without ever measuring it in JS. Used by `.site-header__menu` and the size modal's size-guide panel.
4. **Container queries** (`container-type: inline-size` + `cqw` units) — `.product-carousel-frame` (tile size), `.size-modal__custom-row` (custom-size input width). Used wherever a component's internal sizing needs to respond to its own box rather than the viewport.
5. **Always-rendered, toggled-transparent indicator dot** — reserves its own layout space up front so selecting an option never shifts adjacent text. Used by the metal picker, the order page's shipping picker (`.order-shipping__option::before`), and — since the header refactor — the header's own category filter tags (`.site-header__nav a.is-cat::before`, toggled by `.is-active`; the lone tag left when a series has just one category defaults to it, permanently). The order page's terms tick-box (`.order-terms__toggle`) is a variant of the same idea scaled up into a standalone control (opacity-toggled fill, no outline) rather than a small accent next to other text, since there it *is* the whole control.
6. **Full-bleed clickable divider bar as one real element** — `.product-card__bar-link` is a single `<a>` breakout out to `100vw` (`--black-bg`, with `.product-card__label-name` set to `--white` so the product name stays legible over it — `.product-card__label-type`'s existing `--category-col` grey already read fine against black), used as the whole row's click target, rather than an invisible overlay layered on top of separate content.
7. **Stopping an oversized grid item from widening its track — `min-width: 0` on the item vs. `minmax(0, 1fr)` on the track** — two related fixes, and which one applies depends on *what* is being stretched. Grid items default to `min-width: auto`, i.e. they refuse to shrink below their own content's minimum size. **One level up**, that's what `.product-card`'s own `min-width: 0` is for: `.product-card` is itself a grid item of `.product-grid`, and without it an oversized figure plus the label's nowrap text was forcing `.product-grid`, and so the whole page, wider than the viewport (visible as `.product-card__bar-link`'s breakout landing a few px off-center, with a matching hairline of genuinely scrollable overflow on the far edge). **Inside** `.product-card`, though, the item-level fix does *not* work: a bare `1fr` track is shorthand for `minmax(auto, 1fr)`, and that `auto` minimum is driven by the item's own **specified** size regardless of the item's `min-width` — confirmed via `getBoundingClientRect`, a 252px figure in a bare `1fr 1fr` card on a 320px phone grew column 1 to 252px outright and collapsed column 2 to 0, `min-width: 0` on the figure or not. The fix there is on the track: `minmax(0, 1fr) minmax(0, 1fr)` gives each column a fixed rather than `auto` minimum, so the split stays an even 50/50 no matter what's inside. Reach for `minmax(0, 1fr)` whenever `fr` columns must stay proportional even when a child is too big for its share.
8. **Setting only `overflow-x` (or only `overflow-y`) makes the other axis `auto` too** — per the CSS overflow spec, an element with one axis explicitly scrolling and the other left at its `visible` default has that other axis computed to `auto` as well, not `visible`. Bitten here: `.size-modal__panel` (`overflow-y: auto` for its own vertical scroll) needed an explicit `overflow-x: hidden` alongside it, or a full-bleed child risked a stray horizontal clip/scrollbar once the panel's own vertical scrollbar was showing. (The metal picker's old scrolling swatch row, `.product-metals__options`, was the other case; the stacked-bar picker no longer scrolls at all.) Always pair the axis you actually want scrollable with an explicit value (usually `hidden`) on the other, rather than leaving it unset.
9. **Element-scoped `mask-image` fade instead of a gradient overlay** — `.product-card__label`'s last 0.75rem fades to transparent via `mask-image: linear-gradient(to right, #000 calc(100% - 0.75rem), transparent 100%)`, so a product name too long for the screen dissolves rather than being clipped mid-letter by `html { overflow-x: hidden }` (the no-horizontal-scroll design means it can never simply overflow). Two things make this work and both are load-bearing. The box is stretched to the **true viewport edge** (`right: calc(50% - 50vw)`, technique #2), so its own `100%` mark *is* the screen edge at any viewport size — a fixed-width box would fade somewhere arbitrary. And it's a **mask on the label itself, not a gradient overlay painted across the row**: `.product-card__bar-link`'s black divider sits directly behind this box at that same edge and has to stay solid all the way out, which an overlay would have faded right along with the text. A mask can only ever affect its own element's pixels. Reach for this whenever something must fade at a screen edge *over* other content that has to stay intact. `.order-item__meta` reuses it (the drawer's rows with the identical 1rem-from-the-end variant) for a name+attrs label that must never wrap; `.selection-bar__toggle` reuses it again, mirrored (fading in *from* transparent over its first 1rem instead of *to* it) and anchored to a fixed-width clipping box rather than a shrink-to-fit one, to fade an overflowing icon stack instead of text — see "Floating selection bar" below.
10. **Mask-shaped backdrop-filter cutout** — `.emjive-3d-viewer__nudge-hand` (the 3D viewer's idle-nudge hand hint): a `<div>` with `-webkit-mask-image`/`mask-image: url("../assets/hand-pointer-thumb-opened.svg")` (a solid black silhouette, edited from its original outline-only `fill-opacity:0` SVG source specifically so the whole hand fills the mask, not just its rim) plus `backdrop-filter: invert(1)`. Paints no fill/border of its own — the SVG only supplies the mask shape, and the invert filter shows through it, so the hint reads as a color-inverted cutout of whatever's underneath (product image or 3D model) rather than a fixed-color icon, staying legible over any background with no conditional styling needed. A different technique from #1 above (that one inverts a full-width/height band with token-based backfill; this one clips the same `invert(1)` idea to an arbitrary SVG silhouette instead of a rectangle).

## Loader (`.loader`, lines 3388–3547)

The compact logo as a loading mark that lives **inside the container of the asset it covers** — parts enter at that container's right border and leave through its left. `js/loader.js` builds the markup (never hand-written in a page): `.loader` (absolute overlay, `z-index: 2`, `overflow: hidden`, `container-type: size`, `pointer-events: none`, transparent) holding `.loader__mark` — a one-cell grid, `--loader-mark` wide (`clamp(3rem, 22cqw, 7.5rem)`, so it scales with the container; the page variant keeps `clamp(4.5rem, 15cqw, 7.5rem)`) and an explicit height (`× 0.4826`, the logo crop's ratio — not `aspect-ratio`, same Safari-grid caution as the product cards' figure) — with three `.loader__part` boxes stacked in it. The loader renders **hidden** (`.is-waiting`) until its show-delay is up.

- **Parts are boxes, shaped by a mask, that invert what is underneath.** Each `.loader__part` paints nothing itself: `mask-image` (a data-URI SVG of the dot / dot / V, `viewBox="48 411 1405 678"`, one `:nth-child` rule each) plus `backdrop-filter: invert(1)` — the same technique as the viewer's nudge hand (see "Recurring non-obvious techniques"). So over the page they read dark, over a fallback image or a 3D model they read as an inverted cutout. They are boxes rather than SVG shapes both because a backdrop-filter needs a box and because iOS Safari handles CSS/Web Animations on SVG *child* elements unreliably (wrong pace, fade not showing) — don't "simplify" it back. Where two parts overlap mid-crossing their inversions cancel in the overlap.
- **Three kinds of host.** (1) Any positioned container — a card's figure, a carousel slide, a 3D viewer's box: the absolute overlay above. (2) `cover()` hosts (`.loader-host`): the host's `<img>` children sit at `opacity: 0` while `.is-loader-pending`, then fade in over `--fade-quick` once the loader has left. (3) The page: `.loader--page` is `position: fixed`, `z-index: 100` (above the header 80, sheets 85, bars 90), opaque `--bg`, on `<body>`; `html.emjive-page-loading::before` (`z-index: 99`, opaque `--bg`) is the cover that is up from the first paint, and `.emjive-page-revealing` fades it out. `.loader--bleed` (no `overflow: hidden`) is for a host whose own edges aren't visible — see `client-scripts.md`.
- **Tokens, all on `.loader`** (read by `js/loader.js`): `--loader-cycle` (the only value in seconds), then `--loader-in` / `--loader-slow` / `--loader-out` / `--loader-gap` / `--loader-stagger` as **percentages of the cycle** (in + slow + out + gap should total 100%; if not, the gap is kept and the other three scale to fit), and `--loader-slow-speed` (a share of the crossing's average speed). `--loader-delay` (150ms) is on `:root`, since it is read before any loader exists. There are deliberately no `@keyframes` — keyframe percentages can't be computed from custom properties, and the easing curves are solved from them (see `client-scripts.md`). Under `prefers-reduced-motion` no loader is mounted at all.

## Production-hygiene rules (added with the hardening pass)

- **`.skip-link`** (next to `.visually-hidden`): the same clipped-rect recipe until `:focus`, then a full-width bar exactly the header's height (`--header-height`, which — with `--header-pt`/`--header-pb`/`--header-image-size` — now lives on `:root`, since the link is the header's sibling), `--bg`/`--black`, laid over it (z-index 100), **no outline**.
- **`.page-message`** — the failed-load / not-found component built by `window.EmjiveMessage.show()` (`js/series.js`): text left-justified in a `--message-width` (60vw) block centred on the screen, button centred 1.5rem under it. The text is DINish in `--category-col` at `calc(0.75rem * var(--text-scale))` — 12px at the base scale, 14.4px on a wide screen, like the rest of the copy; `.page-message__button` is the plain text button (the `.selection-empty__back` recipe, no outline). `--hero` fills the first screen of the homepage's empty hero slot; `--grid` spans the product grid.
- **`.emjive-notice`** — the `alert()` replacement (`EmjiveOrderRows.notice`): a full-width `--black`-on-`--bg` bar that slides up out of the bottom and rests on the highest visible bottom element (selection bar + drawer, Select/checkout bar, checkout drawer, Modify sheet — measured when shown, set as `--notice-rest`); an outer clip element sits above that stack so the bar rises from it rather than across the glass bars; z-index 89 (under the bars' 90), `pointer-events: none`.
- **Focus ring** is `1.6px` (`--focus-ring`, `--focus-ring-inverted`) — 20% thinner than the original 2px. Chrome snaps outlines to whole device pixels, so it reads as 1px on a 1x screen.
- **Closed panels leave the tab order**: `.site-header__menu` and `.selection-bar__drawer` are `visibility: hidden` when closed, with the visibility transition *delayed on close* so the collapse still plays (`.disclosure__panel`'s existing recipe). The drawer is also visible during an Add's peek (`.selection-bar.is-peeking`).
- **Hover is gated**: `.btn`, `.selection-empty__back`, `.order-checkout-bar__button`, `.product-select-bar__button` hover rules sit in `@media (hover: hover)` so touch screens don't keep a button looking pressed after a tap.
- **Fallbacks**: `.series-hero` has `min-height: 100vh` before the `100svh` line; `@supports not selector(:has(*))` reserves the bottom bar padding on `body` for Firefox < 121; `html` sets `text-size-adjust: 100%`.
- **Deliberately not done** (needs on-device checking, and would move visuals): `env(safe-area-inset-bottom)` on the bottom bars, `svh`/`dvh` for the hero's `--reveal-pin-height` (it is measured against `window.innerHeight` in `hero.js`), and changing `touch-action: none` on the grid canvases.

## Accessibility rules (the last three sections of the file)

Three blocks live at the end of `css/style.css` (just behind the Loader section), deliberately last so the `!important` in the third one is the file's only use of it and is easy to find.

**`.visually-hidden`** (just after the base `button, input, textarea` rule) — the 1px-clipped-rect recipe, present to assistive tech and absent from the design. Used by `index.html` and `launch-order.html`, which both needed a real `h1` and have nowhere visible to put one. Not `display:none`/`visibility:hidden`, either of which would remove it from the accessibility tree and defeat the point.

**Focus visibility** — one site-wide `:focus-visible` rule on `a`/`button`/`input`/`[tabindex]:not([tabindex="-1"])` using `--focus-ring`, and a second list overriding it to `--focus-ring-inverted` for everything sitting on a black surface (the selection bar, order rows, the checkout bar). The ring also sets `position: relative; z-index: 1` so neighbours don't paint over it — which makes three exceptions load-bearing:

- **`tabindex="-1"` is excluded, and `.size-modal:focus` draws no outline.** That's how the two sheets' dialog roots take focus (from script, so a screen reader announces them). With the rule reaching them, the fixed sheet turned `position: relative` whenever the browser counted that focus as visible — and iOS Safari does for the first scripted focus after a page load — dropping it to the end of the page: invisible, untouchable, and back only once a tap moved focus away. That was the long-running "sheet doesn't appear on iPhone" bug.
- **Controls that are positioned already keep their own position**: the Modify strip's three buttons (which also draw their ring inset, light on the dark strip), and `.product-card__label` restore `position: absolute` under `:focus-visible`. Anything positioned that can take focus needs the same.
- **Two deliberate opt-outs**: the size field (`.size-modal__custom-input`) shows no outline while typed into — the caret marks it — and `.is-focus-quiet` (set by `js/focus-trap.js` on focus handed back right after a tap) drops the ring until the next key press.

`.product-card__bar-link` is intentionally unreachable (`tabindex="-1"` + `aria-hidden`, set in `js/main.js`) because it duplicates `.product-card__label`.

**Reduced motion** — one `@media (prefers-reduced-motion: reduce)` block. Uses `transition-duration: 0.01ms`, **not `0s`**, and that is load-bearing rather than boilerplate: a transition whose combined duration is `0s` is never started, so it fires no `transitionend` — and several `transitionend` listeners drive real logic (`selection-bar.js` removing a collapsed icon, revealing the summary slot's next label, and — since the bar-first/text-last rework — syncing the icon strip's own reveal to that same moment; `order-rows.js` removing a collapsed row (now gated on both the row's own collapse *and* its invert band's longer, delayed fade, not just the former), finishing an expand and swapping a crossfading part; `selection-page.js` swapping the list and the empty state; `modify-modal.js` building the viewer after the slide-in and handing the bar back after the Modify strip's own exit finishes, on a fallback timer now sized per exit path rather than one shared constant). At `0.01ms` they still fire, sub-frame, so reduced motion gets the fast path instead of falling through to their backstop timers. The `transition: none` writes and the `.is-instant` classes survive it (they set `transition-property: none`). The `animation-*` lines are inert today — there is not one `@keyframes` in this file or in any hero bundle (the Loader's animation is Web Animations in `js/loader.js`, out of this block's reach; that script checks the same media query itself and mounts no loader at all) — and exist so the first one anyone adds is covered. JS-driven per-frame motion is out of reach here and is gated in `js/three-viewer.js` instead; see `client-scripts.md`.
