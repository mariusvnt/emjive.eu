# Tooling

## `package.json` scripts

```json
"dev": "vite", "build": "vite build", "preview": "vite preview",
"auto-render": "node scripts/auto-render.js",
"optimize-models": "node scripts/optimize-models.js",
"measure-models": "node scripts/measure-models.js",
"split-models": "node scripts/split-models.js",
"optimize-images": "node scripts/optimize-images.js",
"optimize-hdri": "node scripts/optimize-hdri.js",
"image-variants": "node scripts/make-image-variants.js",
"scene-tool": "node scripts/scene-tool-server.js",
"json-tool": "node scripts/json-tool-server.js",
"lint": "eslint .",
"validate-data": "node scripts/validate-data.js",
"check-dist": "node scripts/check-dist.js",
"verify": "npm run lint && npm run validate-data && npm run build && npm run check-dist",
"render-favicons": "node scripts/render-favicons.js"
```

`npm run verify` is the one command that says a change is fit to deploy — see "Verification and CI" below. `package.json` also pins `engines.node >= 22` (CI reads `.nvmrc`, which says 22).

`dev`/`build`/`preview` are genuinely wired up and work, and **serve over HTTPS** (`@vitejs/plugin-basic-ssl` in `vite.config.js`'s `plugins`: a self-signed certificate, dev and preview only — nothing in the build). It was put there for the iPhone's `DeviceMotionEvent.requestPermission` (only exposed on secure pages) when the homepage stack tilted with the phone; that tilt is gone, but the certificate stays so a phone on the network gets a secure context like the real site: `npm run dev -- --host` and accept the certificate warning in Safari. Runtime dependencies are `three` and `cannon-es` (the stack's physics, lazily loaded); `npm run dev` is the documented way to run the site locally (see `procedures.md`) and is required specifically for `js/three-viewer.js`'s bare-specifier imports (`three`, `three/addons/...`) — this is a real, live-site file (loaded as `<script type="module">`), not a dev-only one, so Vite is a hard requirement to run the site at all now, not an optional convenience. `three` is a real runtime `dependencies` entry (not just a devDependency) since `three-viewer.js` imports it directly; `puppeteer-core`/`sharp` are `devDependencies`, used only by `auto-render.js`, as are `@gltf-transform/*`/`draco3dgltf`/`meshoptimizer`, used only by `optimize-models` (`meshoptimizer`) and `measure-models` (the other two). `scene-tool` and `json-tool` each start their own, completely separate bare Node server (see below for both) — neither touches Vite at all, and both can run alongside `npm run dev` (and each other) on their own ports.

## `scripts/optimize-models.js` + `scripts/optimize-images.js` + `scripts/optimize-hdri.js`

The three "source art arrives heavy" squeezers. All take `--dry-run` to report without writing, or explicit paths to limit what they touch. The first two rewrite files **in place and delete nothing else** — git is the undo. `optimize-hdri` is the exception and writes a **sibling** file instead; see its own paragraph.

`optimize-models` walks `assets/series/*/products/*/*.glb` and runs: strip textures + `TEXCOORD_n`/`COLOR_n`/`TANGENT` → `weld()` → `dedup()` → `prune()` → `draco()`. It then **re-reads each written file and decodes its Draco payload**, asserting the triangle count is unchanged, the bounding box hasn't moved by more than one quantization step, and the vertex count is within 2% (Draco's encoder re-splits vertices at attribute seams, so it wobbles slightly in both directions by design). It exits non-zero if any model fails that round trip — it is overwriting the only copy of an art asset, so "the encoder said it was fine" isn't the standard. First run: 66.85MB → 8.26MB across eight models, all verified. The catalog's models are now hand-made low-poly versions (14k–39k vertices, 29k–78k triangles, ~1 MiB decoded each): run over them it only recompresses (8.44MB → 0.80MB for all nine, bounds unchanged) and drops the leftover `TEXCOORD_0`.

(The `--simplify` figures below describe the dense exports the catalog used to be made of; none of today's models needs it.) `--simplify=<ratio>` additionally runs meshoptimizer's `simplify()` and is **opt-in on purpose**: it genuinely changes the silhouette, and these same models are what `auto-render.js` re-renders every icon and top shot from, so it's an art call. For reference, `--simplify=0.25` cuts five of the nine cleanly (e.g. cartilage 762K → 190K triangles) but barely moves `rib-cage`/`suture`/`joint`, whose exports are effectively unwelded and so have no shared edges to collapse.

`optimize-images` converts stray PNG/JPEG under `assets/` to WebP (quality 82, alpha preserved, downscaled to fit 2048px) and deletes the source. It prints the old→new path list rather than editing `products.json` itself — see `assets.md`. **It is not the tool for hero art**: it only matches `.png`/`.jpe?g`, it deletes its input, its `MAX_DIMENSION = 2048` would silently cap anything wider (producing a file whose name no longer describes it), and it encodes at quality 82 while `assets.md` specifies 90 for hero renders.

`optimize-hdri` halves the Radiance `.hdr` environment maps in `assets/hdri/`, defaulting to every one wider than 1024px (`--width=<n>` overrides the target). This mattered more than its size suggests: `studio_kontrast_04_2k.hdr` was 5.62MB — 61% of the homepage's total weight, and over five times the combined size of the three ring models it was lighting — and it sits on the critical path, since `three-viewer.js` `Promise.all`s the model and the environment before its first render, so no model appears until the whole HDRI has landed. Halving it to 1024×512 cost 4.22MB and nothing visible: the texture is never displayed, only prefiltered by `PMREMGenerator` into a roughness-blurred mip chain whose top level is 256px a side.

It is a **hand-rolled RGBE codec with no new dependencies**, because `sharp` cannot read Radiance — the libvips build it ships has that format compiled out (`sharp.format.rad.input.file === false`), and making ImageMagick or ffmpeg a prerequisite would be the repo's only non-npm system dependency. Two things to preserve if it is ever modified: the downsample happens in **linear space**, never on the RGBE bytes (RGBE packs three mantissas against one shared exponent, so neighbouring pixels on different exponents cannot be averaged directly — in an HDR image that error is orders of magnitude, not a rounding artefact); and the box filter is guarded to exact integer ratios, where it *is* the correct area average and cannot undershoot into a negative radiance the format can't represent. Like `optimize-models`, it re-decodes what it wrote and checks both the dimensions and the mean luminance (≤1% drift) before reporting success — a real run drifts ~0.23%, which is RGBE's 8-bit mantissa quantization.

Unlike its two siblings it writes a sibling file rather than overwriting, because width is part of the filename by convention (`_2k` → `_1k`), so a halved file under the old name would be a lie. It prints the old→new path and leaves updating `data/series.json`'s `hdris` map and deleting the original to you.

None of the three is wired into `build`. They're deliberate, occasional, reviewable passes, not something that silently rewrites binaries on every deploy.

## `scripts/measure-models.js` — each model's volume and size

`npm run measure-models` (`--dry-run` reports without writing) reads every product's `assets.model` — and, for a product with `designs`, each non-default design's `model` (`data.md`) — with `@gltf-transform/core` plus the Draco decoder (the same setup as `optimize-models`; no new dependencies), measures it, and writes the result into that product's — or design's — `"geometry"` line in `products.json` (fields in `data.md`). The product page turns it into a cost breakdown (and, at the largest size, the room its dimension brackets need) with the constants in `data/series.json`'s `metal-costs`; the box's pose (`min-box`) is what the brackets are drawn on.

- **Volume**: node transforms are applied, corners are welded by position (1e-4 mm), and each connected shell contributes |Σ signed tetrahedra|. The absolute value per shell is needed because several exports have inverted winding (a negative signed volume). The models are authored in mm (1 unit = 1 mm), so cm³ = mm³ / 1000. It also counts edges not shared by exactly two triangles: a nonzero count is printed as "not watertight" (volume approximate; today six of rib-cage's ten designs: the default 1L2L3, 123, 23, 2L3, 13 and 3 — listed as `bones/rib-cage [123]` and so on).
- **Size**: the extents of the **minimum-volume bounding box**, longest first. It builds the convex hull (`three/examples/jsm/math/ConvexHull.js`), then for each distinct hull-face normal finds the best box flush with that face (a 2D rotating-calipers search over the projection's hull), and finally polishes the winner numerically. To keep it to a couple of seconds a model, every candidate normal is first scored on a thinned set of ~800 extremal hull vertices and only the best 12 are re-scored on the full hull.
- **Writing**: only the `"geometry"` line inside the product's block is replaced or inserted (right after `per-metal-specs`), in the file's own line-ending style, so a run changes nothing else, and a second run over unchanged models changes nothing at all. A design's own line is replaced or inserted right after its `"picks"` line (`withDesignGeometry()`), the design's entry located by its `"key"` inside the product's block (`findBlockSpanByAnchor`). It reuses `json-tool-blocks.js`'s `findProductBlockSpan`; `measureFile()` is the one measuring function behind both. `"model-sha1"` is the hash of the `.glb` bytes.
- **Not in the build**: like the optimizers it's a deliberate pass. `validate-data.js` is what enforces it — every product must have `geometry`, and its hash must match the file on disk.

- **The box's pose**: besides the extents, `"min-box"` records the winning box's centre (mm) and three unit axes, sorted like `dimensions-mm`, in the glTF scene's own frame (node transforms applied, which is the frame the viewer's model group is in).

## `scripts/split-models.js` — one export of every model, split into the catalog's files

`npm run split-models -- <file.glb> [<file.glb> …] [--dry-run] [--no-optimize]`. The models are authored together in Blender and exported as **one glTF with a root node per model** (`items.glb`: `furcula`, `foramen`, `foramen-twisted`, `rib-cage-1L2` …), with a second export of the same nodes as thick-barred wireframes (`items-wireframes.glb`: nodes named `<name>-wireframes`). This script cuts them up into the files `products.json` names. Any number of files may be given; **a later file overrides earlier nodes of the same name** (the corrected `rib-cage-1.glb` after `items.glb`), for models and wireframes alike.

- **Matching.** A node's name is slugged and matched, in every `products.json`, to a design `name` (a product with `designs`) or else a product `name`; the node's `-wireframes` twin goes to that entry's `wireframe` path. Nodes that match nothing are listed. The default design writes to the *product's* own paths, the others to their entry's `model`/`wireframe`.
- **Writing.** For each node: a new document (`Document` with a quiet `Logger`), `copyToDocument` of that node alone, `prune()`, written as a `.glb` to the entry's path; a wireframe keeps `POSITION` only and loses its material (the viewer draws it with its own). Then `optimize-models` runs over what was written (weld + Draco, round-tripped), unless `--no-optimize`.
- **Orientation guard.** The export has more than once lost a node's rotation (furcula's +90° about Y is the known case). When replacing an existing model, the new file's world bounds are compared with the old file's: if they match only under the old root rotation, the old rotation is kept on the new model — and the same correction is applied to its wireframe (`quatMultiply(fix.to, quatMultiply(quatInverse(fix.from), R_w))`), which is exported unrotated alike — and the script says so. Fixing it in the .blend would make the guard moot.
- **Afterwards** (the order that works): `measure-models` (the geometry and hashes of everything written), then `auto-render -- --product=<slug>[,…]` for the products and designs whose renders are now out of date, then `validate-data`. A wireframe must line up with its model in world space (≈0.1 mm; checked by eye in the specs stage, the box and the bars should coincide).

## `scripts/make-image-variants.js` — the other versions of the big images

Writes the extra versions of every image the site loads in more than one size, **next to the original** (`assets.md`'s "Responsive versions" has the table; the sizes, qualities and `PHONE_CROP` live at the top of the script): the product x-ray and the hero photo in four versions (desktop low `_lo`, smartphone high `_m` and low `_m_lo`; the original is desktop high), the hero's hand x-ray and extension panels as `_m` only, and each icon's `_128` thumbnail. The smartphone versions are **cropped** (`sharp`'s `extract`, around the centre, full height) to the share of the width a phone can show, then resized; the layout (`--xray-crop`, `--hero-crop`) has to know the same number, which is why `validate-data.js` compares them (`PHONE_CROP.xray` is 0.85 now: a phone's x-ray is cut to the middle 0.85, which is wider than any phone's screen).

```text
npm run image-variants                       write any that are missing
npm run image-variants -- --force            rewrite every one
npm run image-variants -- --dry-run          report only
npm run image-variants -- --series=<slug>    only that series' images
```

It exports `makeVariants({ dryRun, force, series, kinds })` (and `PHONE_CROP`), which is what `scripts/auto-render.js` calls — **`auto-render --image-variants`** runs every rule with `force` and renders nothing (no Chrome, no GPU, no `products.json` writes), and a full render ends with an "icon thumbnails" step (`kinds: ["icons"]`, forced) because the icons it just wrote are the source of the `_128` files. A rule matches by filename pattern, so a new product's x-ray/icons are picked up with no registration; a new *kind* of image is a new entry in `RULES`. Like the other art scripts it is not part of `build`: the generated files are committed. It never touches the originals or the 3D models.

## `vite.config.js`

Exists specifically because `npm run build`'s output needs to be *deployable*, not just correct in dev — a plain `vite build` with no config silently produces a broken `dist/` for this site (confirmed by inspecting the output directly): Vite only treats `index.html` as a build entry by default (every other page would ship unprocessed, with the same unresolved bare-specifier `three` import that breaks on any plain static host), and it can't bundle or copy classic `<script src>` tags at all (so `js/main.js`, `js/product.js`, and the other classic scripts vanish from the build entirely — not just left unbundled, actually absent) or trace paths that only exist as runtime string data (a series' `products.json` icon/model paths, the hero-bundle paths in `data/series.json`, the HDRI path in `three-viewer.js`). Two things fix this: `build.rollupOptions.input` lists all seven HTML pages explicitly, and a small inline `closeBundle` plugin copies `js/`, `assets/`, `data/`, and `series/` into `dist/` verbatim after the real build runs. `series/` is on that list for the same reason as `data/` — it holds each series' hero bundle, referenced only as string paths and injected at runtime, which is also why a hero bundle's JS can never use a bare specifier. Also sets `base: "/"` because the site is served from the root of `emjive.eu`; a subfolder deploy would need that subfolder's path instead (see `README.md`'s "Deploying" section).

### What else the config does (all verified against the built `dist/`)

- **`restoreHeadOrderAndPreload()`** — a `transformIndexHtml` plugin (`order: "post"`). Vite's HTML build (a) inlines `<link rel="preload" as="fetch" href="data/series.json">` as a `data:application/json;base64,…` URL (the file is under its inline limit), which can never satisfy the real `fetch`, so the early request the preload exists for never happened, and (b) re-emits the stylesheet *after* the blocking `<script>`s, contradicting the order `scroll-memory.js`/`loader.js` depend on. The plugin restores the real `data/series.json` href and moves every stylesheet link in front of the first real `<script>` (comments are blanked first so a tag *mentioned* in a page comment isn't matched). `scripts/check-dist.js` fails the build if either regresses.
- **`injectLoadHints()`** — a second `transformIndexHtml` plugin (`order: "post"`, build only — it needs the bundle) that adds early-discovery `<link>`s, from the same `data/series.json` the pages read, for the **featured** series (a visitor on another series just gets a few unused preloads), ahead of the stylesheet so the preload scanner meets them first: `data/series/<slug>/products.json` on pages with `data-products="eager"` (also started by `js/series.js` itself — the same request, a hop earlier), and, on the homepage (`#seriesHero` in the page), the hero fragment, `hero.css`, `hero.js` and the first `hero.preload` image as its **low-res version, one link per side of the phone query** (`media=` picks the right one; `fetchpriority="high"`). **Deliberately not hinted: the three.js chunk, the HDRI and the model on `product.html`.** They are the heaviest things on the page and none is part of its first paint; with `modulepreload`/`preload` in the `<head>` they shared a throttled link with the LCP image and measurably pushed it later (its request started at 2.6s instead of 1.2s in the throttled lab). `js/product.js` starts all three itself once the first paint is in (`client-scripts.md`). `scripts/check-dist.js` asserts the `products.json` preload exists on opted-in pages, and `PHONE_QUERY` in this file is one of the copies `validate-data.js` compares.
- **`emitSitemap()`** — `generateBundle` emits `sitemap.xml` from `data/series.json` + each series' `products.json`: `https://emjive.eu/gallery` plus `https://emjive.eu/<slug>` per product (the addresses the site really uses — `pages.md`'s "Addresses"; `check-dist.js` fails if it lists anything else). The noindex pages are left out; add one here when it gets real content.
- **`emitItemPages()`** — `closeBundle` (build only) copies the **processed** `dist/product.html` to `dist/<slug>.html` for every product, rewriting the item's `<title>`, meta description, `og:title/description/url/image/image:alt`, `twitter:title/description/image` and adding `<link rel="canonical">` — and, for an item of a non-featured series, the `products.json` hint (`injectLoadHints()` names the featured series'). Each tag is matched with a regex; a tag missing from `product.html`'s head **throws**, so editing that head can't silently leave items with the generic tags. Product data and slugs come from `readProducts()` (shared with the sitemap) and `scripts/slugs.js`.
- **`cleanUrls()`** — dev-server and `vite preview` middleware doing what `.htaccess`'s rewrite rules do (neither server reads `.htaccess`): `/gallery` → `/index.html`; `/<name>` → `/<name>.html` when that file exists (in preview, that includes every item's built page); in dev, where per-item files don't exist, an item's `/<slug>` → `/product.html`. Only extension-less single-segment paths are touched. Keep it and the `.htaccess` block in step.
- **`scripts/slugs.js`** — the one build-side definition of an item's address: `slugify(name)` and `reservedNames(root)` (the page routes plus every top-level file/folder name of the repo and `public/`). Used by `vite.config.js` and `validate-data.js`; `js/series.js`'s `productSlug()` is the browser twin, and `validate-data.js` compares the two.
- **Minification of the verbatim-copied files** — after the copy, `minifyCopiedFiles()` runs esbuild (via Vite's `transformWithEsbuild`, no extra dependency) over `dist/js/*.js` and each `series/<slug>/hero.{js,css}` in place: same filenames, no sourcemaps (~306KB of scripts → ~116KB). esbuild keeps top-level names in a plain script, so the `window.Emjive*` globals and load order are untouched.
- **`public/`** — Vite's default public dir, copied as-is to the root of `dist/`: `.htaccess`, `robots.txt`, `favicon.ico`, `apple-touch-icon.png` (see below).
- **`404.html`** is a real rollup input (key `notFound`) so Vite rewrites its stylesheet/logo to absolute hashed URLs; it has no `<script>` because the site's classic scripts are referenced relatively and would 404 at depth.
- `worker: { format: "es" }` — `js/hdr-worker.js` is created with `new Worker(new URL("./hdr-worker.js", import.meta.url), { type: "module" })` in `three-viewer.js`; Vite bundles it to `dist/assets/hdr-worker-<hash>.js` (~69KB, mostly three's loader base classes, off the main thread) and rewrites the reference, but only emits an ES-module worker with this setting (the default is an IIFE, which `{ type: "module" }` can't load). The worker's CSP is already covered by `worker-src 'self' blob:`.
- `build.chunkSizeWarningLimit: 700` — the one big chunk is the lazy three.js chunk (~680KB / ~179KB gz), a deliberate size; see `client-scripts.md`'s `viewer-entry.js`. The homepage stack's chunk (`js/stack-scene.js` plus `cannon-es`, ~97KB / ~29KB gz) is separate and imports the first one's `toolkit` export.

### What the build deliberately does *not* ship

Copying whole trees is the right default but it isn't free, and two separate mechanisms trim it. Both were added after measuring `dist/` at 28MB and finding ~6MB of it unreachable; it then built at 20MB (15MB today, now that the catalog's models are low-poly).

`NEVER_COPY` is a `cpSync` filter listing the paths the copy step skips:

- **`assets/fonts/`** (1.35MB) — Vite *does* trace the `@font-face` `url()`s in `css/style.css` and the `<link rel="preload">` hrefs in every page's `<head>`, emits its own content-hashed copies, and rewrites both references to point at them. Nothing in the built output mentions `assets/fonts/` at all, and only 5 of the 45 files there were ever referenced. Re-check this if a font is ever loaded from a runtime string rather than from CSS.
- **`assets/hand_normal.webp`** (0.64MB) — dead in the repo and in the build; see `assets.md`.
- **`assets/logo.svg`, `logo_compact.svg`, `hand-pointer-thumb-opened.svg`, `metal-sample_*.webp`** — referenced only from HTML `<img>`/`<link>` and `css/style.css` `url()`s, which Vite traces and re-emits hashed; the verbatim copies beside them were byte-identical and never requested.
- **`js/viewer-entry.js`** — a module entry Vite bundles (its relative `import("./three-viewer.js")` only resolves inside the bundle); the verbatim copy would point at the unbundled source below.
- **`js/three-viewer.js`** (~85KB) — the unbundled ES module source. Built pages load Vite's bundled copy; this one still carries the bare `import "three"` that nothing at runtime can resolve. Every *other* file in `js/` is a classic script the built HTML really does load by its original path, which is why this is one exclusion rather than a rule about `js/`.
- **`js/hdr-worker.js`** — the module worker `three-viewer.js` starts; Vite bundles it, and the verbatim copy would carry a bare `import "three/addons/…"` nothing can resolve. `check-dist.js` forbids it in `dist/` like the other two sources.
- **`js/stack-scene.js`** — the homepage stack's module (bare `three` and `cannon-es` imports): reached only through `js/viewer-entry.js`'s `import("./stack-scene.js")`, which Vite bundles to `dist/assets/stack-scene-<hash>.js`. Forbidden in `dist/` by `check-dist.js` too.

`dropUnusedDracoDecoderCopies()` is a `generateBundle` hook deleting bundle entries matching `/draco_(decoder|wasm_wrapper)/` (~1.26MB). Those come from three's own `DRACOLoader.js`, which resolves its bundled decoder with `new URL('../libs/draco/…', import.meta.url)` — a pattern Vite treats as a static asset reference and emits. This site can never request them: `js/three-viewer.js` calls `setDecoderPath(new URL("assets/draco/", document.baseURI).href)` before any load, replacing every one of those URLs with the self-hosted copy under `assets/draco/` (which stays, and is still copied). **If that `setDecoderPath` call is ever removed or made conditional, this hook has to go with it** — three would then genuinely need the copies it emitted.

## `scripts/auto-render.js` (~1100 lines)

Renders per-metal product icons, "top shot" images, and the metal-sample swatch squares via a real (GPU-accelerated) headless Chrome instance, driving the site's **own** `js/three-viewer.js` / `window.EmjiveModelViewer` rather than a hand-duplicated reimplementation — so a render can't silently drift from what the live site actually shows. See `procedures.md` for the invocation/usage walkthrough; this doc covers the internal architecture instead.

**Major pieces:**

- `findChrome()` — checks `CHROME_PATH` env var first, then a hardcoded list of common install paths per OS; throws if none found.
- `startServer()` — a bare `http.createServer` serving repo files by path, plus a special `/__render__.html` route serving an in-memory `HARNESS_HTML` string. Has a path-traversal guard (resolves the requested path and checks it still starts with the repo root before serving).
- `HARNESS_HTML` — a minimal page with an `<script type="importmap">` resolving `three`/`three/addons/*` straight from `/node_modules/...` (this bare server has no bundler of its own to do that resolution, unlike the real site's Vite build) and a `<script type="module" src="js/three-viewer.js">`. Its own inline module script defines three page-side render functions on top of that: `window.__renderTarget(product, metalKey, sizePx, hdriRelPath)` (the icon/fallback-img capture, calling `window.EmjiveModelViewer(product, metalKey, {transparentBackground: true, static: true, hdri: hdriRelPath, onReady})` directly — `static` skips the idle-nudge hint and continuous animate loop so nothing can shift the framing before the screenshot; the Node side then saves this one screenshot two ways, see `renderIconAndFallback` below), `window.__renderTopShot(...)` (same, plus `hdriRelPath` — `scene.environment` is already whichever HDRI this series resolved to by the time `onReady` fires, no override needed, unlike an earlier version that swapped in a cached `RoomEnvironment` PMREM texture instead — but additionally adds a procedural soft-shadow plane, adds an invisible finger occluder, and calls `handle.setCameraOrbit({ rotation: 0, tilt: 0, zoom })` to force a straight-down view — the direct replacement for the old model-viewer-based harness's `jumpCameraToGoal()`+`camera-orbit`-attribute combo), and the swatch pair `window.__buildSwatchScene(sizePx, metalKey, hdriRelPath, blurPx, camera)` (builds a minimal stub `{ name, "3d-viewer-camera-default": swatchOrbit(camera) }` and calls `window.EmjiveModelViewer(stubProduct, metalKey, {transparentBackground: true, static: true, hdri: hdriRelPath, environmentBlur: blurPx, swatch: true, onReady})` **once** for all the metals — `options.swatch` is what used to be a separate `buildMaterialSwatch()` function, then a single `options.primitive`; see `client-scripts.md`) and `window.__aimSwatch(metalKey, camera)` (`applyMetal(metalKey)`, then `setCameraOrbit(swatchOrbit(camera))` to draw it — a static viewer renders only on explicit calls — then two `requestAnimationFrame`s). The first three render functions wait two `requestAnimationFrame`s after their own completion signal before setting `window.__renderReady = true`, so the *settled* frame gets captured, not a stale one; the swatch scene sets it from `onReady` alone and the per-metal wait is `__aimSwatch`'s own. A `disposeCurrentHandle()` helper runs before every render call — it disposes the previous `WebGLRenderer` (a fresh one is built per render, since a full run creates many contexts in one browser session and undisposed ones eventually exhaust the browser's WebGL context limit) — `js/three-viewer.js`'s own HDRI loading needs no equivalent help, since it's loaded fresh per instance rather than cached across contexts (see `client-scripts.md`). `window.EmjiveModelViewer` can return `null` if WebGL context creation fails (see `client-scripts.md`) — unlike the live site, which falls back to a static icon image in that case, this tool has no equivalent fallback (rendering the icon *is* the job), so the render functions instead throw a descriptive `Error` naming the product/metal (or, for the swatch scene, just "the swatches") that failed, aborting the run rather than crashing on a confusing null dereference or silently shipping an incomplete set of renders.
- `addFingerOccluder(scene, box)` (top-shot only) — a real finger is never present in these renders, so a straight-down shot of a ring would otherwise show whatever geometry actually sits under its visible top surface: the band's own inner wall, or (Furcula's split shank specifically) a sightline straight through a gap to the far side. This fakes the occlusion a finger would provide with an invisible plane — `MeshBasicMaterial({colorWrite: false, depthWrite: true})`, so it blocks whatever's behind it in the depth test without ever contributing a visible pixel — positioned at the model's own vertical midpoint (`box.min.y + size.y * 0.5`) and given `renderOrder: -1` so it draws (and claims the depth buffer) before the model regardless of THREE's own distance-sorted opaque order. A uniform 50%-height cut across every product was settled on only after several fancier per-product approaches (a radius-fitted cylinder to leave untouched geometry provably safe, then per-angle radii to hug an elongated shank more tightly, then deriving the cutoff straight from the nearest real surface via raycasting) each failed a different way against the three products current at the time — see the function's own comment in the source for the specifics. Deliberate trade-off, not a bug: this fully fixes Furcula's shank but does visibly cut into Disc's own lower band surface, since Disc's decorative material happens to start lower relative to its own bounding box than the other two.
- Because that occluder writes depth but not color, it can't share a render pass with the existing soft-shadow plane without a visible side effect: tried directly, the occluder winning the depth test against the shadow (drawn later, in the transparent pass) erased the shadow's own color exactly where it did, punching a hole in the gradient at the "finger" location. Fixed with a two-pass render instead — the model hidden on its own `THREE.Layers` layer for a first pass so the shadow draws alone against a genuinely empty canvas, then the model and the occluder brought back for a second, non-clearing pass with the shadow specifically re-hidden (redrawing it a second time double-blended the area the occluder wasn't covering, a subtler version of the same artifact). The shadow plane's own size (`sphere.radius` multiplier) was also tightened, separately — the previous multiplier left faint non-zero alpha reaching the captured frame's own edge, invisible at this render's native 1024×1024 but a visible translucent rectangle once composited small onto the hero's hand (see below).
- `captureTarget`/`captureTopShotTarget` → `renderIconAndFallback`/`renderTopShot` (and `renderSwatches`, below) — drive Puppeteer to call the harness functions, screenshot the result, and encode to WebP via `sharp` (`quality: 92`). A swatch is captured through a square frame of `SWATCH_CAPTURE` (72) css px (the camera's fov is solved for it — the biggest square inside the sphere's disc) and saved at `SWATCH_SIZE` (72px) — the downscale from the 2x capture is done here rather than left to the browser. Captures happen at 2x the final pixel size then downscale — real GPU MSAA already handles edge antialiasing; this step is purely for retina-sharp source pixels. `renderIconAndFallback` calls `captureTarget` **once** per product/metal and saves that one screenshot buffer two ways, in this order: first as-is (a plain resize, `FALLBACK_IMG_SIZE` = `ICON_SIZE`) for `fallback-img`, then through `normalizeIconFraming` (trim/re-center/pad) for `icon` — see `data.md` for why the two need different treatment. The swatches are **not** a scene per metal: `renderSwatches(page, wantedMetals, hdriRelPath, blurPx, camera)` builds the scene once in the harness (`window.__buildSwatchScene` — one sphere under the swatch HDRI, via `options.swatch`; see `client-scripts.md`) and then, for each wanted metal, `window.__aimSwatch` gives the sphere that metal and draws it, the camera being the same for all (`swatchOrbit(camera)`), and the page is screenshotted — a **72×72 css px** square (captured at 2x like the rest, `omitBackground`) per metal, resized to `SWATCH_SIZE` and written to `assets/metal-sample_<metal>.webp`. Every swatch shares the camera, the sphere and the HDRI: only the shader differs. Nothing is cropped — the frame already is the biggest square in the disc. It runs once after every product has been rendered, not inside the per-metal loop; `--swatches-only` skips the products entirely (no icons/top shots, no `products.json` writes) for tuning the swatch scene. The picker shows the file as it is.
- `--product=<slug>[,<slug>…]` — only those products (their names as slugs; the swatches are skipped when it is given). Every product with `designs` also renders its **non-default designs**: `designView(product, design)` makes a view of the product with the design's model and geometry (the product's camera), and the per-metal loop renders each one's `icons` and `fallback-img` (no top-shot) into the product's folder under the design's file names (`<slug>-<design key>_icon_<metal>.webp`), patching them with `updateDesignMetalFieldInText(text, product, designKey, blockKey, metal, newRelPath)` — the same regex idiom as the next function, but anchored first on the product's `"id"` and then on the design's `"key"` inside its slice.
- `updateProductMetalFieldInText(text, product, blockKey, metal, newRelPath)` — the regex-based JSON text patcher. Doesn't re-parse/re-stringify the whole file (see `data.md` — that would flatten its hand-aligned formatting). Instead: finds the product's block via its unique `"id": "<id>"` anchor, slices to the next `"id":` occurrence (or EOF), then within that slice matches `"<blockKey>":\s*\{[^}]*\}` (works for the nested `assets.icons`, `assets.fallback-img`, and `assets.top-shot` objects alike, since the regex only needs to be unique *within* one product's slice — this is also exactly why it can't be used to match `assets` itself, which also contains plain-string/array fields like `model`/`xray`/`photos` and would break the "no nested braces" assumption). Returns `null` rather than throwing if either regex fails to match, so the caller can warn and skip instead of corrupting the file. `scripts/scene-tool-server.js` (below) reuses this exact `"id"`-anchor/non-nested-braces idiom for its own patchers, adapted for whole-block numeric/string replacements instead of a per-metal string swap.
- `productFolder(seriesSlug, product)` — builds a product's render output folder (`assets/series/<slug>/products/<slug(name)>_<category>/`) **from the series layout**, rather than inferring it from `path.dirname(product.assets.model)` as it used to. That inference couldn't tell one series' tree from another's, and wrote to the repo root for any product without a model yet, since `path.dirname("")` is `"."`. The trade-off is that `assets.md`'s `<slug>_<category>` folder convention is now load-bearing: a hand-renamed folder gets a *new* one rather than being silently found. A warning fires when `product.assets.model` sits outside the predicted folder, which doubles as a check that no model was missed by a move.
- `warnCategoryDrift(seriesIndex, targets)` — warns on the two category invariants nothing else enforces: a series declaring a category outside `series.json`'s global vocabulary, and a product whose category its own series doesn't declare (it renders in the unfiltered grid but no filter button can reach it). This is the only thing that has the index and every series' products parsed at once. An empty `sizes` list is *not* an error — it deliberately disables the Select button (see `data.md`). Two siblings, same "warn but don't crash on data-integrity drift" shape, checking every series regardless of `--series`: `warnHdriDrift(seriesIndex)` (a series' `hdri` key not in the top-level `hdris` map) and `warnSwatchSceneDrift(seriesIndex)` (`swatch-hdri` not in `hdris`, `swatch-blur` present but not a number of 0 or more, or `swatch-camera` present but not `{ rotation, tilt, roll }` of numbers).
- `main()` — parses metal args (validated against `series.json`'s top-level `metals`) and an optional `--series=<slug>` to narrow the run, finds Chrome, starts the server, launches Puppeteer with GPU-forcing flags (`--use-angle=d3d11` added only on `win32`; `--enable-gpu-rasterization --ignore-gpu-blocklist` on all platforms), then **checks the actual WebGL renderer string** via `WEBGL_debug_renderer_info` and warns if it contains "swiftshader"/"software" (meaning no real GPU/MSAA was used — see `CHROME_PATH` in `procedures.md`). Also resolves each series' own `hdri` (into `target.hdri`, threaded through every render call for that series) and the top-level `swatch-hdri` (into a path), `swatch-blur` and `swatch-camera` once — a missing or malformed one falls back (no HDRI choice: the viewer's default; no blur; the default camera, `SWATCH_CAMERA_DEFAULT`: straight in front at eye level; `warnSwatchSceneDrift` warns). For each metal, for each series, for each product: renders+writes the fallback-img and icon in one pass (patching `assets.fallback-img` and `assets.icons`, deleting each old file if its path changed), renders+writes the top shot (same for `assets.top-shot`); then, after the whole metal loop, renders the swatches (global, not per-series, using the resolved `swatch-hdri`, `swatch-blur` and `swatch-camera`). Writes each series' patched text back only if it actually changed. Runs in a `try/finally` that closes the browser and HTTP server either way.
  **`--image-variants`** short-circuits `main()` before any of that (before validation of metals, before Chrome): it validates `--series`, runs `makeVariants({ force: true, series })` from `scripts/make-image-variants.js` and returns. And every full run (not `--swatches-only`) ends with `makeVariants({ force: true, kinds: ["icons"], series })` — the `_128` thumbnails of the icons it just rendered.

  **One target per series file, with its `raw`/`text`/`data` kept strictly bundled together.** Product ids are only unique *within* a file now, so a shared top-level `productsText` could have one file's text patched using another file's product and still satisfy `updateProductMetalFieldInText`'s `"id"` anchor.

## `public/` — the host configuration

- **`.htaccess`** (OVH shared hosting is Apache): www→apex and http→https redirects; the **clean-URL rules** (`/index.html` → 301 `/gallery`; `/<page>.html` → 301 `/<page>`, except `product.html` — old `product.html?id=` links land there and `js/product.js` moves them on — and `404.html`, the ErrorDocument; a trailing slash is stripped; internally `/gallery` → `index.html` and `/<name>` → `<name>.html` when that file exists, which covers the pages and every item's built page without listing them — the bare `/` stays on DirectoryIndex, no redirect; the `THE_REQUEST` guard keeps the redirects from firing on the internal rewrites; `check-dist.js` asserts the rules are in `dist/.htaccess`, and only a `curl -I` on the live host proves they run — README's "Production checklist"); MIME types for `.glb`/`.wasm`/`.hdr`/`.webp`/`.woff2`; deflate (including `.glb`/`.hdr`, which compress poorly but not for free); caching — `/assets/<name>-<8-char hash>.<js|css|woff2|svg|webp>` (Vite's own output) `immutable, max-age=1y`, html/js/css/json/xml/txt `no-cache` (revalidate by ETag — this is the cache-busting for the verbatim-copied scripts and JSON that keep fixed names), unhashed binaries (models, images, HDRIs, wasm) a week plus `stale-while-revalidate=86400` (served stale for up to a further day while the browser refetches in the background) — they keep their names when art is regenerated, so a change that must show up sooner needs a new filename; security headers (`nosniff`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options`, HSTS at `max-age=300` to start); and a **`Content-Security-Policy-Report-Only`** (rename to `Content-Security-Policy` once a pass over every page logs no violations). Every block is in `<IfModule>`, so a module missing on the plan skips the block instead of 500ing the site — which also means each part has to be confirmed with `curl -I` after deploy (README's "Production checklist").
- **`robots.txt`** points at `https://emjive.eu/sitemap.xml`. **`favicon.ico`** (PNG-in-ICO, 32px) and **`apple-touch-icon.png`** (180px, on `--bg`) are generated by `scripts/render-favicons.js` from `assets/logo_compact.svg` (`npm run render-favicons`; only re-run if the logo changes).
- Because the deploy mirrors `dist/` over `www/` with `--delete`, anything placed on the server by hand — an `.htaccess` included — is wiped on the next push. It has to live here.

## `scripts/scene-tool-server.js` + `scene-tool.html`

A standalone dev page (`npm run scene-tool`, then open `scene-tool.html`) for tuning a product's camera angle, a series'/the swatch renderer's HDRI, the swatch's HDRI blur and camera angles (rotation, tilt, roll), and a metal's shader — all as a live preview through the site's real `window.EmjiveModelViewer`, with a Save action that text-patches the relevant source file in place. Written to replace the old "drag it, hand-edit the JSON, reload, compare, repeat" workflow `procedures.md` used to document for `3d-viewer-camera-default` — see that doc's "Setting a model's default view" for the actual usage walkthrough; this section covers the server's own architecture.

Like `json-tool`'s, the server binds to `127.0.0.1` only and rejects any request whose `Host` isn't a loopback name for its port, or whose `Origin` (on anything but a plain read) isn't itself — these servers can write and delete files in the repo, and previously answered the whole LAN. Deliberately built as a **second, completely separate** bare `http` server (port 5200) rather than a Vite dev-middleware route or a browser File System Access API — it mirrors `scripts/auto-render.js`'s own already-proven pattern (bare server + import-map-resolved `three-viewer.js`) instead of tangling a dev-only save endpoint into `vite.config.js` (whose whole reason for existing is production-build correctness), and needs no Chromium-only permission dance the way FSA would. Never added to `vite.config.js`'s `build.rollupOptions.input`, so it's naturally absent from `npm run build`'s output — same as `auto-render.js` itself.

- **Static serving** — same `MIME` map and path-traversal guard as `auto-render.js`'s own `startServer()` (duplicated rather than imported/shared — a little redundancy here is consistent with this repo's own tolerance for that trade-off, e.g. `vite.config.js`'s `copyFilesVitesBuildCantTrace()` comment), including `/node_modules/...` so `scene-tool.html`'s own import map (same `three`/`three/addons/*` resolution `HARNESS_HTML` uses) can be served.
- **Five save endpoints**, one per {concern × mode}, so `scene-tool.html`'s tick boxes only fire the ones actually ticked: `/api/save-product-camera` (product mode, patches that product's `3d-viewer-camera-default`), `/api/save-series-hdri` (product mode, patches that product's series' `hdri`), `/api/save-swatch-camera` (swatch mode, replaces the `"swatch-camera": { ... }` block — rotation, tilt, roll rounded to 2 decimals), `/api/save-swatch-hdri` and `/api/save-swatch-blur` (swatch mode, the top-level `"swatch-hdri"` string and `"swatch-blur"` number — the HDRI tick fires both), `/api/save-metal-shader` (either mode, patches `METAL_PRESETS` in `js/three-viewer.js` itself — the one save target that isn't JSON). Every endpoint re-reads its target file fresh per request (this server is long-lived across many separate Save clicks, unlike `auto-render.js`'s one-shot batch read), validates before touching disk, and writes only on a successful patch match — otherwise a 4xx with a clear "field not found, add it by hand first" message rather than inserting a new key.
- **Patchers** — `updateCameraDefaultInText`/`updateSeriesHdriInText`/`updateSwatchSceneInText`/`updateMetalPresetInText`, all variations on `auto-render.js`'s own `"id"`-anchor, non-nested-braces block-scoping idiom (see `updateProductMetalFieldInText` above), adapted for whole-block numeric/string replacements instead of a per-metal string-value swap. `updateMetalPresetInText` is the one that patches JS source rather than JSON — bounded to `METAL_PRESETS`'s own object-literal span (`"var METAL_PRESETS = {"` to the first `"};"` after it) before matching the one metal's sub-block within it, so it can never touch anything else in the ~1600-line file.
- **`scene-tool.html`** itself — a single self-contained file (inline `<style>`/`<script type="module">`), not split into a separate JS file, mirroring how `auto-render.js`'s own `HARNESS_HTML` is one big inline string. One cascading selection (HDRI → Model [a flat list, `<optgroup>`-separated into every series' products and one "Metal swatch (sphere)" entry] → Metal) drives a single shared viewer built via `window.EmjiveModelViewer(product, metal, {freeOrbit: true, hdri, swatch: true, environmentBlur})` — see `client-scripts.md` for what `freeOrbit`/`swatch`/`target`/`dispose()` actually do. **Swatch mode** differs from product mode in what it lets you touch: the HDRI picker (starting on the saved `swatch-hdri`; it follows the mode, switching back to the series' own in product mode) plus a **Blur** slider and field (a gaussian, px of the HDRI image — released/committed values rebuild the viewer, since the environment is rebuilt), the Camera section with a **slider and a number field each** for rotation (−180…180), tilt (0…180) and roll (−180…180) — kept in step, the zoom hidden (the frame is solved) — the box being the swatch's own square frame (360px, not draggable: the sliders and fields are the camera), the Metal buttons re-tinting the one sphere while the shader sliders still re-tint live, and the "Camera" tick saving `swatch-camera` and the "HDRI" one saving `swatch-hdri` and `swatch-blur`. The product camera's rotation/tilt/roll now have sliders too, kept in step with dragging. In product mode, camera rotation/tilt/roll/zoom are both draggable (release and it stays exactly there, roll included — see `client-scripts.md`'s `options.freeOrbit`) and directly typeable (four number inputs, each skipped by the read-back loop while it has focus so live dragging can't fight your typing). Metal-shader sliders mutate `window.EmjiveModelViewer.METAL_PRESETS[metal]` in place and re-invoke `applyMetal()` for an instant, no-rebuild preview.

## `scripts/json-tool-server.js` + `json-tool.html`

A standalone dev page (`npm run json-tool`, port 5201, then open `json-tool.html`) for editing `data/series.json`'s global parameters (`featured`/`categories`/`hdris`/`metals`) and editing, adding, or removing a series or a product — including drag-and-drop for the hand-owned asset files (3D model, x-ray, extra photos). Written to replace the old "hand-edit `products.json`, get the folder-naming convention or the per-metal-map shape wrong, `auto-render` warns about it after the fact" workflow `procedures.md` used to be the only guide for — see that doc's "Adding a product"/"Adding a category"/"Adding a series" sections for the actual usage walkthrough; this section covers the tool's own architecture.

Four scope decisions worth knowing before reading the source, all enforced structurally rather than just by convention:

1. **No `auto-render` integration** — never shells out to it or touches Puppeteer/`sharp`. It only writes JSON + hand-owned asset files; regenerating icons stays a manual `npm run auto-render` (and the x-ray's other versions a manual `npm run image-variants`, which `npm run verify` insists on) afterward (see "Re-rendering icons and metal swatches" in `procedures.md`).
2. **Never writes `assets.icons`/`assets.fallback-img`/`assets.top-shot`, for any metal.** The UI has no upload slot for them at all (a plain reminder paragraph stands in their place instead), and the shared block-renderer (below) always copies those three per-metal maps verbatim from the current on-disk product rather than from form input — there's no code path here that could touch them even by accident.
3. **A new metal only ever touches the top-level `metals` array** (a removal also drops that metal's `metal-costs` entry). `js/three-viewer.js`'s `METAL_PRESETS`, `css/style.css`'s swatch rule and a new metal's `metal-costs` values are never written by this tool — adding a metal here shows an on-screen reminder about those still-manual edits (see "Choosing a product's metal" in `procedures.md`), same places that section has always described.
4. **Never edits a product's `geometry`.** `scripts/measure-models.js` owns it; `renderProductBlock` just carries it through from the current on-disk product, so any edit or cascade keeps it. A brand-new product has none until `npm run measure-models` runs (the add response says so, and `validate-data` fails until then), and replacing a model through the tool adds a warning to re-run it.

Deliberately a **third, completely separate** bare `http` server, same reasoning as `scene-tool-server.js`'s own header comment (mirrors `auto-render.js`'s proven bare-server pattern rather than tangling a dev-only save endpoint into `vite.config.js`). Never added to `vite.config.js`'s `build.rollupOptions.input`, so it's naturally absent from `npm run build`'s output, same as the other two tools. Unlike `scene-tool.html`, it has **no 3D preview at all** — no `three` import map, nothing like `scene-tool.html`'s live viewer — camera angle/HDRI/metal-shader/swatch-scene tuning all stay `scene-tool.html`'s job; this page's camera/HDRI fields are plain typed inputs with a footer pointer to `npm run scene-tool`.

- **`scripts/json-tool-blocks.js`** — a plain sibling module, pure functions only (no `fs`/`http`), so its output can be sanity-checked by eyeballing it against real file text without touching disk. Two families of helper:
  - `insertBeforeArrayClose`/`insertBeforeObjectClose`/`appendToInlineStringArray` (add) and `removeArrayEntryInText`/`removeObjectEntryInText`/`removeFromInlineStringArray` (remove) — genuinely new primitives beyond what `scene-tool-server.js`/`auto-render.js` ever needed, since those two only ever patch a field that already exists; this tool also has to grow or shrink a JSON collection (`products[]`, `series[]`, `categories{}`, `hdris{}`, `metals[]`). Bracket-depth counting (`findMatchingClose`) is string-aware, so a literal `]`/`}`/`"` inside a quoted value can never be mistaken for real structure. `removeObjectEntryInText` reconstructs the surviving entries from scratch (canonical spacing) rather than patching around the removed one's own comma in place; `removeArrayEntryInText` deletes exactly one adjacent comma (trailing if present, else leading) so the array stays valid regardless of whether the removed entry was first, middle, or last.
  - `renderProductBlock`/`renderSeriesBlock` — full-block renderers used for BOTH adding and editing a product (and for adding a series), so the two code paths can't drift into producing different formatting. Field order/shape mirrors the real hand-authored files exactly (see `data.md`). A product's `geometry` is likewise emitted only when present (right after `per-metal-specs`), and its `designs` (`renderDesignsBlock(designs, metals)`, after `assets`, the same canonical spacing as the rest: options one per line, each design's `picks` inline and its `geometry`, `model`, `wireframe`, `icons` and `fallback-img` below it) when it has them — the tool has no editing UI for them (they are hand-authored, written by `split-models`/`measure-models`/`auto-render`), only the round trip; renaming a product's folder moves its designs' model and wireframe files along with the rest (`handleProductEdit`). The optional `3d-viewer-camera-default.roll` is written only when the product already has one, so a rewrite (a photo change, the remove-metal cascade) never drops an authored roll and never adds `"roll": 0` to a product that omits it; `json-tool.html`'s roll input is left blank for such products for the same reason. `findBlockSpanByAnchor` locates a whole `{ ... }` block by a unique `"id"`/`"slug"` field inside it (walking back to the block's real opening `{` and forward to its real matching `}`, unlike `auto-render.js`'s/`scene-tool-server.js`'s own anchored patchers, which only ever need a span wide enough to regex a small field within) — what makes both full-block replacement (edit) and clean removal possible.
  - This repo's hand-aligned JSON columns aren't byte-for-byte consistent to begin with (confirmed directly — e.g. one product's `per-metal-specs` row has alignment spaces its sibling rows don't, another product's `top-shot` block is collapsed to one line where every other product's is multi-line), so this module targets clean, consistent, canonical spacing rather than chasing an exact reproduction of the source's own inconsistencies — accepted trade-off: saving any single field re-normalizes that *one product's* block spacing (never the rest of the file).
- **Destructive actions** (remove category/hdri/metal/series/product) sit behind the browser's native `confirm()` on the client, and a blocking check server-side wherever something else in the catalog still depends on it — a category/hdri still declared/used by a series or product, a metal still some product's `default-metal`, a series that's currently `featured`, either metals or series refusing to drop to zero. Removing a metal cascades: every product in every series gets its block re-rendered against the new (shorter) metals list, which — since `renderProductBlock` only ever emits keys for the metals it's given — is sufficient to strip that metal's key from `per-metal-specs`/`icons`/`fallback-img`/`top-shot` everywhere, with no separate per-object key-deletion step needed. Removing a series or a product deletes its real folders too (`assets/series/<slug>/`, `series/<slug>/`, `data/series/<slug>/` for a series; the one product folder under `assets/series/<slug>/products/` for a product) via `fs.rmSync(..., {recursive: true})`, guarded by a regex check on the computed folder path before any recursive delete — the same defense-in-depth `isAllowedAssetDestPath` already gives single-file writes, since a hand-corrupted `products.json`'s `name`/`category` could otherwise slugify into something path-traversal-shaped.
- **Replace/Remove pairs, immediate (not deferred to a Save button)** — shown only next to a file that's *already saved* (an existing model/xray/photo/HDRI), as opposed to the plain dropzones (used only when that slot is still empty, staged as pending until the next Save). Model/xray/photo Replace always writes to the *canonical* `<slug(name)>_{gltf,xray,photoN}.<ext>` path (deleting whatever was there before if it differs — e.g. a hand-exported `Foramen_gltf.glb`'s irregular capitalization doesn't survive a Replace, it becomes `foramen_gltf.glb`); a photo's Replace additionally keeps its array position (so it isn't just "remove + append," which would reorder the feed) and preserves that photo's `description` (below) — only `src` changes. HDRI Replace is the one exception — since an HDRI isn't named from a product/category, it just overwrites the exact existing `hdris[key]` path verbatim, no rename involved.
- **Each saved photo also gets a plain text input for `description`** (`assets.photos[i].description` — the name of the item on the photo, shown as the caption in its corner in the product page's feed, see `data.md`), immediate like Replace/Remove rather than staged for Save: `handleProductUpdatePhotoDescription` (`POST /api/product/update-photo-description`) matches the photo by its current `src`, re-renders, and writes. `renderProductBlock` itself always round-trips whatever's already in `assets.photos[i].description` regardless of what triggered the re-render — so an unrelated edit (price, name, ...) can never silently drop a caption someone already wrote, even though this tool has no dedicated bulk-editing UI for it.
- **File dispatch** reuses `auto-render.js`'s own `productFolder()`/`slug()` logic (from the product's *current* name+category, not wherever `assets.model` already points), so a dropped model/x-ray/photo lands at the same `assets/series/<slug>/products/<slug(name)>_<category>/` convention `assets.md` documents, under the same `<slug>_gltf.<ext>`/`<slug>_xray.<ext>`/`<Name>_photo<N>.<ext>` filenames a human would have hand-picked. Renaming a product (name or category) moves its existing model/xray/photos to the new folder (never the `icons`/`fallback-img`/`top-shot` `auto-render` owns — those are left behind, with a reminder to re-run `auto-render` there) and is blocked outright if that would collide with a different product's own folder.

## `loader-test.html` — the loader's review page

A standalone dev page at the repo root for reviewing the logo loader (`.loader` in `css/style.css`, animated by `js/loader.js`): timing, easing, size, and the invert. No server script — just open `/loader-test.html` under `npm run dev`. By default it shows five dashed boxes at real container sizes (phone card, desktop card, carousel tile, Modify poster, a wide strip), each with a loader that loops until you press its **Finish** button — which releases it the way a real asset does, so you can watch it wait out the cycle in progress; `/loader-test.html?page` shows the full-page arrival loader. Its loaders are mounted with `watchdog: false` so they loop indefinitely. Like `scene-tool.html` and `json-tool.html` it is **not** in `vite.config.js`'s `rollupOptions.input`, so `npm run build` never ships it (`<meta name="robots" content="noindex">` is there for good measure). Its markup is the reference for wherever a real loader gets mounted. Everything is tuned through the `.loader` custom properties — see `styling.md`'s Loader section.
