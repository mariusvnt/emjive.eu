# Client-side scripts

`js/` has 13 files, plus per-series hero bundles under `series/<slug>/`. 12 are plain classic scripts (`<script>` tags, no bundler needed to ship them). The 13th, `js/three-viewer.js`, is an ES module (`<script type="module">`, loaded from `<head>`) — it needs to `import` the `three` npm package, which only a module script can do. Despite the different script *kind*, it's fully part of the live site, not a dev-only file — see `tooling.md` for why an ES module is safe to mix into an otherwise-classic-script codebase, and `pages.md` for the exact load-order mechanics.

## Load order (see `pages.md` for the full page × script matrix and the `defer`/blocking explanation)

`js/scroll-memory.js` is blocking in `<head>` on `index.html` only, and is the **first** script on that page — ahead of `series.js` — because its height reservation has to be in place before `<body>` is parsed. `js/series.js` is blocking in `<head>` on every page, so `window.EmjiveSeries` and `window.EmjiveHero` exist before anything else runs — including `launch-order.html`'s plain synchronous `main.js`. `selection.js` always loads before anything that touches `window.EmjiveSelection`. `three-viewer.js` (a module, in `<head>`, on every page) always finishes before `main.js`/`product.js` (both `defer`), which touch `window.EmjiveModelViewer` at load; `modify-modal.js` touches it too, but only once a row has been tapped, so it needs no `defer`. The body order on every page is `main.js`, `focus-trap.js`, `selection.js`, `carousel.js`, `order-rows.js`, `modify-modal.js`, the page's own script, then `selection-bar.js` last — each builds on the ones before it (`series.html` slots `series-page.js` in straight after `main.js`). `focus-trap.js` is plain (non-deferred), so `window.EmjiveFocusTrap` exists before the whole deferred queue — which covers `product.js` (deferred) and everything synchronous with one placement.

A series' `hero.js` loads later still — injected at runtime by `series.js` — which is why it's written to be inert until called.

## `js/three-viewer.js` (~1440 lines) — the 3D viewer, and the largest file here

The single shared construction path for every 3D product view on the site (homepage grid cards, the product-detail carousel, the Modify sheet's small carousel) and for `scripts/auto-render.js`'s render pipeline — see `tooling.md`. A raw three.js scene per instance, driven by the `TrackballControls` addon (free, pole-crossing rotation — unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have), with a substantial amount of hand-tuned polish layered on top. Exports (all module-internal except the one exposed global):

- **One** module-scope `DRACOLoader` and **one** module-scope `GLTFLoader`, built once at module scope with the decoder attached once — not a fresh `GLTFLoader` per load. Unlike `loadEnvironment()`'s PMREM texture, neither holds per-context state, so one of each safely serves every viewer on the page. This is not a tidiness preference: a `DRACOLoader` per load is the single most-reported cause of Draco failing specifically on **iOS Safari** (three.js#22445, discourse#68835), because each instance spawns its own worker pool and its own WASM heap. Three further settings, all aimed at the same device:
  - `setDecoderPath(new URL("assets/draco/", document.baseURI).href)` — resolved **once, absolutely**, rather than left as the bare relative string `"assets/draco/"`. `DRACOLoader` resolves its paths against the *document*, which is fine while every page sits at the repo root and breaks silently — and only for Draco models — the moment one doesn't.
  - `setWorkerLimit(...)` — lowered from the default 4 to at most 2 (`hardwareConcurrency - 1`, capped). Every viewer here decodes exactly one model and the grid keeps only a handful alive, so extra workers can never be usefully busy; each one is just another structured-clone copy of the decoder config, `wasmBinary` included.
  - `preloadDracoDecoder()` — calls `dracoLoader.preload()` the first time any model load starts, so the decoder's ~336KB downloads *in parallel with* the `.glb` rather than serially after it. Guarded so pages that never show a model never pay for it.

  Three's own decoder files are self-hosted under `assets/draco/` rather than pulled from the Google CDN three.js's examples default to, so the site stays fully offline/no-external-requests — see `assets.md`. **Every** product `.glb` now ships `KHR_draco_mesh_compression`. Without a `DRACOLoader` attached, `GLTFLoader` doesn't degrade gracefully for a Draco model — it throws synchronously (`"THREE.GLTFLoader: No DRACOLoader instance provided."`), the load promise rejects, and the viewer's own fallback behavior makes that read as an inert, undraggable model with no visible error — exactly what happened the one time rib-cage/rib-cage-extended shipped ahead of this being wired up.
- `METAL_PRESETS` — PBR values (`baseColorFactor`/`metallicFactor`/`roughnessFactor`) per metal name, the single source of truth repo-wide (also reused by `scripts/auto-render.js`'s harness, since it loads this exact module). Must stay in sync with `data/series.json`'s top-level `metals` list — see `procedures.md`'s "adding a metal" checklist. `metalToStandardMaterialParams()` converts a preset to `THREE.MeshStandardMaterial` params. Also exposed live as `window.EmjiveModelViewer.METAL_PRESETS` (tool-only — `main.js`/`product.js` never read it) — `applyMetal()` and every viewer build already re-read `METAL_PRESETS[metalKey]` fresh on every call, so `scene-tool.html`'s shader-tuning sliders just mutate this object in place and re-invoke `applyMetal()`/rebuild to preview a change instantly, with no separate override-parameter path needed.
- `parseOrbitConfig()` / `parseTargetString()` — parse `product["3d-viewer-camera-default"]`'s `{ rotation, tilt, zoom, roll }` object (descriptive names for what used to be a single `"<theta>deg <phi>deg <radius%>"` string, the convention a `<model-viewer camera-orbit>` attribute would have used; `roll` — spin around the camera's own view axis — has no equivalent there, it's new) / `cameraTarget`'s `"Xm Ym Zm"` string format into the radians/percent the camera-framing math needs. `roll` defaults to 0 (level) when omitted, true of every product predating the field.
- `loadEnvironment(renderer, hdriSrc)` — loads + PMREM-converts an HDRI into an environment map. `hdriSrc` is the caller-resolved path (`data/series.json`'s top-level `hdris` map, looked up via a series' own `hdri` key by `js/series.js`'s `hdriPath()`, or `scripts/auto-render.js`'s own equivalent resolution — see `data.md`); an omitted/unresolved value falls back to the module's own `DEFAULT_HDRI_SRC` (`studio_kontrast_04_1k.hdr`) — this module is deliberately series-unaware, and `auto-render.js`'s headless harness never loads `js/series.js` at all, so it can't resolve a key here either way. Rebuilt fresh for every `buildThreeViewer()` call, never cached/shared across instances despite two viewers often resolving to the same file (any two showing series that picked the same `hdris` key): a PMREM texture is a GPU resource tied to the specific `WebGLRenderer`/context that built it, and each instance has its own renderer. An earlier version cached this at module scope, meant to be reused across the homepage grid's several simultaneous viewers — that handed later instances a texture handle from a different (invalid) context, which silently rendered them solid black, since this scene has zero `THREE.Light` objects and depends entirely on `scene.environment` for lighting. The PMREM step and the GPU upload therefore stay per-instance — but the *decode* no longer is: `loadHdrSource(src)` memoizes the loaded `DataTexture` per URL (sharing one in-flight promise, so N viewers appearing during one scroll trigger exactly one decode between them), and each call then wraps that one shared pixel buffer in a throwaway `DataTexture` purely so PMREM can upload it into *this* renderer's context, disposing the wrapper immediately after. Disposing a `DataTexture` frees the GPU copy and never the JS typed array behind it, so the cached source survives untouched. That removes N-1 fetches and, more importantly, N-1 RGBE→half-float decodes — tens of ms of main-thread work each, previously repeated once per grid card. A failed load evicts its own cache entry so a later viewer can retry rather than inherit a permanently-rejected promise. **That cache is dropped wholesale on `pagehide` and on `visibilitychange → hidden`** (`releaseHdrSources()`, skipped while a decode is in flight — clearing mid-load wouldn't cancel it, it would just guarantee the next caller starts a second one). What it costs is invisible in a heap profile, because a `DataTexture`'s pixels live in an external `ArrayBuffer` rather than the JS heap: Bones' `studio_kontrast_04_1k.hdr` is 1.4MB on the wire and decodes to 1024 × 512 half-float RGBA — ~4.2MB — held at module scope for the life of the document. (Both figures were 4× larger before `npm run optimize-hdri` halved the source; the cache mattered proportionally more then, and still earns its keep.) Worth every byte while viewers are being built and rebuilt during a scroll, and worth nothing once the page is frozen or backgrounded, which on iOS is exactly when the memory is wanted elsewhere; the price is one re-decode on the next viewer built after the visitor returns. `loadEnvironment` returns the whole **`WebGLRenderTarget`**, not just its `.texture` — `PMREMGenerator` hands target ownership to the caller (`pmremGenerator.dispose()` frees only the generator's own scratch resources), so disposing the texture alone would strand the target's framebuffer. The `HDRLoader` call has a real error callback (logs + rejects) — without one, a failed HDRI request used to leave the returned promise neither resolved nor rejected, silently hanging `Promise.all([modelPromise, environmentPromise])` below forever with zero console output.
- `buildThreeViewer(product, metalKey, options)` — builds one viewer instance: `WebGLRenderer` + `Scene` + `PerspectiveCamera` + `TrackballControls`, a `ResizeObserver`-driven canvas that always exactly fills its container, a poster `<img>` (sourced from `product.assets["fallback-img"][metalKey]` — see `data.md`) shown until the model's first frame renders, and — layered on top of the base rotation — release inertia (frame-rate-independent, re-derived from a continuous decay rate rather than assumed-60fps, with an added progressive-braking boost at low speed so a coast stops crisply instead of trailing off), a continuous two-attractor up-vector leveling drift (pulls toward the product's resting roll — see the roll paragraph under `options.freeOrbit` below — fades to zero at the poles, flips sign continuously through the equator rather than snapping), a bezier/slerp-based "ease back to the default pose" idle reset, and a 3-phase idle "nudge" hint (a small camera wiggle synchronized with a floating hand-shaped overlay — a plain `<div>`, not an `<img>`, whose visible pixels come entirely from a `backdrop-filter: invert(1)` clipped to `assets/hand-pointer-thumb-opened.svg`'s silhouette used as a CSS mask, so it reads as a color-inverted cutout of whatever's underneath rather than a fixed-color icon; see `styling.md`) — suppressed session-wide via `sessionStorage["emjive_model_interacted"]` once any instance has actually been dragged (a real drag, not just a tap — same 6px-distance-threshold pattern `main.js`'s click-navigation uses). Returns `{ el, applyMetal(newKey), setCameraOrbit(orbitConfig), target, dispose() }` — `setCameraOrbit` is an instant (non-animated) reposition, used by the render harness (see `tooling.md`) and by `scene-tool.html`'s rotation/tilt/roll/zoom fields; `target` (tool-only) is the live `controls.target` `Vector3` reference, needed to read a camera pose back as numbers (`scene-tool.html`'s whole reason for existing — nothing else in the codebase computes this inverse, roll included — see `options.freeOrbit` below); `dispose()` tears down the animate loop/`ResizeObserver`/`TrackballControls`' own `window`-level key listeners, disposes the loaded model's own geometry/materials and the HDRI environment's PMREM texture (real GPU memory, tied to this renderer's context — not freed by `renderer.dispose()` alone), then calls `renderer.dispose()` followed by `renderer.forceContextLoss()` — the latter is what actually returns the WebGL context to the browser's finite per-page budget, since `renderer.dispose()` alone only frees the renderer's own bookkeeping (shader program cache, render lists), not the context itself. Originally `scene-tool.html`-only (builds-and-replaces a viewer every time its HDRI/model selection changes, and without a real teardown each switch leaked all three) — `main.js`'s grid now calls it too, repeatedly, as cards scroll in and out of `disposeObserver`'s range (see its own section below), which is exactly why the geometry/environment/context-loss teardown was added: the original renderer/controls-only version would have leaked exactly the GPU memory that lazy build/dispose scheme exists to cap. Returns `null` instead, without throwing, if the browser can't grant a WebGL context (a finite per-page budget — several simultaneous viewers, bfcache-retained contexts from earlier navigations, a weak/mobile GPU) — `main.js` and `product.js` fall back to the plain `assets.icons[metalKey]` image in that case, same as a product with no `assets.model` field at all, and `modify-modal.js` keeps showing the `assets["fallback-img"]` image it opened on. Calls `controls.handleResize()` on every real resize (not just once at construction) — `TrackballControls` caches the element's screen rect itself rather than measuring fresh per pointer event, and at construction time the wrapper is still a detached `<div>` (the caller hasn't appended it to the page yet), so skipping this left `screen.width` permanently stuck at 0 and every drag silently a no-op (NaN rotation deltas, falsy, quietly skipped).
- `options.primitive` (tool/harness-only — `"cylinder"`/`"box"`/`"sphere"`/`"torus"`) — swaps the loaded GLTF for a bare `buildPrimitiveMesh()`-built mesh; everything downstream (`frameCamera()`'s bounding-sphere measurement, `applyMaterial()`'s mesh traversal, controls, the animate loop, `freeOrbit`, `dispose()`) is already agnostic to how `modelRoot` was built, so this is the only branch needed. `product` in this mode can be a minimal stub object — only `product["3d-viewer-camera-default"]`/`product.name`/`product.cameraTarget` are ever read, `product.assets` is never touched. Used by `scene-tool.html`'s swatch-scene mode and by `scripts/auto-render.js`'s swatch renderer (see `tooling.md`) — this **replaced** a separate `buildMaterialSwatch()` function that used to exist purely for that one purpose, retired once swatches needed the same draggable, savable camera orbit products already had (see `data.md`'s `swatch-camera`).
- `options.static` — harness-only (never set by the interactive site): skips the idle-nudge hint and the continuous per-frame animation loop entirely (only explicit `render()` calls, so nothing can shift the framing between the harness's `onReady` firing and its screenshot being taken a few ms later). One of those explicit calls is in `applySize()`: a resize wipes the canvas, and with no animate loop to consume `needsRender`, a static viewer repaints right there instead. That matters because the wrapper is still detached when the ready path's own render runs, so the `ResizeObserver` delivering the real size can land *after* it. Product renders never hit this (their model download always outlasts it), but a primitive swatch whose HDRI decode is already cached by the products rendered before it does. Without the repaint, every metal swatch from the HDRI cache's arrival (`9b2ec03`) until this fix was a fully transparent 240×240 WebP. The repaint is skipped for a viewer that's disposed or whose wrapper has left the page, since `auto-render.js` clears the body between renders without disconnecting old observers. `options.transparentBackground` — also harness-only, controls `preserveDrawingBuffer` (needed for an external screenshot readback of the canvas; the interactive site never reads its own canvas back). The renderer's alpha itself is unconditional now (both the interactive site and the harness render on a genuinely transparent canvas) — an earlier version kept the interactive site's canvas opaque on purpose to dodge a subtler ACES-tone-mapping edge-blending artifact, which traded it for a much more visible bug (a solid near-black square behind every model wherever the canvas wasn't covered by geometry).
- `options.freeOrbit` — `scene-tool.html`-only, wants the opposite trade-off from `static`: full interactive dragging (`static` never starts the animate loop at all, so a drag would be visually dead), but with release inertia and the idle-reset/leveling-drift/nudge behaviors above all switched off, so a dragged pose simply *stays* exactly where it's released — position **and** orientation, roll included — rather than coasting, easing back, or leveling out from under you. That's the whole point of a tool meant to let someone read a pose back as numbers: what you see is what gets saved, nothing about it drifts on its own while you're composing a shot. Three small, additive effects: sets `controls.staticMoving = true` (`TrackballControls`' own built-in "no momentum" flag, simpler than fighting the decay math that drives normal release inertia); skips arming the idle nudge (`scheduleIdleNudge()`'s guard); skips arming the "ease back to default" reset tween and the continuous up-vector leveling-drift correction (both gated individually inside the animate loop's normal-frame branch). `camera.lookAt(controls.target)` and the pole-crossing rotation itself (simply the *absence* of a polar clamp, not a separate mechanism — see below) are unaffected either way.

  Roll — the camera's orientation around its own view axis, 0 = level — is a real, savable part of `3d-viewer-camera-default` (`parseOrbitConfig()`'s `roll` field, defaulting to 0), not just an interactive-only side effect. `rotation`/`tilt`/`zoom` alone only ever encode the camera's *position* on the orbit sphere; `frameCamera()` derives `camera.up` via `restUpRaw(out, eyeDir, rollRad)` — the "level" reference (`WORLD_UP` projected perpendicular to the eye direction) rotated by `roll` around that same eye direction — so the *value* left in `camera.up`, not just the final `lookAt()`-derived orientation, genuinely encodes any authored roll. Exactly at a pole (tilt 0/180) that projection vanishes, and `frameCamera()` falls back to its limit along the orbit's own meridian, `(-cos(tilt)·sin(rotation), 0, -cos(tilt)·cos(rotation))`: at rotation 0 that's what `lookAt()`'s own parallel-up nudge used to produce, which matters because auto-render's top shots sit exactly on the pole (tilt 0) and the hero-hand overlays' rotations are tuned against that orientation — an arbitrary fallback axis was tried and turned every top shot 180°.

  The live site keeps the resting pose — roll included — as an exact fixed point of everything that moves the camera on its own. The "ease back to default" reset tween slerps `camera.up` toward `defaultCameraUp` (captured right after `frameCamera()`). The leveling drift and the idle nudge both rebuild their reference per frame from `restUpRaw()` with the product's `defaultRollRad`, for whatever eye direction they're at. For the drift, that reference is the attractor, left unnormalized (length = sin of the angle from the pole): at rest the tangent is exactly zero, so an authored roll holds instead of decaying toward level, and a roll-0 model doesn't churn `camera.up` along the view axis (invisible, but it defeated render-on-demand); away from rest, the roll-0 in-plane pull is identical to the old `WORLD_UP`-based one, sin² pole fade included. For the nudge, rebuilding up from the yawed eye is what keeps roll steady — a fixed up vector only stays roll-free under a yaw when it's literally `WORLD_UP`, and holding `defaultCameraUp` fixed wobbled roll by ~13° at a 28° tilt. Verified headlessly: at rest, eye and up hold within 1e-4 rad with zero redraws; through the full nudge, roll stays at its authored value; an injected off-rest roll drifts monotonically back to the authored value, not to 0. `TrackballControls`' own rotate step spins `.up` right along with the eye during a free-drag — exactly how `freeOrbit` composing a rolled shot by hand works — and `scene-tool.html`'s `readCurrentOrbit()` reads that roll back out via the same "level reference" projection in reverse (the signed angle, around the eye direction, from level to the camera's actual `.up`), the exact inverse of `frameCamera()`'s forward transform. For `roll: 0` (or omitted, the case for every product predating this field), the projected-vs-raw `WORLD_UP` distinction changes nothing about the final rendered orientation — `lookAt()` only ever uses the up hint's component perpendicular to the view direction, and the two differ by exactly a parallel component, whose cross product with the view direction is zero — so this is additive, not a behavior change for any existing render.

- `options.poster: false` / `options.maxPixelRatio` / `options.onReady` / `options.onError` — all four exist for `main.js`'s grid, where several viewers are alive at once. `poster: false` skips the built-in pre-load `<img>` entirely because the card already has its own image underneath doing that job; `maxPixelRatio` (1.5 on the grid, default 2 elsewhere) caps the canvas backing store, since **iOS Safari enforces a page-wide total canvas budget**, not a per-canvas one, and kills the tab once every canvas summed crosses it. `onReady`/`onError` fire once the model has loaded and painted, or once it definitively hasn't — the grid times its crossfade off the former and restores its static image on the latter. `onReady` predates both, added for `auto-render.js`'s screenshot timing.

### Teardown, and why it is load-bearing

`dispose()` is called constantly now — `main.js`'s grid disposes a card's viewer the moment it scrolls clear — so "was I torn down before this arrived?" is the normal case during a fast scroll, not an edge case. Three things this file gets right that are easy to regress:

1. **Both async load callbacks check `isDisposed` before touching anything**, and free what they were handed if it's set. A `.glb` arriving after teardown has its geometry disposed on the spot; a PMREM target likewise. Without that, a fast scroll leaked the full decoded geometry of everything it started but didn't finish, and — worse — the `Promise.all` ready path ran `renderer.render()` against a context `forceContextLoss()` had already killed, which is what filled the console with repeating `THREE.WebGLRenderer: Context Lost`.
2. **`dispose()` unregisters the viewer's `cancelNudge` from the module-level `allCancelNudgeFns` array, and removes its own `wrapper` pointer listeners.** Both are closures over the entire `buildThreeViewer()` invocation — renderer, scene, controls, decoded model — so either one left behind pins the whole viewer in memory no matter how diligently its GPU resources were freed. Measured on the Bones grid before this: **26 live `WebGLRenderer`s (and `Scene`s, and `TrackballControls`) retained after two scroll passes with zero viewers on screen**, growing linearly with every further pass. After: flat at whatever is actually visible. This is the kind of leak that reads as "iOS Safari reloads the page after a while" rather than as anything obviously wrong.
3. **`dispose()` is idempotent** — an early `if (isDisposed) return` — so a double dispose can't fire a second `forceContextLoss()` at a dead context.

### Render-on-demand

**Read the repaint triggers below before touching any of this.** The animate loop ends in `drawIfChanged()`, not an unconditional `renderer.render()`. It compares the camera's current eye direction and up vector against the pose the canvas currently *shows*, and skips the draw when both are within `STILL_ANGLE_EPSILON` (1e-4 rad, ~0.006° — far below one pixel at any canvas size here). A `needsRender` flag covers the changes that aren't camera motion: a resize, and `applyMetal()`. The `rAF` loop itself keeps running (it's nearly free, and it's what notices a drag starting); only the WebGL draw is skipped. Before this, a viewer that had finished loading and was sitting perfectly still still issued a full draw 60+ times a second forever — on the homepage, for every live card at once, producing pixels identical to the ones already on screen. The epsilon is deliberately *smaller* than `SETTLE_ANGULAR_VELOCITY * dt`, so a release always registers as settled (arming the ease-back-to-default) **before** drawing stops; the other order would strand the camera wherever inertia happened to fade out.

**The catch, and the reason `requestRepaint()` exists.** Skipping redundant draws is only safe while the canvas keeps what was last drawn into it. Every viewer is created with `preserveDrawingBuffer: false` (the default; only `auto-render.js`'s harness sets it true), which explicitly licenses the browser to throw the drawing buffer away after compositing — and iOS Safari does, under memory pressure, on tab/app backgrounding, and on a bfcache restore. **No `webglcontextlost` fires for this**: the context stays alive, only the pixels are gone, so `handleContextLost`'s icon fallback never triggers either. The old unconditional per-frame render hid it completely by repainting within ~16ms; with render-on-demand, an idle viewer that has settled never draws again and the blank canvas is permanent until reload. The easiest way to hit it is the most ordinary navigation there is: tap a product, press Back, and every model on the restored homepage is gone. So `requestRepaint()` (just `needsRender = true` — not a direct draw, because `rAF` is paused when these fire) is registered via `addGlobalListener` on `document`'s `visibilitychange`, `window`'s `pageshow`, and the canvas's own `webglcontextrestored`, and torn down with the rest in `dispose()`. Verified headlessly on a settled viewer: 0 draws while idle, then exactly 1 per trigger, and 0 after `dispose()` — that last number is what proves the listeners really came off shared targets.

Separately, `handleContextLost` treats a genuine `webglcontextlost` as a viewer failure and routes it through the same idempotent `reportError()` path an initial load failure uses, so `options.onError` fires for a model that *had* already loaded and was on screen — not just for one that never made it.

Free, pole-crossing rotation (unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have) isn't a dedicated function either — it's the *absence* of any clamp on `TrackballControls`' own rotation. The extra code on top handles the *consequences* of that freedom: the up-vector leveling drift (so "up" doesn't visibly flip the instant a spin crosses a pole) and the slerp-based (not lerp+normalize) reset/nudge tweens (a naive lerp cuts a visually-wrong-speed chord for a large-angle/near-antipodal sweep, which a pole-crossing spin can easily leave the camera at).

**Exposes**: `window.EmjiveModelViewer = buildThreeViewer` — consumed by `main.js`'s grid, `product.js`'s carousel, `modify-modal.js`'s small carousel, and (with `options.freeOrbit`/`options.primitive`) `scene-tool.html`, a standalone dev tool outside the built site entirely (see `tooling.md`). Also `window.EmjiveModelViewer.METAL_PRESETS`, see above.

## `js/series.js` (~350 lines) — series resolution

Loaded blocking in `<head>` on every page (see above). Fetches `data/series.json` once and exposes `window.EmjiveSeries`:

- `ready` — a promise resolving to `{ index, slug, series }`. **Everything else on the site hangs off this**; `main.js`, `product.js` and `series-page.js` all start from it rather than fetching any JSON path themselves.
- `slug`/`series` — the ACTIVE series: `?series=` if it names a real one, else `index.featured`.
- `metals` — the global metal list. `categories()` — the active series' own category subset. `categoryInfo(id)` — that category's `{ sizes, unit }` from the global vocabulary (only `unit` is read now — see `data.md`).
- `loadProducts(slug)` / `loadManifest(slug)` — **memoized per slug**, so the grid and the hero handoff share one request.
- `mainHref` / `manifestHref` / `productHref` — URL builders. They deliberately **omit `?series=` for the featured series**, so everyday URLs stay clean and links bookmarked before the refactor keep resolving.
- `requestedSlug()` — the raw `?series=` with no fallback applied. Only `series.html` uses it, so it can show a not-found state instead of silently rendering the featured series' manifest.

It also owns **hero bundle loading** on `index.html` (guarded on `#seriesHero` existing): inject the preload hints, inject the hero stylesheet, fetch the fragment and inject the hero script — all in flight at once — then clone each `<template data-series-slot>` into its slot, call `EmjiveSeriesHero.init()`, and hand the series' products to `onProducts()`. On failure it strips `body.has-series-hero` so the selection bar isn't stranded off-screen. See `pages.md` for the full contract and the anti-flash reasoning.

`window.EmjiveHero` lives here too — a plain function registry (`onScroll`/`publishScroll`), not a `CustomEvent`, because it fires once per animation frame during scroll and a registry costs no allocation per publish.

`window.EmjiveMenus` also lives here — click-away coordination for the header menu (`main.js`) and the selection-bar drawer (`selection-bar.js`), two panels that don't know about each other and can be open at once. Each registers `{ root, close() }` via `opened(panel)`/`closed(panel)` when its own open state changes; `root` spans both the panel's trigger and its content, so clicking the trigger itself is never mistaken for "away". `root` only needs a `contains(node)` method — the drawer passes an object whose `contains` also accepts anything inside `#modifyModal`, so a tap on the Modify sheet's backdrop closes the sheet but not the drawer it was opened from. A single `document` click listener here closes only the most-recently-opened panel when a click lands outside every currently-open one's `root` — a second outside click is needed to close the other if both happened to be open together.

## `series/<slug>/hero.js` — one per series

The hero's behavior, loaded at runtime. Assigns `window.EmjiveSeriesHero = { init(root, ctx), onProducts(products) }` and does nothing else at execution time. For Bones that means the frontier-band lift, the scroll-driven x-ray wipe, and `updateHeroRings()` — one `.reveal__ring` `<img>` per product with `hero-hand-visibility.visible: true` (see `data.md`), each positioned/sized/rotated via inline custom properties set from that product's own `hero-hand-visibility` object, so multiple rings on screen don't fight over one shared set. It gets the **full, unfiltered** product list: the rings are hero art, not a listing.

Two rules any hero bundle has to keep: no side effects at execution time (the loader parallelizes on that assumption), and no bare specifiers (Vite never sees this file, so `import "three"` would ship unresolved — call `window.EmjiveModelViewer` instead).

## `js/main.js` (~885 lines)

Loads on **every** page. Owns:

- The header hamburger menu toggle. A delegated click handler on `.site-header__row` also toggles it from anywhere in the row's empty space — same as the `+`/`-` icon — while ignoring clicks on the brand logo (which navigates home instead) or on `.menu-toggle` itself (which already has its own listener, and would double-toggle otherwise). Registers a panel with `window.EmjiveMenus` (`js/series.js`) so a click away from the whole header closes it too — see that file's doc above.
- The **category filter row** (`renderHeaderFilter()`), rendered from `EmjiveSeries.categories()` — the active series' own subset — so it renders identically on pages that load no product data at all. Dual-purpose, branching on `filtersAreInPlace` (`!!document.getElementById("productGrid")`, true only on `index.html`): on the grid page it's the real filter (label + one `.is-cat` tag per category when there's more than one, a single inert `.is-active` tag with no `href` when there's exactly one, hidden outright at zero); everywhere else it's unconditionally a plain `.is-info` "Gallery" link back to `index.html#products` via `EmjiveSeries.mainHref()`. `syncFilterButtons()` toggles `.is-active`/`aria-current` on whichever tags are in `activeCats` — `css/style.css` turns that into a dot, not a color change, the same recipe size/metal selection uses elsewhere. The menu-close handler is **delegated** to the menu container, because those buttons are created after the script runs; a per-link listener would never reach them.
- **Filtering** (`applyFilter`/`toggleCategory`/`setCategories`), on the grid page only. Multi-select toggles that hide already-built cards, sync `?cat=` via `history.replaceState`, and leave the menu open so successive toggles are usable. Elsewhere the same buttons are ordinary links that navigate to the grid with one category applied. Unknown `?cat=` values are dropped against the active series' categories, so a typo shows everything rather than nothing.
- `wireModelClickNavigation(el, href)` — the 6px drag-distance-threshold click-vs-drag disambiguation, attached to a viewer's wrapper so rotating a model doesn't accidentally navigate. Wired inside `startViewerLoad` now (see below), at the point a card's viewer actually gets built, rather than unconditionally in `buildCard`. Tracks `activePointerId` so a `pointerup` that never had a matching `pointerdown` on this element — a drag begun on the page background and released over a card, or a second finger lifting during a two-finger scroll — is ignored rather than measured against stale (initially `0,0`) coordinates, which read as a zero-distance "click" and navigated to a product nobody tapped.
- The grid rendering (`buildCard`/`renderProducts`) — one card per product from `EmjiveSeries.loadProducts()`. Cards are built **once** and kept in a module-scope array; see the WebGL note in `pages.md` for why filtering must never rebuild them.
- **Lazy viewer build/dispose** (two `IntersectionObserver`s feeding one `reconcileViewers()`) — `buildCard` no longer calls `window.EmjiveModelViewer` itself; it always builds the card's placeholder `<img>` first and returns `{ el, figure, iconEl, href }`, which `renderProducts` wraps into a `{ product, el, figure, iconEl, href, modelHandle, wantsViewer, queued, fadeTimer, releaseSlot }` entry and hands to both observers (`figure.cardEntry = entry` is how each observer's callback finds its way back to that state). `buildObserver` (`rootMargin: "150px 0px 150px 0px"`) marks a card `wantsViewer` once its figure nears the viewport; `disposeObserver` (`"300px 0px 300px 0px"` — deliberately larger, for hysteresis, so a card doesn't thrash build/dispose right at one boundary) calls `disposeViewerFor` once it's scrolled well clear. Falls back to eagerly building every viewer up front (the old behavior) if `IntersectionObserver` doesn't exist at all.
  **The observers only decide which cards are in *range*; `reconcileViewers()` decides which of those are worth the memory.** It sorts every `wantsViewer` card by distance from the viewport centre, builds the nearest `MAX_LIVE_VIEWERS` (**3**) and evicts the rest. `evictViewer` drops the viewer and its queue place but leaves `wantsViewer` set, so a card demoted by the ceiling comes straight back when a slot frees — that's the whole difference from `disposeViewerFor`, which means "out of range entirely". A ceiling is needed *on top of* the margins because the margins bound a **distance**, not a count: how many cards fall inside one is a function of viewport height and card pitch, and on a phone (measured back when the figure had a 210px floor: + the 8rem mobile row gap = a 338px pitch, inside an 860px viewport plus 300px of dispose margin each side) that came to **five at once** — the phone figure has since shrunk to exactly half the row (`calc(50vw - var(--edge-px))`, ~177px on a 393px-wide phone, see `styling.md`), which only packs more cards into the same range, each with its own WebGL context, decoded model and — the expensive part — its own PMREM environment target, which cannot be shared across renderers (see `loadEnvironment` above). Three covers everything genuinely on screen at any realistic viewport plus one for the direction of travel; the trade is a very tall narrow window, where a fourth on-screen card sits on its icon.
  **Scheduling** (`scheduleReconcile`, `RECONCILE_INTERVAL_MS = 250`) — both observers, the `scroll`/`resize` listeners, `applyFilter` and `pumpLoadQueue` all funnel through it. The scroll listener is not optional: neither observer fires while a card merely moves *within* its margins, so without it a card held back by the ceiling on the way in would stay on its icon all the way past the middle of the screen. It's a **timer, deliberately not `requestAnimationFrame`**, with the pending timer's own handle as the "already scheduled" flag (cleared as the callback's first statement, so no separate boolean can be stranded by a reconcile that threw). rAF looks like the obvious fit for something driven by scrolling and is the wrong choice: it only fires while the page is producing frames, so a reconcile armed just as the compositor goes idle sits unfired and every later scroll returns early against it — measured at **0–3 rAF callbacks across a six-second idle window where `setTimeout` ticked ~350 times**, with the visible symptom being cards stopping mid-screen on their icons, wanting a viewer, nothing in flight and nothing queued.
  **Freezing** (`releaseAllViewers` on `pagehide`, `rebuildViewersInRange` on `pageshow` with `event.persisted`) — navigating to a product doesn't end this page; both browsers this site cares about put it in the back/forward cache, and a bfcached document is a **live** document, holding every renderer, model and PMREM target while `product.html` builds its own on top. Even under the ceiling that's four at once across the two pages, against an iOS Safari budget that is a page-wide total. The rebuild **re-observes** every figure rather than calling `buildViewerFor` directly: both observers only fire on a threshold crossing and no crossing happens while the page is frozen, so without it every card would sit on its icon until the visitor scrolled far enough to cross a margin. `product.js` does the same from the other end of that navigation — see its section below.
  **Which placeholder image, and why it isn't the icon.** The card shows `assets["fallback-img"][defaultMetal]` when the product has a model, falling back to `assets.icons[...]` only when it doesn't. These are **not** interchangeable: `auto-render.js` trims `icons` to their own alpha bounding box and rescales that to a fixed 80% of the frame (`ICON_CONTENT_FRACTION`) so thumbnails read consistently next to each other — deliberate, and exactly wrong here, because a thin ring's silhouette is far smaller than the bounding *sphere* `frameCamera()` fits to the viewport. Measured on Furcula: the icon drew the ring **1.232× larger** than the live model in both axes and re-centred it ~6% horizontally, so the handover read as the model snapping smaller and sideways the instant it appeared. `fallback-img` is the same capture saved *without* that treatment and matches the live canvas to **0.999× wide / 0.997× tall, centre within 0.1%** — i.e. invisibly. This is the whole reason `fallback-img` exists as a separate asset (see `assets.md`).
  **Load concurrency** (`MAX_CONCURRENT_MODEL_LOADS = 2`, `loadQueue`, `pumpLoadQueue`) — lazy building bounds how many viewers *exist*, not how many start loading at once, and a brisk scroll crosses every card's build margin within a second or two. Capping it means cards resolve one after another in the order they were scrolled past, rather than every model finishing late together with bandwidth split N ways. `entry.wantsViewer` (set by `buildObserver`, cleared by `disposeObserver`) lets `pumpLoadQueue` **drop** queued cards that scrolled back out before their turn came, instead of fetching a model nobody is looking at any more; it also schedules a reconcile afterwards, since the queue is FIFO and knows nothing about where the viewport is now — an entry queued three screens ago can otherwise reach the front long after a nearer card started wanting one.
  **`entry.releaseSlot`, and the bug it closes.** A slot is claimed in `startViewerLoad` and returned by `releaseSlot`, which only ever ran from `onReady`, `onError`, or a refused WebGL context. A dispose landing **mid-load** is the one way a viewer settles without either callback firing — `three-viewer.js` guards its whole ready path on `isDisposed`, and `reportError()` on `isDisposed` too — so a card scrolled past while its model was still downloading silently kept the slot it had taken. Two of those (it's a two-slot pipeline) and the grid **stopped loading models for the rest of the page's life**: every later card queued behind a counter that could never come back down, showing its icon forever with nothing in the console to say why. `startViewerLoad` now hands its `releaseSlot` to the entry and `teardownViewer` calls it — last, since `pumpLoadQueue` inside it can start the next viewer synchronously, and a no-op on the `onError` path where it already ran.
  **The crossfade** — the viewer is mounted at `opacity: 0` and faded in over `MODEL_FADE_MS` (400ms) from `onReady`; the placeholder is only taken out of the layout once that fade completes (hiding it mid-fade would show the page background through the model's transparent areas). `disposeViewerFor` clears that pending timer, so a card disposed mid-crossfade puts its image back correctly. Combined with `poster: false`, the card shows exactly one image at a time throughout.
  Exists because building every product's viewer — a `WebGLRenderer`, a full glTF fetch/decode, a from-scratch HDRI PMREM build, each — unconditionally and instantly the moment the grid rendered stopped being safe once the catalog grew past a handful of products: eight bones products at up to several tens of MB each meant eight simultaneous WebGL contexts, eight HDRI builds, and over 100MB of glTF data all at once on page load, reported as the page reloading erratically on scroll and crashing outright (Chrome's repeated-crash page) on real devices. Verified headlessly (a scripted scroll through the real page, not visual inspection): peak simultaneous viewers capped around 5 of 8 (was: all 8 instantly), zero models fetched before scrolling anywhere near the grid (was: ~100MB at page load), and a disposed card's viewer correctly rebuilds if scrolled back to.
  **`css/style.css`'s `.product-card__figure > img[hidden]` rule is load-bearing for this** — see `styling.md`. Toggling `.hidden` on the icon is a new use of that attribute here; without the matching CSS override, the base `img { display: block; }` rule (author-origin, beats the UA `[hidden]` regardless of specificity) left the "hidden" icon still laid out and pointer-interactive on top of the canvas, silently swallowing every drag meant for the model — confirmed via `elementsFromPoint` and `TrackballControls`' `_pointers` count staying 0 after a simulated `pointerdown`.
- **Lending a WebGL slot to the Modify sheet** — the sheet (`modify-modal.js`) can open over the homepage grid from the floating bar's drawer and builds a viewer of its own. On `emjive:modify-open` the grid's ceiling (`liveViewerCeiling`, normally `MAX_LIVE_VIEWERS`) drops by one and `reconcileViewers()` runs **immediately**, not scheduled, so a grid viewer is gone before the sheet's arrives and the page never holds four contexts at once (the iOS budget is page-wide). `emjive:modify-close` — dispatched only once the sheet's viewer has actually been disposed, after its slide-out — restores the ceiling and schedules a reconcile. Both listeners only exist on the grid page, and only when lazy viewers are supported.
- A guarded contact-form stub (`getElementById("contactForm")`) — a no-op, since no page has that element. Kept for whenever a contact form gets built (see `procedures.md`).

Owns **no hero logic at all** any more, and no `METAL_PRESETS` or viewer-construction logic — those live in the active series' hero bundle and `js/three-viewer.js` respectively. `main.js` is purely a consumer of both.

## `js/scroll-memory.js` (~375 lines) — back-navigation scroll memory

`index.html` **only**, blocking in `<head>`, first script on the page. Makes Back return to the gallery exactly where the visitor left it: right offset on the first painted frame, no jump, no smooth-scroll travel, no blank hold.

**Why the browser can't do this itself.** At first paint `index.html` is almost empty — `#seriesHero` is an empty div held at `min-height: 100svh` and `#productGrid` holds one "Loading specimens…" line. The real height only arrives after three async hops: `data/series.json`, the hero bundle (whose `hero.css` sets `.reveal { height: 200vh }`), then that series' `products.json` rendered by `main.js`. Native scroll restoration runs long before any of that, against a document a fraction of its final height, so the offset clamps to near zero and the visitor lands at the top. Every other page builds its height synchronously from markup, which is why this is scoped to one page — elsewhere it would be a second opinion fighting a working one.

- **Per-history-entry key.** A token minted into `history.state` as `emjiveScrollKey`; the position itself lives in `sessionStorage` under `"emjive:scroll:" + key` as `{ y, h }`. Keyed off the *entry*, not the URL, because one session can hold two `index.html` entries at different offsets and a URL key would let the second overwrite the first. The value is in `sessionStorage` rather than `history.state` because saving means writing on every scroll and Safari rate-limits `replaceState` hard enough to throw. **`main.js`'s `syncFilterUrl()` must keep passing `history.state` back through its `replaceState`** — it used to pass `null`, which discarded the token on every category toggle.
- **Saving** — `window.scrollY` plus `documentElement.scrollHeight` on `pagehide`, on `visibilitychange → hidden`, and on a ~300ms-throttled `scroll` listener as the crash/OOM net. Suppressed while a restore is in flight, so a mid-restore `scrollY` of 0 can't overwrite a good value.
- **Restoring (fresh load)** — `history.scrollRestoration = "manual"` (per-entry, so it doesn't leak to other pages), then the saved height is set as `--emjive-restore-height` inline on `<html>` and `emjive-restoring-scroll` added, all from the head script *before `<body>` is parsed*. `css/style.css` turns that into a `min-height` on `body`, so the offset is reachable immediately; `applyScroll()` then runs in the first `requestAnimationFrame` that has a `document.body`, and rAF callbacks run **before** the frame they belong to is painted, so no wrong-offset frame is ever presented. The loop keeps re-asserting while the hero and grid land.
- **Restoring (bfcache)** — `pageshow` with `event.persisted`: the DOM and height come back intact, so it just calls `applyScroll()` synchronously. Needed because `"manual"` opts out of the UA's traversal restore too.
- **`contentReady()`** — called by `main.js` once the grid is rendered *and* filtered (the last thing that changes this page's height), and also from its `.catch`, so a failed products fetch releases the restore immediately instead of waiting out the deadline. It waits for `scrollHeight` to reach the reservation, then races the on-screen cards' placeholder decodes plus `document.fonts.ready` against a ~250ms grace, then reveals. Two frames, not one, before revealing — the first lets the hero's own scroll handler and `selection-bar.js` react to the restored offset, so the x-ray wipe and the floating bar are already in step on the frame the grid appears.

**Three things that had to be defused, all of which will re-break this if changed:**

1. `html { scroll-behavior: smooth }` (`css/style.css`) would make `scrollTo` **animate** — i.e. exactly the visible "scrolling back to where you were" this file exists to avoid. `applyScroll()` overrides it inline around the call; `behavior: "instant"` is belt-and-braces, wrapped because a browser predating that enum value throws on it.
2. **Scroll anchoring** would shift the offset as the hero grows `100svh → 200vh` *above* the restored position — correct in general, wrong here, where an absolute offset is the thing being preserved. Hence `overflow-anchor: none` in the restore CSS.
3. The first `wheel`/`touchstart`/`pointerdown`/`keydown` (capture phase, so a canvas handler that stops propagation can't hide it) sets `userTookOver`, which stops the re-assert loop but deliberately **does not** end the restore window — dropping the height reservation early would collapse the document under the visitor and yank the scroll, the same jerk this prevents, just triggered by their own input.

**Failsafes**, none of which may ever leave the page stuck: a `setTimeout(endRestore, ~1200)` armed at script execution, so a JS error anywhere else still releases the reservation; an idempotent `endRestore()`; and guards on `"scrollRestoration" in history`, on `replaceState`, and on `sessionStorage` access (which throws outright in Safari private mode) — any failure degrades to the browser's own behaviour.

**Exposes**: `window.EmjiveScrollMemory = { isRestoring(), contentReady() }`, consumed only by `main.js`.

## `js/selection.js` (~235 lines)

The cart/selection data layer — a thin `localStorage` wrapper. `STORAGE_KEY = "emjive_selection"`. `readAll()` falls back to `[]` on any read error (e.g. corrupted JSON). `writeAll()` never throws: if `setItem` fails (storage blocked outright, as Safari does with all site data blocked, or over quota), the list moves into an in-memory copy (`memoryItems`) that `readAll()` serves instead, so the bar and order page still show the change and the index-based mutators below keep acting on the list that's on screen. The next successful write clears it and hands the selection back to `localStorage`. That copy lasts only as long as the page does — it can't follow the visitor to the next one. Every mutating call dispatches `new CustomEvent("emjive:selection-changed", { detail: { action, index } })` on `window`, **synchronously**, from inside the call — the sole mechanism other scripts use to react live to a change without a page reload. `action` is `"add"`/`"remove"`/`"insert"`/`"update"`/`"clear"`; it's how `selection-bar.js` tells an Undo's insert (its icon plays the collapse in reverse) from an Add's (its icon slides in from the edge), and how `selection-page.js` knows a Save happened.

Four mutators, all index-based (an item's position in the stored array, not an id): `addItem(item)` (pushes to the end — `product.js`'s Add), `removeItem(index)` (splices it out — the Modify sheet's Unselect), `insertItem(index, item)` (splices it back in at a specific position — the Modify sheet's Undo, so a restored item lands back where it was rather than at the end the way `addItem` would), and `updateItem(index, patch)` (`Object.assign`s `patch` onto the existing item in place — the Modify sheet's Save, changing metal/size and the price and icon that come with them without moving the item).

**Sizes** — the rules both size fields (`product.js`'s sheet and the Modify sheet) share, so the two can't drift apart: `sanitizeSizeInput(raw)` is the keystroke filter (comma → dot for comma-decimal keypads, digits and one dot, at most two decimals); `normalizeSize(raw)` is the one form a size is stored in (`"62."` → `"62"`, `"62.5"` → `"62.50"`, `".5"` → `"0.50"`, leading zeros dropped, `""` for no digits); `isValidSize(raw)` — non-empty and above zero — is what gates Add and Save. `appendSize(parent, size)` appends a size value to `parent` as plain text, except a decimal size's fractional part — that renders in a `.size-fraction` span (`css/style.css`, `font-size: 0.75em`), always two digits (padded for carts saved before `normalizeSize` existed), instead of as a literal `.`, since every row that shows a size joins `.category.metal.size` with literal dots, and a decimal point in the size itself would read as a fourth trait segment.

**Diffing** — `itemKey(item)` (`series|productId|metal|size`, tolerating a missing `series`) and `singleChange(oldKeys, keys)`, which says whether a change from one list of keys to the next was a single insert, remove or in-place update (and at which index), or `null` for anything else. Shared by `selection-bar.js`'s icon strip and `order-rows.js`, so both animate exactly the one thing that changed.

**Exposes**: `window.EmjiveSelection = { getSelection, addItem, removeItem, insertItem, updateItem, clear, formatPrice, sanitizeSizeInput, normalizeSize, isValidSize, appendSize, itemKey, singleChange }`.

**Item shape**: `{ series, productId, name, category, metal, size, price, image }` — a deliberately self-contained snapshot, so `launch-order.html` never has to re-fetch or join against any products file to render itself. `series` is what makes `productId` meaningful, since ids are only unique within one series. Selections saved before that field existed simply lack it; `itemKey()` tolerates it being absent so an existing cart doesn't read as all-new.

## `js/focus-trap.js` (~290 lines) — the two sheets' keyboard containment, and the page lock

Loaded on **all seven pages**, since every page can open the Modify sheet. Not folded into `js/series.js` despite that file already hosting two non-series globals: `series.js` is blocking in `<head>`, and nothing here needs to be.

**Exposes**: `window.EmjiveFocusTrap = { activate(root, options), release(focusTarget), focus(target) }`. `options` is `{ include, returnFocus, fallbackFocus, initialFocus, onEscape }`, all optional. `release(focusTarget)` sends focus somewhere other than `returnFocus` (the Modify sheet sends it to the bar's Undo after an Unselect); `focus(target)` moves focus the same way `release()` hands it back, for moves that aren't a release (an Undo resolving).

Load-bearing rather than incidental:

- **The trap root is `.size-modal`, never `.size-modal__panel`.** On `#modifyModal` the small carousel is a *sibling* of the panel, not a child — a panel-scoped trap would leave part of the dialog outside itself. Both sheets carry `role="dialog"`/`aria-modal`/`aria-label`/`tabindex="-1"` on `.size-modal`: a screen reader honouring `aria-modal` hides everything outside the declared dialog.
- **`include`** — elements outside the root whose controls count as inside the trap: the Modify sheet's buttons live in the page's bar (its strip), so the sheet passes that. Every Tab is moved by hand, wrapping at both ends, across root then include, since the browser's own Tab order would never step between two separate parts of the document. Focus landing on an included element isn't pulled back. `focusable()` skips anything inside `[inert]`.
- **`returnFocus` may be a function**, resolved at `release()` time rather than at `activate()` — the thing that opened a sheet can be gone by the time it closes (a row whose item was just unselected, a list that emptied). Both list pages pass a lookup by index plus a `fallbackFocus`.
- **Candidates are re-queried on every Tab**, never cached: the Modify sheet rebuilds its metal buttons and carousel slides per open, and Save toggles `disabled` live.
- **Escape lives here**, registered on `activate` and removed on `release`. One listener means Tab and Escape can't disagree about whether a sheet is open.
- **Focus handed back after a tap draws no ring.** Programmatic focus inherits `:focus-visible` from the element focus came from, and the size field (a text input) always matches it — so a row refocused after typing in the field and tapping Save would get a ring around it. A capture-phase `pointerdown`/`keydown` tracker records the last input; focus handed back right after a pointer input gets `.is-focus-quiet` (`css/style.css` drops the ring for it) until that element blurs or a key is pressed.
- **The root it focuses on open must never be given a position by a focus style.** It's focused so the dialog's label is announced, and iOS Safari counts the first scripted focus after a page load as `:focus-visible`; the site-wide ring rule used to set `position: relative` on anything with a `tabindex`, which turned the fixed sheet relative and dropped it to the end of the page, out of sight and untouchable. See `styling.md`'s focus section.

**The page lock** is here too: `activate()` locks and `release()` unlocks, since every modal on the site freezes the page behind it. `html.is-modal-open` (`css/style.css`) sets `overflow: hidden` on `<html>`, not `<body>` — `html` carries `overflow-x: hidden`, and once `html`'s overflow isn't `visible`, `body`'s own overflow no longer reaches the viewport (the `body`-level lock this replaced never worked). The scroll position doesn't move, so nothing driven by it (the homepage bar's scroll-linked reveal) does either. Where scrollbars take up room (Windows), hiding the page's would widen everything behind the backdrop by its width, so its width is published as `--page-scrollbar` and given back as padding on `<html>` and on the fixed bars and header. (`scrollbar-gutter: stable` would be tidier, but Chrome doesn't keep the root's gutter once its overflow is hidden.)

A closed modal needs no handling: `.size-modal` is `visibility: hidden`, `visibility` inherits, nothing inside redeclares it, and an element whose computed `visibility` isn't `visible` is excluded from sequential focus navigation.

## `js/product.js` (~550 lines)

Owns `product.html` end to end. Resolves `?id=` via `findProduct()` — the active series first, then a scan of the remaining series in index order (each memoized), which is what keeps bare `?id=` bookmarks working now that ids are only unique per series. Then renders (by the file's own numbered section comments):

1. **Label** — name, category, per-metal thumbnail, price.
2. **Carousel** — builds the slides into `#productCarousel` (a 3D viewer via `window.EmjiveModelViewer` if `product.assets.model` is set, else a fallback icon image, then any `product.assets.photos`) and calls `carousel.sync(true)` right after `#productDetailContent` is unhidden, since `[hidden]` elements measure zero. The dragging, paging and tap-to-center behaviour is `js/carousel.js`'s (see below) — the Modify sheet's small carousel runs the same code. Each photo slide (`buildPhotoSlide()`, built on `EmjiveCarousel.imageSlide()`) also renders a `.product-carousel__caption` naming which finish/context that shot depicts — `"On display: " + (photo.description || "—")`. The caption is a real sibling of the `<img>`, not an overlay on top of it: it's absolutely positioned to the slide's own bottom-right corner, in extra height `css/style.css`'s `.product-carousel--has-photos` reserves below `--tile` on the viewport (toggled by `renderCarousel()` whenever `product.assets.photos` is non-empty) — done this way, rather than shrinking the photo's own box to fit a caption inside it, so every photo still fills `--tile` edge-to-edge and stays flush against its neighbors in the filmstrip.
3. **Metal picker** — re-tints the live 3D model in place via `state.modelHandle.applyMetal(metal)` (no reload, no camera reset), and separately updates the label thumbnail/fallback icon/specs/price, since only the 3D model re-tints itself automatically.
4. **Characteristics** — metal-dependent weight/composition/price from `product["per-metal-specs"][selectedMetal]`.
5. **Select button + size sheet** — the unit is looked up by *category* (not per-product) via `EmjiveSeries.categoryInfo()`; a category without one disables the button ("No sizes available"). Because that vocabulary is global rather than per-series, a cross-series hit needs no re-hydration. `#sizeModal` is a `size-modal--drawer` bottom sheet resting right above the floating selection bar — see `styling.md`. Its one control is the typed size field ("Custom size"), filtered on every keystroke by `EmjiveSelection.sanitizeSizeInput()` (two decimals at most; a comma-decimal keypad's `,` becomes `.`), with the "Size guide" toggle as its own row underneath.

   There's no confirm button inside the sheet. While the field holds an orderable size (`EmjiveSelection.isValidSize()`), `syncAddAction()` calls `window.EmjiveSelectionBar.showAction("Add", confirmAdd)`, handing the actual "add to cart" action to the bar itself (see `js/selection-bar.js` below); emptied or invalid, `hideAction()`. **Enter** in the field adds too — the bar sits outside the focus trap, so without it a keyboard visitor could type a size and have no way to add it. `confirmAdd()` calls `EmjiveSelection.addItem({...})` with the self-contained snapshot (the resolved series included, the size through `normalizeSize()`) and then `closeModal()`, which always calls `hideAction()` in turn — covering both a successful add and an abandoned one (backdrop click/Escape) with the one line. Every `window.EmjiveSelectionBar` call is guarded (`if (window.EmjiveSelectionBar) …`), this file's convention for cross-file globals. On `emjive:modify-open` the sheet closes itself: the drawer can still be opened over it, and a drawer row's Modify must not stack a second sheet on top.

All page state lives in one `state` object (product, metals, selected metal, the live model handle, the icon-fallback image).

**The carousel viewer's failure and freeze paths** (both inside `renderCarousel`, and easy to confuse):

- `onError → replaceModelSlideWithIcon()` is the **permanent** fallback, for an initial load/HDRI failure or a later WebGL context loss (see `three-viewer.js`'s `handleContextLost`). It swaps the failed slide's contents for the same icon a model-less product gets, **in place** — the slide keeps its place in the track (`slideSources`), which is what the carousel's geometry is built on, so a failure arriving long after the carousel was measured and scrolled can't desync it. It reuses `state.iconFallbackImg`, so `onMetalSelect`'s existing swap branch handles a later metal switch with no extra wiring. Before this existed, either failure left a permanently blank 3D slide with nothing telling the visitor anything was wrong.
- `releaseModelViewer()` on `pagehide` / `restoreModelViewer()` on `pageshow` with `event.persisted` is the **reversible** one, and the mirror of `main.js`'s `releaseAllViewers` from the other end of the same navigation: pressing Back doesn't end this page, it goes into the back/forward cache still holding its WebGL context, decoded model and PMREM target while the grid rebuilds several of its own. `restoreModelViewer` rebuilds via `buildModelViewer()` (factored out of the original assignment; it reads `state.selectedMetal` at call time, so it picks up whatever metal is selected *now*) and **bails if the slide has lost `.product-carousel__slide--model`** — that class disappearing is exactly the `replaceModelSlideWithIcon` case, where a rebuilt viewer would be an invisible second context underneath the icon the visitor is looking at.

## `js/carousel.js` (~370 lines) — the carousels' dragging and paging

Moved out of `product.js` when the Modify sheet grew a small carousel of its own, so both run the same code. **Exposes** `window.EmjiveCarousel(carouselEl)` → `{ sync(reset) }`, plus `EmjiveCarousel.imageSlide(src, alt)` — a plain full-bleed `<img>` slide, `draggable = false`. The caller builds slides into `.product-carousel__track` and calls `sync(true)` once they're in and visible — it re-counts the slides from the track and centers the first; a resize re-clamps on its own.

No rim/arrow click zones: navigation is either a free horizontal drag (rubber-band overshoot past either end; release lands exactly where the drag left it, clamped back into bounds — no momentum coast) or a tap directly on a slide, which centers it (`centerOnSlide()`) however far from center it started. On a narrow/phone-width viewport (`isMobileCarousel()` — the one existing `max-width: 640px` breakpoint) a real drag instead always pages exactly one slide forward/backward and centers it, committing only past a real drag distance (15% of a tile) or a fast-enough short flick (gated by a minimum distance too, so touch-event jitter on a barely-moved drag can't read as a flick) — short/slow drags spring back to the slide they started on. A pointer's horizontal-vs-vertical intent is axis-locked in `onPointerMove` (the first movement past a small slop decides it, once) so a vertical scroll starting on the strip is handed off untouched to the browser's own `touch-action: pan-y`; `pointercancel` (the browser interrupting a pointer itself — that same scroll handoff is the common case) is handled separately from a clean `pointerup` so an interrupted gesture is never misread as a tap. Every way a slide gets centered shares one symmetric ease-in-out transition (`CENTER_TRANSITION`; `CANCEL_TRANSITION` is the same curve, shorter, used only when a mobile drag springs back). Bounds stay "first/last tile centered" (not edge-flush).

The drag's pointer is captured on the **track**, not the viewport: in the Modify sheet only the track takes pointer events (the empty band beside the slides lets a tap through to the sheet's backdrop), so a capture on the viewport would lose the drag.

**Notable gotchas** (from the file's own comments): `img.draggable = false` + `dragstart` prevention stops the browser's native image-drag gesture from fighting the custom pointer-drag scroll; a `pointercancel` doesn't reliably carry the pointer's final coordinates, so settling a drag interrupted mid-gesture falls back to the strip's own live position instead of the event's `clientX`; a drag that starts inside `.emjive-3d-viewer` is left alone entirely (no `pointerdown` tracking at all) so it rotates the model via `TrackballControls` instead of paging the carousel.

## `js/order-rows.js` (~355 lines) — the item rows, in every list

The rows `launch-order.html`'s order list and the floating bar's drawer share (`selection-page.js`, `selection-bar.js`) — and the copy in the order page's drawer over its checkout bar — so they can't drift apart. **Exposes** `window.EmjiveOrderRows.create({ listEl, rowClass, showPrice, onModify, onResize })` → `{ render(items, { animate }), settledHeight(), buttonAt(index) }`.

- **A row is one `<button>`** (`li.order-item > .order-item__inner > button.order-item__content`: thumb, name + `.category.metal.size` via `appendSize()`, the price when `showPrice`) with a spoken `aria-label` ("Modify Furcula, steel, size 62.50"). A tap anywhere on the `<li>`, padding included, calls `onModify(binding)` — no hover state, no in-row overlay; the Modify sheet does the rest. A row mid-collapse ignores taps.
- **Rows follow the selection one change at a time** instead of being rebuilt. With `animate` on, `render()` runs `EmjiveSelection.singleChange()` over the old and new keys: an **update** (a Save) crossfades just the parts of that row that changed — icon, label, price (`fadeSwap()`: `.is-swapping` fades a part out in 0.12s, the new value goes in, a new icon only once decoded so there's never a blank frame, and it fades back in over 0.18s; a per-element token makes the latest swap win); a **remove** (an Unselect) collapses the row (`.is-removing`, taken out once *both* the inner's `max-height` transition *and* its invert band's own opacity transition have ended, or a 400ms fallback — the band now fades out on a longer, delayed schedule than the row's own collapse, per `styling.md`'s "bar first-in/last-out" rule, so `collapse()` races both via `Promise.all` rather than just the one that used to finish last); an **insert** (an Undo) plays that collapse in reverse — the row goes in at full size so `onResize()` can measure where the list is heading, snaps shut under `.is-instant` with no frame painted in between, and opens from there on the next frame, `.is-expanding` clipping it meanwhile. Anything it can't explain as one change, or `animate` off, rebuilds.
- **The list emptying out is left to the page** (the drawer closes, the order list crossfades to its empty state), which simply stops calling `render()` — so the last row leaves along with its list rather than collapsing on its own first, and an Undo finds it still in place.
- **`settledHeight()`** — the list's height once every row now collapsing or expanding has finished. What the bar's drawer sizes itself to, so it heads straight for its final height rather than overshooting and correcting afterwards.
- **`buttonAt(index)`** — the row button now at that index. The Modify sheet's `returnFocus` looks it up late, since rows come and go.

## `js/modify-modal.js` (~815 lines) — the Modify sheet

The one "Modify" popup on the site, opened by tapping a row in either list — so it lives on all seven pages and builds its own DOM at load (`#modifyModal`, a `.size-modal--drawer.size-modal--modify` bottom sheet; no page has markup for it). **Exposes** `window.EmjiveModifyModal = { open(item, index, options), isOpen(), attach(bar) }`.

- **`open()`** resolves the item's product (`item.series`, falling back to `EmjiveSeries.slug` for a selection saved before that field existed) via `EmjiveSeries.loadProducts()`, since the stored snapshot doesn't carry `per-metal-specs`/`icons`. An `openToken` makes the latest tap win over a slower earlier fetch; a product that's gone, or a failed fetch, `alert()`s rather than leaving a row that silently does nothing. Calls while the sheet is open are ignored — the row it's showing is the only one in view. The products behind the current selection are **prefetched on `load`**, so even the first Modify on the order page doesn't wait on `products.json`.
- **The sheet opens before the model.** Slide 1 starts as the model's `assets["fallback-img"]` image, in a box sized exactly like the viewer (`.size-modal__model-poster`); the WebGL viewer (`maxPixelRatio: 1.5`) is built only once the sheet has slid in (`transitionend` on the sheet's `transform`, or 400ms), and takes its place — its own poster is that same image, so nothing moves. Building a viewer means a new WebGL context and a synchronous shader compile, which is a long hold on a phone's main thread; the sheet used to wait for it. No context to be had, or a later `onError`: the image stays, or comes back. Photos follow as `EmjiveCarousel.imageSlide()` slides — the small carousel is `js/carousel.js`. A metal pick re-tints the live model (`applyMetal`) or swaps the stand-in image.
- **`options`** — `bar`: the page's bar, as `{ el, show(strip), hide(strip) }` — the strip lives in `el`, and `show`/`hide` let that bar hand its own content over its own way (`selection-bar.js`'s summary slot, `selection-page.js`'s checkout bar); `onOpen()`/`onClose()` (the floating bar's drawer shrinks to the row and grows back; the order page's drawer opens and closes); `returnFocus`/`fallbackFocus` (an element or a function returning one).
- **Its buttons live in the page's bar** — the strip (`.modify-strip`), mounted into the bar as soon as the bar exists, via `attach(bar)` (called by `selection-bar.js` and `selection-page.js`), rather than in the middle of the first open. Unselect (the left quarter, plain `--white` label) and Save (the right three quarters, label centered on the whole bar; `disabled` while the field holds nothing orderable — `isValidSize`) share one invert band (`.modify-strip__band`) sized to Save's own button at rest, so only Save's label reads dark on a light band — Unselect and Undo are never under it (an earlier version gave each of Unselect/Save its own band, measured by this file into `--unselect-band`/`--save-band` on every open and resize; both the second band and the measuring are gone now). The strip's own outer show/hide (`bar.show`/`hide`) splits its dark surface (`css/style.css`'s `.modify-strip::before`, grouped with the band) from its buttons' opacity — surface leads in/trails out, buttons the reverse, `css/style.css`'s `--fade-fast` each — since a pseudo-element's opacity is capped by its host's, so the old single-opacity container couldn't time the two independently. The focus trap `include`s the strip, so Tab reaches Unselect and Save; Enter in the size field saves.
- **Save** → `updateItem()` (metal, `normalizeSize()`d size, that metal's price and icon), the sheet closes, and the band — grown to cover the whole strip, then faded out (`css/style.css`'s `.is-saved` rule, ~0.5s total: the width grow doubles as the fade's own delay) — finishes before `bar.hide()` hands the bar back (`leaveAfterSave`/`exitStrip`, waiting on the band's own `opacity` `transitionend`, with `SAVE_LEAVE_MS` — 600ms, sized for this longer real transition rather than reusing `LEAVE_MS` — as its fallback; that reuse used to make the 400ms fallback win the race and cut the band's fade off ~100ms early). **Unselect** → `removeItem()`, with the item kept aside; the band regresses to `width: 0`, "Undo" crossfading in partway through, focus moves to it, and the sheet closes. **Undo** (offered for `UNDO_MS`, 4s) → `insertItem()` back at its index; its label fades out on its own (the band's already gone), then the bar gets its content back (`leaveStrip`/`exitStrip`, `LEAVE_MS` fallback) and focus goes to the restored row. An unused offer runs out the same way, the removal standing; another Modify opening meanwhile ends it early (`commitUndo`). Nothing here re-renders anything — the lists follow `emjive:selection-changed`.
- **Events** — dispatches `emjive:modify-open` before building anything (`product.js` closes its size sheet; `main.js` frees a WebGL slot) and `emjive:modify-close` once its viewer is actually disposed, after the slide-out.
- **`pagehide`** — closes the sheet, disposes the viewer at once rather than after the slide-out (a bfcached page is still live, context and all), and ends any Undo offer, so a restored page doesn't come back offering one.

## `js/selection-bar.js` (~685 lines)

The floating bar, on every page except `launch-order.html` (that page isn't in its script list at all, plus it self-guards with `if (!window.EmjiveSelection) return;`). Builds its whole DOM programmatically and appends to `<body>`.

**The summary row's one slot** shows exactly one thing at a time, in this order of precedence: `add` ("Add", while `product.html`'s size sheet holds an orderable size), `strip` (the Modify sheet's strip, while the sheet is up or its Undo is on offer), `order` (the thumbnail strip + "Order ›") and `empty` ("No selected item"). `computeSummaryMode()`/`summaryElFor()` pick one; `updateSummaryState()` swaps. The swap is **sequenced, not simultaneous**: the incoming label only starts fading in once the outgoing one has fully faded out (`revealCurrentSummaryMode()`, chained off the outgoing element's own `transitionend` — filtered on `e.target`, not just `propertyName`, now that the strip's own opacity is two separately-timed layers rather than one, so a button's faster leg bubbling up can't fire this early — with a 350ms fallback for a backgrounded tab) — a simultaneous crossfade left two semi-transparent labels stacked mid-transition. A swap asked for while another is still mid-fade **retargets** it rather than starting a second one on top (saving and at once tapping another row, a size typed during an Undo offer). Hidden labels are `inert`, and so is the whole summary row while the strip covers it. All share one `--fade-fast` opacity duration — see `styling.md`. **The icon strip joins this same reveal now, rather than fading in on its own the instant `is-add-active`/`is-strip-active` clears**: `updateSummaryState()` still hides it at that same instant (its own `.is-hidden` class), but `revealCurrentSummaryMode()` is what un-hides it, alongside Order/the empty label — so icons and whichever label is coming back fade in together instead of icons arriving a beat early, the bug this fixed.

**`window.EmjiveSelectionBar = { showAction(label, onConfirm), hideAction() }`** — `product.js`'s way into the `add` mode. While it's on, `.is-add-active` makes the *whole bar* the button — a bar-level click listener fires `pendingConfirm` (ignoring clicks from inside the drawer, since a drawer row's tap can still be bubbling through the bar when the mode changes under it); `addActionBtn` deliberately has no listener of its own, to avoid double-firing — and the drawer sits out.

**The drawer** lists the items as `js/order-rows.js` rows (`.order-item--drawer`); tapping one calls `openModify()`, which opens the Modify sheet with this bar as its `bar` (`stripHost`, `attach`ed at load). The drawer's height is a real measured px value, set on the drawer and on its inner scroll box alike by `syncDrawerHeight()` — it reads `rows.settledHeight()`, caps the list at two thirds of the screen (`LIST_CAP`), and publishes `--selection-bar-live-height` (summary + the height the drawer is heading to) on `<html>` for either sheet to rest on. While the Modify sheet is up the drawer is **reduced to the tapped row** (`setDrawerReduced()`): its height becomes that row's, `.is-drawer-reduced` stops scrolling by hand (a space-taking scrollbar's width goes back as padding, so the rows keep their width), and `animateDrawerScroll()` moves the list's scroll in step with the height transition — each frame, the same share of its distance as the drawer has covered of its own — so the row glides into place right above the bar. When the sheet goes, height and scroll go back. `setDrawerOpen()` registers the drawer with `window.EmjiveMenus`, whose `root` also counts `#modifyModal` as inside — the sheet's backdrop closes the sheet, not the drawer.

**The icon strip** (newest first in DOM, so the oldest pick stays anchored next to Order) animates only the one icon a change touched (`EmjiveSelection.singleChange()`): an Add slides its icon in from the screen's left edge (`playEnterAnimation`), an Unselect collapses it (`playExitAnimation`), an **Undo plays that collapse in reverse** (`playRestoreAnimation` — told apart from an Add by the change event's `detail.action`), a Modify swaps its `src`. Anything else rebuilds. The strip doesn't shrink to fit once wide: `.selection-bar__icon` is `flex-shrink: 0` and the strip `justify-content: flex-end`, so the excess overflows past its *left* edge, where `.selection-bar__toggle` clips and fades it — see `styling.md`.

This file has no notion of **which page it's on**, which was always the point. It subscribes to `window.EmjiveHero.onScroll` for the homepage's scroll-driven entrance — unconditionally: the active series' hero owns all the geometry and publishes how far past its trigger the page has scrolled, and this file measures its own `.selection-bar__summary` height to turn that into a transform. On a page with no hero nothing ever publishes, so the bar just stays visible. The starting-hidden state is `css/style.css`'s `body.has-series-hero` scoping (see `pages.md` for why that stopped being `:has()`).

Listens for `emjive:selection-changed` (`render(e)`) — this is how it stays in sync with adds from `product.js` and every change the Modify sheet makes.

## `js/selection-page.js` (~390 lines) — `launch-order.html`'s checkout review

The order page's logic — see `pages.md`'s `launch-order.html` section for what it all looks like.

- **Rows** — `js/order-rows.js` rows with prices; tapping one opens the Modify sheet with the checkout bar as its `bar`. `render()` runs on load and on every `emjive:selection-changed`, and the rows animate just the one change. `listState` tracks whether the list or the empty state is showing: the last item leaving crossfades the list into the empty state, and an Undo crossfades it back (`crossfade(fromEl, toEl)` — a sequential opacity swap, hand-orchestrated because `[hidden]` is `display: none`, which can't transition; a newer one supersedes one still under way).
- **The checkout bar as the strip's host** (`stripHost`, `attach`ed at load): showing the strip sets `.is-strip-active` (a pure-CSS, `transition-delay`-sequenced swap — now a three-beat cascade, row-out then the strip's own surface-in then its content-in, since the strip's reveal itself split into two beats — see `styling.md`), makes the bar's own row `inert`, and — through `stripShown` — keeps the bar up for an Undo that followed the last item out. The checkout button ignores clicks meanwhile.
- **The drawer over the checkout bar** — this page's version of the floating bar's drawer shrinking to the tapped row: `.order-checkout-drawer`, a fixed element built here holding a copy of the tapped row (its own `EmjiveOrderRows`, `inert` and `aria-hidden` — assistive tech already has the real row in the list). Opened on the sheet's `onOpen` (max-height to the row's measured height, publishing `--selection-bar-live-height` so the sheet rests on it), closed on `onClose`. A Save crossfades the copy along with the real row (`detail.action === "update"`); an Unselect leaves it to close with the sheet.
- **Shipping/terms/checkout** — `SHIPPING_OPTIONS`, a small in-file placeholder array (easy to extend later, not a restructure), rendered as a single-select dot-indicator list. Shipping is part of the checkout bar's total. The terms row's click is delegated across the whole element (the dedicated tick-box or the surrounding sentence both toggle; a click on the actual `<a>` to `terms.html` navigates instead). `updateCheckoutGate()` disables `#orderCheckoutButton` until both a shipping option is selected and terms are ticked. The button itself is a stub — no Stripe session exists yet, so a click (once enabled) just `alert()`s that it isn't connected, the same convention `main.js`'s guarded `#contactForm` handler uses.

## Cross-cutting contracts (the highest-value section if you're changing behavior that spans files)

- **`window.EmjiveSeries`** — set by `js/series.js` (blocking, in `<head>`), consumed by `main.js`, `product.js`, `modify-modal.js` and `series-page.js`. The one place "which series is this, and where's its data" lives.
- **`window.EmjiveHero`** — set by `js/series.js`, published to by the active series' `hero.js`, subscribed to by `selection-bar.js`. A plain function registry, one number: how far past the hero's trigger point the page has scrolled.
- **`window.EmjiveMenus`** — set by `js/series.js`, registered with by `main.js` (header menu) and `selection-bar.js` (drawer — whose `root` also counts the Modify sheet as inside). Click-away coordination: a click outside every currently-open panel's root closes only the most-recently-opened one.
- **`window.EmjiveSeriesHero`** — set by a series' `hero.js`, called by `js/series.js`. `{ init(root, ctx), onProducts(products) }`.
- **`window.EmjiveModelViewer`** — set by `three-viewer.js`, consumed by `main.js` (grid), `product.js` (carousel), `modify-modal.js` (the sheet's small carousel), and `scene-tool.html` (a standalone dev tool, `options.freeOrbit`/`options.primitive`). The one place 3D viewer construction/materials/camera behavior lives.
- **`window.EmjiveSelection`** — set by `selection.js`, consumed by `product.js` (add, plus the size helpers), `modify-modal.js` (remove/insert/update, plus the size helpers), `order-rows.js` (`appendSize`, `itemKey`/`singleChange`), `selection-bar.js` (read, `itemKey`/`singleChange` for its icons) and `selection-page.js` (read).
- **`window.EmjiveSelectionBar`** — set by `selection-bar.js`, consumed only by `product.js`. `{ showAction(label, onConfirm), hideAction() }` — lets the size-selection sheet on `product.html` delegate its actual "Add" action to the bar itself, instead of a button inside the sheet. (The Modify sheet doesn't go through this: it hands the bar its whole strip, via the `bar` option below.) `product.js` guards every call (`if (window.EmjiveSelectionBar) …`) even though load order guarantees it's already set by the time `product.js`'s deferred code runs.
- **`window.EmjiveFocusTrap`** — set by `focus-trap.js` (all seven pages), consumed by `product.js` (`#sizeModal`) and `modify-modal.js` (`#modifyModal`). Also owns the page lock (`html.is-modal-open`). See its own section for the constraints that aren't obvious from the API.
- **`window.EmjiveCarousel`** — set by `carousel.js`, consumed by `product.js` and `modify-modal.js`. `EmjiveCarousel(carouselEl)` → `{ sync(reset) }`, plus `EmjiveCarousel.imageSlide(src, alt)`.
- **`window.EmjiveOrderRows`** — set by `order-rows.js`, consumed by `selection-bar.js` (the drawer) and `selection-page.js` (the order list, and the copy in its drawer over the checkout bar). `create(options)` → `{ render, settledHeight, buttonAt }`.
- **`window.EmjiveModifyModal`** — set by `modify-modal.js`, consumed by `selection-bar.js` and `selection-page.js`. `{ open(item, index, options), isOpen(), attach(bar) }`; `options.bar` (`{ el, show(strip), hide(strip) }`) is the contract between the sheet and whichever bar hosts its strip.
- **`"emjive:modify-open"` / `"emjive:modify-close"`** — `CustomEvent`s on `window`, dispatched by `modify-modal.js` before it builds anything and once its viewer is disposed. `product.js` closes its size sheet on the first; `main.js`'s grid gives up one WebGL slot between the two.
- **`prefers-reduced-motion`** — honoured in two places that don't know about each other. `css/style.css`'s trailing `@media` block collapses every CSS transition site-wide (at `0.01ms`, **not** `0s` — see that block's own comment; several `transitionend` listeners drive real logic and a `0s` transition never fires one). `js/three-viewer.js` reads the query directly via `matchMedia` for the four things CSS can't reach: release inertia, the ease-back-to-default pose reset, the up-vector leveling drift and the idle nudge. It reuses `freeOrbit`'s existing plumbing via a shared `noAutoMotion()` predicate, so the two switches can't drift apart. Deliberately **not** a shared `window.Emjive*` global: `three-viewer.js` is the only JS consumer, and it's also loaded by `scene-tool.html`, which loads no `series.js` at all. The homepage hero's x-ray wipe is deliberately **not** gated — it's scroll-linked and entirely visitor-driven, nothing plays on its own, and short-circuiting it would strand the floating selection bar off-screen (see `window.EmjiveHero` above).
- **`window.EmjiveScrollMemory`** — set by `scroll-memory.js` (`index.html` only), consumed only by `main.js`, which calls `contentReady()` once the grid is rendered and filtered. Guard every call on the object existing; it is absent on every other page.
- **`"emjive:selection-changed"`** — `CustomEvent` on `window`, dispatched synchronously by every `selection.js` mutation, with `detail: { action, index }`. `selection-bar.js` and `selection-page.js` listen for it.
- **`pagehide` / `pageshow`** — five separate files listen, for three different reasons, and it's worth knowing which is which before adding another. `main.js` (grid) and `product.js` (carousel) release their viewers on `pagehide` and rebuild on `pageshow` with `event.persisted`, so a bfcached page holds no GPU memory; `modify-modal.js` closes its sheet and disposes its viewer on `pagehide`, and ends any Undo offer, without rebuilding anything; `three-viewer.js` drops its decoded-HDRI cache on `pagehide` and registers `requestRepaint` on `pageshow` for the discarded-drawing-buffer case; `scroll-memory.js` saves the offset on `pagehide` and restores it on a persisted `pageshow`. Nothing uses `unload` anywhere — an `unload` listener would disqualify the page from the back/forward cache entirely, which is the thing all of the above are written around.
- **`localStorage["emjive_selection"]`** — the persisted selection array (via `selection.js`).
- **`sessionStorage["emjive_model_interacted"]`** — unrelated to selection; remembers within a browsing session whether the visitor has already discovered models are draggable, to stop nudging them with the wiggle hint (set/read in `three-viewer.js`).
- **`sessionStorage["emjive:scroll:<key>"]` + `history.state.emjiveScrollKey`** — the saved `{ y, h }` for one history entry and the token that names it (`scroll-memory.js`). Anything calling `history.replaceState` on `index.html` must pass `history.state` back through rather than `null`, or the token is lost.
- **Item shape**: `{ series, productId, name, category, metal, size, price, image }` (see `selection.js` above).
